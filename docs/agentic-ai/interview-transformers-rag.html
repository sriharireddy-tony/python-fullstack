Section 1

LLM & Transformer fundamentals

The bar here is not reciting the architecture diagram. It is being able to say why each block exists — what breaks without it — and to trace a token from string to logit without hand-waving.

1.1

Walk me through a Transformer from input tokens to generated output.

coremust be fluent

The answer they want is a pipeline, in order, with a reason attached to each stage. Here it is for a decoder-only model — GPT, Llama, Qwen — which is what almost everything in production now is. 

  "payslip is blank"
        │
        ▼  tokenizer (BPE)              text → integer ids
  [1350, 8391, 374, 10321]
        │
        ▼  embedding lookup             ids → vectors      [T, d_model]
  [[0.02, -0.11, …], …]
        │
        ▼  + positional information     order becomes visible
        │
        ▼  ┌─────────────────────────┐
        │  │  N × TRANSFORMER BLOCK  │
        │  │                         │
        │  │   x + Attention(LN(x))  │  ← mix across tokens
        │  │   x + FFN(LN(x))        │  ← think per token
        │  └─────────────────────────┘
        │
        ▼  final layer norm
        ▼  output projection            [T, d_model] → [T, vocab]
  logits
        │
        ▼  softmax + sampling           pick the next token
  "for"
        │
        └──────► append, feed back in, repeat

The two-line summary of a block, which is worth memorising:

  • Attention mixes information across tokens. It is the only operation in the whole model where one position can see another.
  • The FFN transforms each token independently. Same weights applied at every position, no communication.

Everything else — residuals, normalisation, positional encoding — exists to make those two operations trainable at depth.

Where candidates lose the room

Saying "the encoder processes the input and the decoder generates the output" for a model that has no encoder. GPT, Llama and Qwen are decoder-only. Know which architecture you are describing before you start.

1.2

Encoder-only, decoder-only, encoder–decoder — when would you pick each?

core

The distinction is what each token is allowed to see, and that determines what the model is good for.

ArchitectureEach token seesGood atExamples
Encoder-onlyThe whole sequence, both directionsUnderstanding: classification, NER, embeddingsBERT, most embedding models
Decoder-onlyItself and everything before itGeneration, and in practice everything else tooGPT, Llama, Qwen, Gemini
Encoder–decoderEncoder: all. Decoder: past + all of encoderTransduction: translation, summarisationT5, BART, the original 2017 paper

The reason encoder-only wins for embeddings is bidirectionality. To represent "payslip is blank for contractors" as one vector, the word payslip should be informed by contractors. A causal model physically cannot do that — position 1 can never see position 6.

In this system

Both types run side by side. qwen3-embedding:0.6b is encoder-style and produces the 1024-dim vectors for retrieval; qwen3:8b is decoder-only and writes the answers. They are different models doing categorically different jobs, and conflating them is a common interview slip.

1.3

Explain self-attention. Why three projections instead of one?

coredeep

Self-attention lets every token build a weighted summary of every other token, where it chooses the weights itself.

The database analogy is the one that lands:

  • Query — what this token is looking for
  • Key — what each token offers as a match
  • Value — what each token actually contributes if matched

Q·K decides how much to attend; V decides what flows. Collapsing them would force one vector to serve as both the advertisement and the goods — a token could not say "I am the subject of this sentence" as a matching signal while contributing tense information as content.

Scaled dot-product attention, complete

import torch, torch.nn.functional as F

def attention(x, Wq, Wk, Wv, mask=None):
    Q, K, V = x @ Wq, x @ Wk, x @ Wv        # [T, d_k] each
    scores  = Q @ K.transpose(-2, -1)       # [T, T]  token-to-token
    scores  = scores / (Q.size(-1) ** 0.5)  # see 1.4
    if mask is not None:
        scores = scores.masked_fill(mask, float("-inf"))
    weights = F.softmax(scores, dim=-1)     # each row sums to 1
    return weights @ V                      # [T, d_v]

The whole model's expressive power lives in that [T, T] matrix. Row i is a probability distribution: "given what I am, how much of each other token do I want?"

The cost nobody mentions until it hurts

That matrix is O(T²) in both time and memory. Doubling context quadruples attention cost. This is the single reason long-context is hard, and why FlashAttention, sliding-window attention, and GQA exist.

1.4

Why divide the scores by √dk?

favourite follow-up

To stop softmax saturating and killing the gradient.

If Q and K components are roughly independent with unit variance, their dot product over dk dimensions has variance ≈ dk. At dk = 128 the scores swing by ±11 or so. Feed that to softmax and it collapses to nearly one-hot — one token gets weight ~1.0, the rest ~0.

A saturated softmax has a vanishing derivative, so gradients stop flowing and the layer stops learning. Dividing by √dk renormalises the variance back to ~1 and keeps the distribution soft enough to train.

The effect, in three lines

d_k = 128
scores = torch.randn(1, 8) * (d_k ** 0.5)   # unscaled magnitude

F.softmax(scores, -1)               # → [0.98, 0.01, 0.00, …]  saturated
F.softmax(scores / d_k**0.5, -1)    # → [0.31, 0.18, 0.12, …]  learnable
Say this and you sound senior

"It's a variance-control trick, not a normalisation of the output. The scaling keeps the softmax in its high-gradient region — without it, deep models with large head dimensions barely train."

1.5

What does multi-head attention buy that a single large head does not?

core

Multiple attention patterns at once. One softmax produces one distribution — one thing a token can look at. Real language needs several simultaneously: the syntactic head of the phrase, the coreferent pronoun, the adjacent token.

Crucially, heads split the dimension rather than adding to it: dhead = dmodel / h. Eight heads of 64 across a 512-dim model costs the same FLOPs as one head of 512 — you get diversity for free.

Multi-head, batched

class MultiHeadAttention(nn.Module):
    def __init__(self, d_model, n_heads):
        super().__init__()
        self.h  = n_heads
        self.dk = d_model // n_heads          # 512 / 8 = 64
        self.qkv = nn.Linear(d_model, 3 * d_model)
        self.out = nn.Linear(d_model, d_model)   # W^O: mixes heads back

    def forward(self, x, mask=None):
        B, T, C = x.shape
        q, k, v = self.qkv(x).chunk(3, dim=-1)
        # [B, T, C] -> [B, heads, T, dk] so heads batch like extra samples
        q, k, v = (t.view(B, T, self.h, self.dk).transpose(1, 2) for t in (q, k, v))

        att = (q @ k.transpose(-2, -1)) / self.dk**0.5
        if mask is not None:
            att = att.masked_fill(mask, float("-inf"))
        y = F.softmax(att, dim=-1) @ v

        y = y.transpose(1, 2).contiguous().view(B, T, C)   # concat heads
        return self.out(y)

W^O is not decoration. Without it the heads are concatenated but never combined, and the next layer sees eight independent 64-dim opinions rather than one 512-dim representation.

Modern models often use Grouped-Query Attention: many query heads share a smaller number of K/V heads. That shrinks the KV cache (see 1.12), which is the real memory constraint at inference.

1.6

What is cross-attention and where does it appear?

core

Identical mechanism, different source. In self-attention Q, K and V all come from the same sequence. In cross-attention, Q comes from one sequence and K, V from another. 

# self-attention        : one sequence talking to itself
Q, K, V = x @ Wq, x @ Wk, x @ Wv

# cross-attention       : decoder asking the encoder
Q       = decoder_state @ Wq      # "what do I need next?"
K, V    = encoder_out   @ Wk, encoder_out @ Wv   # "here is the source"

It is the bridge in an encoder–decoder model: it is how a translation decoder looks back at the source sentence. Decoder-only models have no cross-attention — the "source" is simply earlier tokens in the same stream, which is exactly why prompting works at all.

The RAG connection worth making

"RAG is cross-attention done in retrieval space instead of parameter space. Rather than training a component to attend over a corpus, you fetch the relevant part and paste it into the context — then ordinary self-attention does the work. That's why RAG needs no fine-tuning."

1.7

Why is masked attention necessary, and what exactly is masked?

coretrap

Without a causal mask, training is cheating: the model predicting token 5 could attend to token 5. It would learn to copy, score near-zero loss, and generate nonsense at inference where the future does not exist.

The mask sets the upper triangle of the score matrix to −∞ before softmax, so those positions receive exactly zero weight.

The causal mask

T = 5
mask = torch.triu(torch.ones(T, T, dtype=torch.bool), diagonal=1)
# True = block
#  F T T T T      token 0 sees only itself
#  F F T T T      token 1 sees 0,1
#  F F F T T
#  F F F F T
#  F F F F F      token 4 sees everything

scores = scores.masked_fill(mask, float("-inf"))   # BEFORE softmax

−∞ before softmax, not zero after. Zeroing weights afterwards breaks the normalisation — the surviving row no longer sums to 1, and you have silently rescaled every attention output.

Two masks, often confused

Causal mask hides the future and is architectural. Padding mask hides <pad> tokens in a batch of uneven lengths and is a batching artefact. Forget the padding mask and your model attends to padding, which quietly poisons short sequences in a batch.

1.8

Why does a Transformer need positional encoding at all?

coredeep

Attention is permutation-equivariant. It is a weighted sum over a set. Shuffle the input and you get the same outputs, shuffled — so "payroll blocked release" and "release blocked payroll" are literally indistinguishable to bare attention.

SchemeHowExtrapolates?Used by
SinusoidalFixed sin/cos of varying frequency, added to embeddingsIn principleOriginal 2017 paper
Learned absoluteA trainable vector per positionNo — hard cap at trained lengthBERT, GPT-2
RoPERotates Q and K by an angle proportional to positionYes, and interpolates wellLlama, Qwen, most modern models
ALiBiLinear distance penalty added to scoresYesBLOOM, MPT

RoPE won because it encodes relative position as a natural consequence of rotation: the dot product between a rotated query and a rotated key depends only on the difference of their angles. Relative distance is what language actually cares about — "the previous word" matters, "word 4,197" does not.

Production symptom

A model that degrades sharply past its trained context length is usually hitting positional extrapolation failure, not "running out of memory". Context extension via RoPE scaling (NTK, YaRN) is the standard fix and it is not free — quality drops as you stretch.

1.9

What does the feed-forward network do? It looks like filler.

deep

It is two thirds of the parameters and the current best guess at where factual knowledge is stored.

Attention moves information between positions but is fundamentally a weighted average — it is linear in V. The FFN is where the non-linear transformation happens, applied identically at every position. 

class FeedForward(nn.Module):
    def __init__(self, d_model, expansion=4):
        super().__init__()
        self.up   = nn.Linear(d_model, expansion * d_model)   # 512 -> 2048
        self.down = nn.Linear(expansion * d_model, d_model)   # 2048 -> 512

    def forward(self, x):
        return self.down(F.gelu(self.up(x)))

The expand-then-project shape is the point. Widening to 4× creates room to compute many features in parallel; the projection back selects and recombines them. A useful mental model from the interpretability literature: the up-projection is a set of key detectors, the down-projection their associated values — a soft key-value memory.

Modern models use SwiGLU with a gate, and typically ~⅔·4·d to keep the parameter count comparable: 

def swiglu(x, W_gate, W_up, W_down):
    return (F.silu(x @ W_gate) * (x @ W_up)) @ W_down
The one-liner

"Attention decides what to look at; the FFN decides what to think about it. Editing-model research locates factual recall in FFN weights, not attention."

1.10

Residual connections and layer norm — why both, and does order matter?

deeptrap

Residuals give gradients a path that skips every non-linearity. x + f(x) has derivative 1 + f'(x), so even when f' vanishes the gradient still flows. Without them, 96 stacked layers do not train.

They also create the residual stream: a running representation that each block reads from and writes into, rather than replaces.

Layer norm normalises across the feature dimension per token — independent of batch size, which is why it is used instead of batch norm for variable-length sequences.

Order matters more than it looks

# Post-LN — the 2017 original
x = LayerNorm(x + Attention(x))
x = LayerNorm(x + FFN(x))
# needs LR warmup; unstable beyond ~12 layers

# Pre-LN — what everything modern uses
x = x + Attention(LayerNorm(x))
x = x + FFN(LayerNorm(x))
# clean residual path; trains at 100+ layers without warmup

In Pre-LN nothing sits between the input and output of the residual, so the gradient highway is unobstructed. That single rearrangement is what made very deep Transformers trainable.

Most current models also use RMSNorm — drop the mean-centring, keep the scaling. Marginally cheaper, empirically just as good.

1.11

Why subword tokenization, and how does it bite you in production?

coreRAG-relevant

Word-level vocabularies cannot handle unseen words; character-level makes sequences far too long, and attention is O(T²). BPE splits the difference: start from characters, repeatedly merge the most frequent adjacent pair, stop at a target vocabulary size. 

from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-Embedding-0.6B")

tok.tokenize("payslip")      # ['pay', 'slip']          common → few tokens
tok.tokenize("OS-1042")      # ['OS', '-', '104', '2']  identifiers shatter
tok.tokenize("ERR-40001")    # ['ERR', '-', '400', '01']
This is a real RAG failure, not trivia

Identifiers, error codes and SKUs fragment into meaningless pieces. The embedding of ERR-40001 is not close to the embedding of ERR-40002 in any useful way — and it is not far from it either. Embeddings are systematically bad at exact tokens, and that is the single strongest argument for hybrid retrieval (see 3.6).

In this system

Measured on 24 error-code queries: semantic search reached recall@20 = 0.583; keyword search reached 1.000. Same corpus, same queries. Tokenization is why.

1.12

Explain autoregressive generation. What is the KV cache and why does it matter?

coredeep

Generation is a loop: run the model, take the logits at the last position, sample a token, append it, repeat. 

tokens = tokenizer.encode(prompt)
for _ in range(max_new_tokens):
    logits = model(tokens)[:, -1, :]          # only the last position matters
    logits = logits / temperature
    probs  = F.softmax(top_p_filter(logits, p=0.9), dim=-1)
    nxt    = torch.multinomial(probs, 1)
    if nxt == eos_id:
        break
    tokens.append(nxt)

Naively that recomputes attention over the whole prefix every step — O(T²) per token, O(T³) for the sequence. But K and V for past tokens never change (the causal mask guarantees the past cannot see the future). So cache them: 

k_cache = torch.cat([k_cache, k_new], dim=2)   # append one column
v_cache = torch.cat([v_cache, v_new], dim=2)
att = (q_new @ k_cache.transpose(-2, -1)) / dk**0.5   # one row, not a matrix

Which produces the two-phase behaviour you see in any served model:

PhaseWorkBound byFeels like
PrefillAll prompt tokens in parallelComputeTime to first token
DecodeOne token at a time, reading the cacheMemory bandwidthTokens per second

Cache size = 2 × layers × heads × d_head × seq_len × bytes, per sequence. It grows linearly with context and is usually what limits how many concurrent requests a GPU can hold — hence GQA, paged attention, and quantised caches.

In this system

The local model was emitting chain-of-thought before answering: 217 output tokens for "Say OK" against 9 from the hosted model. Decode is the slow phase, so that made re-ranking time out against a 25-second deadline. Fixed by passing "think": false — the output is schema-constrained anyway, so the reasoning was generated and discarded.

Section 2

Embeddings & vector representations

The section where hand-waving is most obvious. Interviewers probe whether you have actually looked at the numbers — what a cosine of 0.44 means, why your dimension is what it is, whether you know your model is asymmetric.

2.1

What is an embedding, precisely?

core

A learned map from text to a fixed-length vector, trained so that geometric closeness corresponds to semantic closeness.

"Fixed-length" is the load-bearing part: a three-word title and a two-page description both become 1024 numbers. That is what makes them comparable and indexable — and also what makes them lossy.

The map is learned by contrastive training: pull known-related pairs together, push random pairs apart. So an embedding space encodes whatever notion of relatedness was in the training pairs — which is why a general model has no idea that 80C and section 80C investment proof are the same thing in Indian payroll.

Text in, vector out — production path

vector = await embeddings.embed_query("payslip is blank for contractors")
len(vector)      # 1024
vector[:5]       # [0.0268, -0.0332, 0.0095, 0.0092, 0.0123]
Sharpen it

"An embedding is a lossy compression optimised to preserve one specific thing — similarity as defined by the training objective. It is not a summary, and it is not reversible."

In this system

With re-ranking off, the entire similar-issues feature makes zero LLM calls: one embedding call, one vector search, one SQL query.

2.3

How do you choose the embedding dimension?

deepexpects a real answer

Higher dimensions carry marginally more information and cost linearly more in storage, memory and every distance computation. The honest answer is that you measure it rather than reason about it.

In this system — a decision I got wrong first

The build started on qwen3-embedding (8B) at 4096 dimensions. That was never a decision — it was the default the model emitted. Moving to the 0.6B variant gave 1024 native: a quarter of the storage, a quarter of the index memory, and roughly 4× faster distance computation.

What made it a one-line change is that the dimension is probed from the model at startup, never configured — and source_hash includes the model name, so every stored vector invalidated automatically.

The senior answer

"I inherited 4096 from the model default, which is not a justification. The way to settle it is to truncate to 2048/1024/512 and run the retrieval eval at each — recall@k is free to compute. If quality is flat at 1024, take the 4× saving."

2.4

Cosine, dot product, Euclidean — which and why?

core

Cosine, for text, almost always. The reason is length.

Euclidean distance is sensitive to vector magnitude, and magnitude in text embeddings correlates with document length. Use L2 and a long ticket and a short ticket about the identical bug look far apart — you have built a length filter wearing a similarity filter's clothes.

Cosine compares direction only, which is the semantic part. 

import numpy as np

def cosine(a, b):
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

# If vectors are pre-normalised to unit length, cosine IS the dot product --
# and dot product is a single fused instruction, so most vector databases
# normalise on write and use dot internally.
a, b = a / np.linalg.norm(a), b / np.linalg.norm(b)
similarity = float(a @ b)
The bug this causes when porting

Some stores return distance (smaller is closer), others similarity (larger is closer). Chroma returns cosine distance; Pinecone returns cosine similarity. Carrying a 1 - d conversion across a migration inverts every ranking while still producing plausible-looking numbers between 0 and 1. Convert once, at the adapter boundary, and assert the direction.

2.5

What are asymmetric embeddings and why do they matter?

deepsilent failure

Many retrieval models are trained so that queries and documents are encoded differently — typically a task-instruction prefix on the query only. A short question and a long passage are different kinds of text, and forcing them through one encoding loses recall. 

# Query gets an instruction prefix
EMBED_QUERY_INSTRUCTION = (
    "Instruct: Given a software bug report, retrieve other bug reports "
    "describing the same underlying problem\nQuery: "
)
EMBED_DOCUMENT_INSTRUCTION = ""      # documents get nothing

async def embed_query(self, text):
    return (await self._embed([f"{self._query_instruction}{text}"]))[0]

async def embed_documents(self, texts):
    return await self._embed([f"{self._document_instruction}{t}" for t in texts])
Why this is dangerous

Using the wrong one produces no error whatsoever. You get a valid vector of the right dimension. Recall is simply worse, and unless you have an evaluation harness you will never know.

In this system

The port exposes embed_query and embed_documents as separate methods precisely so this cannot be got wrong silently. A single embed(text) would compile, run, and quietly under-perform.

2.6

A result has cosine similarity 0.44. Is that a good match?

excellent question to be asked

Unanswerable without calibration for your corpus and model — and saying so is the correct answer.

Cosine between two pieces of ordinary English rarely drops below ~0.3 even when the texts are unrelated. They share syntax, function words, and register. So a naive reading of 0.44 as "44% similar" is badly wrong — it is closer to no match at all.

In this system — measured, not guessed
PaircosineReality
OS-4 vs OS-18 (same SCIM bug, different words)0.889True duplicate

So the usable band is roughly 0.80+ for duplicates and below 0.55 for noise. The UI labels these very close / close / loose / distant rather than showing a bare percentage, because "44%" reads as a weak match when it means none.

How to answer

"Not without knowing the corpus. I'd embed a few hundred known-related and known-unrelated pairs, plot both distributions, and set the threshold where they separate. Absolute cosine values are not portable across models or domains."

2.7

What are Matryoshka embeddings?

deep

Models trained with Matryoshka Representation Learning apply the loss at several nested prefixes — 64, 128, 256, … 1024 — so the leading dimensions carry the most information. You can then truncate the vector and keep most of the quality. 

full = embed(text)              # 4096 dims
small = full[:1024]             # keep the first quarter
small = small / np.linalg.norm(small)    # MUST re-normalise: truncation
                                         # changes the magnitude

Useful for a two-stage search: retrieve broadly with truncated vectors, then re-score the survivors with full-dimension vectors.

In this system — considered and rejected

Truncating the 8B model to 1024 was the alternative to switching to the 0.6B model. It lost on a design argument: the dimension is probed from the model and treated as authoritative, so a native-1024 model kept that property with a one-line change, whereas truncation meant adding a slice-and-renormalise step plus a configurable dimension — reintroducing exactly the hardcoded value the probe exists to eliminate. It also pays full 8B inference cost and throws away three quarters of the output.

2.8

How does vector search actually work at scale?

deep

Exact search is a linear scan: compute similarity against every vector, O(N·d). Fine at 100k, hopeless at 100M. Production uses approximate nearest neighbour and accepts a small recall loss for a large speed win.

IndexIdeaTrade
HNSWMulti-layer navigable small-world graph; greedy descent from a sparse top layerFast and accurate; high memory; the default
IVFCluster vectors, search only the nearest n clustersLower memory; recall depends on nprobe
PQQuantise sub-vectors to codebook entriesHuge compression; lossy; usually combined with IVF

HNSW's tunables are M (edges per node), ef_construction (build-time breadth) and ef_search (query-time breadth). Only the last is adjustable per query — raise it for recall, lower it for latency.

The one that surprises people

ANN recall is not 100%, and your offline evaluation probably assumed it was. If you measured recall@20 on a small corpus with exact search and then deploy HNSW at scale, real recall is lower — and the gap widens with aggressive filtering, because filtered ANN search can walk the graph into a region where everything is excluded.

3.7

How do you combine two rankings? Talk me through RRF.

deepthe differentiator

Scores from different retrievers are not comparable — a cosine of 0.72 and a ts_rank_cd of 0.09 live on unrelated scales. Reciprocal Rank Fusion sidesteps that by using rank, not score: 

K = 60
scores = defaultdict(float)
for ranked_list in (semantic_hits, lexical_hits):
    for rank, doc_id in enumerate(ranked_list, start=1):
        scores[doc_id] += 1.0 / (K + rank)

Ranks are comparable by construction, a document in both lists is promoted automatically, and there is no weight to tune. It is the standard answer, and it is usually right.

In this system — RRF was measured and rejected

Implemented exactly as above, equal weight, it scored below its own best input on both query families: 0.986 vs 1.000 at R@5 on paraphrases, and 0.792 vs 1.000 at R@20 on identifiers.

The cause is structural, not a misconfiguration. RRF's value is its agreement bonus, and that bonus is also its failure mode when the retrievers are of unequal quality for the query at hand: 

1/(60+35) + 1/(60+2)  =  0.0266   >   1/(60+1)  =  0.0164
  weak retriever's rank 2               strong retriever's rank 1

And weighting the secondary down does not fix it — that is provable. Require that an agreement bonus never lift a document above the leader's own top hit:

1/(K + 2) + w/(K + 1)  <=  1/(K + 1)
                   w   <=  1/(K + 2)  =  0.016   at K = 60

At any weight small enough to be safe, the secondary only orders the tail — which is a cascade. "Keep the agreement bonus" and "never rank worse than the better retriever" are not simultaneously satisfiable.

What shipped instead is a cascade: the leading retriever's order, with the other's finds appended below. It is never worse than the leader alone at any cutoff, and agreed is still recorded so the re-ranker and the UI keep the cross-retriever signal even though ordering no longer uses it.

Why this story lands

It demonstrates measuring a textbook technique instead of adopting it, deriving why the failure is structural, and shipping the simpler thing. Add the honest caveat — unaided on identifiers RRF actually beats the cascade, and the cascade only wins because an exact-match probe handles that family first — and you look like someone who reads their own results carefully.

How do you handle metadata filtering and access control?

coresecurity

Two mechanisms, and mixing them up is how leaks happen.

  • Filtering narrows results — status, date, team. A UX concern.
  • Isolation enforces that a caller can never see another tenant's data. A security boundary.

Never implement isolation as a metadata filter. One forgotten where clause becomes a cross-tenant leak with nothing underneath to catch it.

In this system

Postgres enforces isolation with row-level security and FORCE ROW LEVEL SECURITY across 13 tables — a developer who forgets a tenant clause is caught by the database. The vector store has no equivalent, so isolation is one namespace per tenant: a query names exactly one namespace and cannot read across. There is no filter to forget, and the namespace name derives from the authenticated tenant id, never from client input. 

def namespace_for(tenant_id: uuid.UUID) -> str:
    return f"tenant_{tenant_id.hex}"      # never accepts client input
Pre-filter vs post-filter

Post-filtering retrieves k then discards — a selective filter can leave you with two results out of fifty. Pre-filtering restricts the ANN search itself, which is correct but can degrade recall badly when the filter is narrow, because the graph walk gets trapped. Know which your store does; over-fetch to compensate.

3.10

How do you set a retrieval threshold?

deep

Empirically, from labelled pairs — never from intuition, because the absolute numbers are not portable (see 2.6).

  • Embed known-related and known-unrelated pairs.
  • Plot both similarity distributions.
  • Choose the threshold by the cost of each error: a false positive shows a wrong document; a false negative shows nothing.

For a suggestion panel, false positives cost more. A panel that is sometimes wrong gets ignored, and once ignored it is dead. So bias toward silence.

The design principle

"No results must be a first-class answer. A threshold tuned to always return something is how a retrieval feature loses trust — most queries genuinely have no good match, and saying so is the correct output."

In this system

Two thresholds at different stages: a fused-score floor of 0.012 before re-ranking, and a model-confidence floor of 0.55 after. A 0.3-confidence "related" is noise with a number attached, so it is dropped rather than shown.

3.11

How do you manage the context window?

deepcommon failure

Budget it explicitly rather than hoping. And do not assume a bigger window solves it — lost in the middle is well documented: models attend most reliably to the beginning and end of their context, so material buried in the middle is effectively invisible. 

BUDGET = 8000                       # tokens for retrieved context
used, context = 0, []
for doc in ranked_documents:        # best first
    cost = count_tokens(doc.text)
    if used + cost > BUDGET:
        break                       # stop; do NOT truncate mid-document
    context.append(doc)
    used += cost

Four rules that matter more than the budget number:

  • Order by relevance, and consider putting the best at both ends.
  • Drop whole documents, never truncate one — half a document is often worse than none, because it reads as complete.
  • Label every chunk with its source, so citations can be verified afterwards.
  • Reserve room for the answer. Context plus output must fit.
More context is not free

Cost and latency scale with input tokens, and quality often drops past a point as genuinely relevant material gets diluted by marginal material. Stuffing 20 documents when 5 would do is a common and expensive regression.

4.2

Fixed-size chunking — how much overlap, and why any?

core

Overlap exists to survive a bad cut. If an answer straddles a boundary, neither chunk contains it whole — overlap gives a second chance. 

def fixed_chunks(tokens, size=512, overlap=64):
    step = size - overlap
    return [tokens[i:i + size] for i in range(0, len(tokens), step)]

# 10,000 tokens, size 512, overlap 64
#   stride 448  ->  ~23 chunks  ->  index is ~14% larger than the corpus

10–20% is the usual band. The cost is real and often forgotten: overlap inflates the index, and it puts near-duplicate chunks into your top-k, so three of your five results can be three windows over the same paragraph.

Deduplicate after retrieval

With overlap you should collapse results that share a parent document or overlap textually, otherwise the context window fills with the same sentences repeated. This is a bug people ship without noticing, because each individual result looks relevant.

4.3

How does recursive character splitting actually work?

core

It tries separators in order of preference, and only falls to a worse one when a piece is still too large. 

SEPARATORS = ["\n\n", "\n", ". ", " ", ""]     # best -> worst

def recursive_split(text, size, seps=SEPARATORS):
    if len(text) <= size:
        return [text]
    sep, rest = seps[0], seps[1:]
    parts = text.split(sep) if sep else list(text)

    out, buf = [], ""
    for part in parts:
        candidate = buf + sep + part if buf else part
        if len(candidate) <= size:
            buf = candidate                       # keep accumulating
        else:
            if buf:
                out.append(buf)
            # this part alone is still too big -> recurse with a finer separator
            out.extend(recursive_split(part, size, rest) if len(part) > size else [part])
            buf = ""
    if buf:
        out.append(buf)
    return out

The empty string at the end is the guarantee of termination: worst case it splits per character, so no chunk can ever exceed the limit. That is why it is the safe default — it never produces an oversized chunk that silently gets truncated by the embedding model.

4.4

What is semantic chunking and is it worth it?

deep

Embed each sentence, walk the document, cut where consecutive similarity drops.

vectors = embed([s for s in sentences])
sims = [cosine(vectors[i], vectors[i + 1]) for i in range(len(vectors) - 1)]

threshold = np.percentile(sims, 5)      # relative, not absolute -- see 2.6
boundaries = [i for i, s in enumerate(sims) if s < threshold]

Note the threshold is a percentile of this document, not a fixed number. An absolute cutoff fails for the reason in 2.6: cosine values are not portable.

Usually not worth it — say so

It costs an embedding call per sentence at ingest, boundaries move when you change embedding model, and published comparisons rarely show it beating structure-aware splitting on documents that have structure. It earns its place on long unstructured narrative — transcripts, interview notes — where there are no headings to use.

5.3

Explain HNSW.

deep

A hierarchical navigable small-world graph. Vectors are nodes; edges connect near neighbours. Layers are built with exponentially decaying probability, so the top layer is sparse and long-range, the bottom contains everything. 

  layer 2   ●───────────────────●            sparse: big jumps
              \               /
  layer 1   ●───●─────────●───●──────●       medium hops
             \  |        /    |     /
  layer 0   ●──●──●──●──●──●──●──●──●        every vector, short edges

  search: enter at the top, greedily descend to the closest node,
          drop a layer, repeat. O(log N) hops instead of O(N).
ParameterControlsRaise it toCost
MEdges per nodeImprove recall, especially high-dimMemory, permanently
ef_constructionBuild-time candidate breadthBuild a better graphIndex build time
ef_searchQuery-time breadthImprove recall per queryLatency

ef_search is the only one you can change without rebuilding, which makes it your live recall/latency dial. Sensible defaults: M 16, ef_construction 64–200, ef_search ≥ top_k and tuned upward until recall plateaus.

Deletes are the weakness

HNSW has no true delete — implementations tombstone and the graph degrades as tombstones accumulate, because edges still point at removed nodes. High-churn corpora need periodic rebuilds. Ask about this in an interview and you sound like you have operated one.

5.5

How do you optimise an index once it is live?

deep

In the order that gives the most for the least:

  1. Measure recall against exact search first. Sample 200 queries, brute-force the true top-k, compare. Without this number you are tuning blind.
  2. Tune ef_search. Free, live, per-query. Usually where the answer is.
  3. Reduce dimensions. Linear savings in memory and compute — see 2.3.
  4. Quantise. float32 → int8 is 4× smaller for a few points of recall. Binary is 32× and needs a re-score pass.
  5. Rebuild if churn is high. Tombstones degrade the graph.
  6. Only then reshard. The expensive, structural option.
def measure_recall(queries, k=20):
    hits = 0
    for q in queries:
        exact = set(brute_force_topk(q, k))     # ground truth
        approx = set(index.search(q, k))
        hits += len(exact & approx)
    return hits / (len(queries) * k)            # e.g. 0.94 = losing 6%
The line that shows operational maturity

"ANN recall is a parameter, not a constant. Most teams never measure it, so they cannot tell an index regression from a model regression — and those need completely different fixes."

A bi-encoder must compress a document into a vector before it knows the question. That is the fundamental limitation, and it is why re-ranking helps so much: a cross-encoder can let the word "blank" in the query attend directly to "empty file" in the document.

One sentence

"A bi-encoder answers 'which of these million documents is roughly relevant'; a cross-encoder answers 'of these twenty, which is actually best'. You need both because neither can do the other's job at the other's scale."

The common misconfiguration

Retrieving 5 and re-ranking 5. That spends the re-ranker's entire value on reordering a set that has already lost the answer. Retrieve 50, re-rank 20, show 5.

6.5

Retrieval quality is poor. What do you try, in what order?

judgement test

Cheapest and highest-yield first. Most people start at the bottom of this list.

  1. Build an evaluation set. Fifty labelled queries. Without it every later step is guesswork.
  2. Check the obvious break. Is anything indexed? Is the query embedded the same way as the documents (2.5)? Is the tokenizer consistent (3.6)?
  3. Add the missing retriever. Dense-only on identifier queries, or sparse-only on paraphrases, is the single biggest structural gap.
  4. Fix chunking. Usually the largest single quality lever, and free to evaluate.
  5. Add re-ranking. Reliable +0.2–0.4 precision@5 for real latency.
  6. Query rewriting. Helps conversational and vague queries; costs a call.
  7. Swap the embedding model. Expensive — a full re-embed — and usually smaller than the above.
  8. Fine-tune embeddings. Last. Needs labelled data you probably do not have.
Why the order is the answer

"Almost everyone jumps to a better embedding model, which is the most expensive change with one of the smallest effects. The first four steps are cheap, and in my experience they account for most of the gap."

RAG evaluation metrics

3.14 covered the strategy. This section is the metric definitions — expect to be asked to define MRR or nDCG cold, and to say which one you would actually use.

7.1

Define precision, recall and hit rate for retrieval.

core
def precision_at_k(retrieved, relevant, k):
    top = retrieved[:k]
    return len([d for d in top if d in relevant]) / k

def recall_at_k(retrieved, relevant, k):
    top = retrieved[:k]
    return len([d for d in top if d in relevant]) / len(relevant)

def hit_rate_at_k(retrieved, relevant, k):
    return 1.0 if set(retrieved[:k]) & set(relevant) else 0.0
MetricAsksUse when
Precision@kOf what I showed, how much was right?The user reads everything shown
Recall@kOf what was right, how much did I show?Feeding an LLM — missing evidence is fatal
Hit rate@kWas anything right in the top k?One good document is enough to answer

Recall is usually the retrieval metric that matters in RAG, because a re-ranker and an LLM can both ignore a bad document but neither can invent a missing one.

7.2

Define MRR, MAP and nDCG. When is each right?

coredefinitions expected cold

MRR — reciprocal of the rank of the first correct result, averaged.

def mrr(results_per_query, relevant_per_query):
    total = 0.0
    for results, relevant in zip(results_per_query, relevant_per_query):
        for rank, doc in enumerate(results, start=1):
            if doc in relevant:
                total += 1 / rank        # rank 1 -> 1.0, rank 4 -> 0.25
                break
    return total / len(results_per_query)

Only the first hit counts. Right when one good answer ends the task — a lookup, a "did this happen before" check.

MAP — average precision at every relevant position, then averaged over queries. Rewards getting all the relevant items high.

def average_precision(results, relevant):
    hits, total = 0, 0.0
    for rank, doc in enumerate(results, start=1):
        if doc in relevant:
            hits += 1
            total += hits / rank         # precision at this position
    return total / len(relevant) if relevant else 0.0

nDCG — the only one that handles graded relevance rather than binary, with a logarithmic position discount.

import numpy as np

def ndcg_at_k(results, gains, k):        # gains: doc -> 0..3
    def dcg(order):
        return sum(gains.get(d, 0) / np.log2(i + 1) for i, d in enumerate(order, start=1))
    ideal = sorted(gains, key=gains.get, reverse=True)[:k]
    return dcg(results[:k]) / dcg(ideal) if dcg(ideal) else 0.0

MRRNoFirst hit onlyKnown-item search
MAPNoAll hitsMultiple relevant documents
nDCGYesAll, discounted"Very / somewhat / not" relevant
7.3

Which metric would you actually put in CI?

judgement

Recall@k for the gate, MRR alongside it for diagnosis. Recall answers "can the system possibly succeed"; MRR answers "is it putting the answer where a human will see it". They move independently and the pair localises a regression.

In this system — reported per query family

Retrieval is measured on two families separately, and running only one would have produced the wrong architecture: paraphrase queries make keyword search look like pure overhead, while identifier queries are what it exists for. The harness prints MRR, R@1/3/5/10/20 and nDCG per configuration, exits non-zero if the shipped combiner falls below a single retriever, and costs zero LLM calls.

The line worth having

"A single averaged number hides the case you care about. I report per query family, because the whole point of hybrid retrieval is that different families fail differently — and an average is exactly the shape that conceals that."

7.4

How do you measure faithfulness and detect hallucination?

deep

Three layers, cheapest first, and the cheap one catches the most damaging class.

1. Deterministic citation grounding. Extract every reference the model claimed; check each against what was actually retrieved. No model needed.

cited     = set(REFERENCE_PATTERN.findall(answer))    # \bOS-\d{1,6}\b
allowed   = references_seen_in_tool_results(state)
ungrounded = cited - allowed        # anything here was invented

2. Claim-level LLM judging — RAGAS faithfulness: decompose the answer into atomic claims, check each against the context, score = supported / total.

3. NLI entailment — a smaller, cheaper, more consistent alternative: does the context entail each claim?

In this system — the exact hallucination, caught twice

The local model answered a ticket count correctly, then decorated it with three invented references: OS-1042, OS-1043, OS-1044. RAGAS scored it faithfulness 0.20 with relevancy 0.88 — the dangerous combination.

The cause was precise: the aggregate tool returned counts with no references, and the model filled the absence. Making the tool declare "ticket_references": [] and stripping decorative fabrications took faithfulness from 0.73 to 0.92.

Two traps in LLM-as-judge

The judge is unstable. One identical sample scored three times at temperature 0: 0.25, 0.25, 1.00. Read judged metrics as a trend, never a per-row verdict.

Relevancy punishes honest refusals. RAGAS classifies noncommittal answers as irrelevant by design, so "the data does not answer that" scores 0.00. Optimising it rewards guessing — which is why faithfulness is the metric to gate on.

7.5

How do you build a golden set without a labelling team?

deep
  • Harvest from usage. Accepted suggestions, clicked results, resolved tickets linked as duplicates. Free, real, and it grows.
  • Mine existing structure. An FAQ is question–answer pairs. A ticket marked duplicate_of is a labelled pair someone already made.
  • Synthesise, then have a human filter. Generate questions from documents with an LLM; keep the ones a person confirms. Cheap, and the filtering step is what makes it honest.
  • Seed deliberately. Plant known relationships in a demo corpus.
In this system — including the mistake

16 clusters, 20 hand-written variants, each the same defect in a different customer's voice. Clusters deliberately stress different retrievers: payslip and leave clusters share almost no vocabulary (semantic should win); TDS and PF hinge on 80C and ECR (keyword should win).

The first version was worthless and looked perfect. Every configuration scored 1.000 on every metric — because the variants paraphrased only titles and reused the base description, so the task was exact-text matching. A benchmark everything passes has no power to distinguish anything.

A later audit found a second version of the same fault one level out: the surrounding corpus was drawn by weighted sampling, so 200 of 220 tickets sat in an exact-duplicate group. Rebuilding it kept the conclusions and collapsed the margins — the case for embeddings on paraphrase went from +0.158 to +0.014.

The strongest thing you can say about evaluation

"I audited my own benchmark and found it was flattering the results — twice. The conclusions survived; the margins did not. A saturated benchmark reads as success, which is what makes it dangerous."

7.6

How would you determine whether a RAG system is working?

the summary question

Two questions, and they need separate answers because they fail independently.

  "Is it retrieving the right information?"
      recall@k, MRR, nDCG on a golden set
      per query family, not averaged
      free -> gate every change on it

  "Is it generating a reliable answer from that information?"
      faithfulness   -- is every claim supported by the context?
      groundedness   -- does every citation resolve?
      relevancy      -- does it answer the question asked?
      costs LLM calls -> run occasionally

  AND, underneath both:
      acceptance rate -- did a human agree?
      the only number that is not a proxy

The separation is diagnostic. High retrieval + low faithfulness means the model is ignoring good context — a prompt or model problem. Low retrieval + high faithfulness means it is faithfully reporting that it found nothing — a retrieval problem. Fixing the wrong one is the most common wasted week in RAG work.

Close on this

"Every offline metric is a proxy. The number that is not a proxy is whether the people using it accepted the answer — which is why the accept and reject buttons exist partly as the evaluation dataset. The feature and its own labelled data are the same thing."

8.3

Single agent or multi-agent — how do you decide?

over-engineering trap

Default to one agent with more tools. Split only when there is a reason a single agent cannot satisfy.

Legitimate reasons to split:

  • Different permissions. A read-only research agent and an agent that can write are different trust boundaries — and that boundary is best enforced structurally.
  • Different models. A cheap classifier in front of an expensive reasoner.
  • Context pressure. Twenty tools is a large prompt and degrades selection accuracy; splitting keeps each prompt focused.
  • Genuine parallelism. Independent subtasks that can run at once.
  • Team ownership. Different teams shipping independently.
What multi-agent actually costs

Every hand-off is a lossy summarisation, latency accumulates serially, cost multiplies, and failures become non-local — agent C fails because agent A misphrased something two hops back. Debugging a multi-agent system is substantially harder than debugging one agent with ten tools.

The senior framing

"Multi-agent is a decomposition strategy, not an upgrade. I use it when a boundary already exists in the problem — usually permissions or ownership — not to make the architecture look sophisticated."

8.4

How does agent routing work?

core

Three mechanisms, and you should reach for them in this order:

  1. Rules. Deterministic, free, testable. A regex for an order number routes to order lookup. Use rules wherever the signal is unambiguous.
  2. Embedding similarity. Embed the query, compare to route exemplars. Cheap, no LLM, handles paraphrase.
  3. LLM classification. Most flexible, costs a call, and needs a fallback route for low confidence.
async def route(query: str) -> str:
    if ORDER_ID.search(query):                  # 1. deterministic
        return "orders"

    scores = {r: cosine(embed(query), exemplar) for r, exemplar in ROUTES.items()}
    best, score = max(scores.items(), key=lambda kv: kv[1])
    if score > 0.75:                            # 2. cheap semantic
        return best

    return await classify_with_llm(query)       # 3. expensive, last
Always have a default route

The failure people ship is a router with no fallback: an unroutable query either errors or gets silently forced into the nearest branch, which produces a confident answer from the wrong specialist. "I am not sure which of these you mean" is a valid route.

Section 9

LangGraph

Expect to be asked how state moves between nodes. The answer that scores explains reducers, because that is the part people skip.

9.1

Explain StateGraph, nodes and edges.

core

LangGraph models an agent as a state machine rather than a loop. A shared state object is threaded through nodes; edges decide what runs next. 

from langgraph.graph import StateGraph, START, END

graph = StateGraph(MyState)

graph.add_node("guard",    guard_input)      # (state) -> partial state
graph.add_node("retrieve", retrieve)
graph.add_node("answer",   answer)

graph.add_edge(START, "guard")
graph.add_conditional_edges("guard", route, {"retrieve": "retrieve", "end": END})
graph.add_edge("retrieve", "answer")
graph.add_edge("answer", END)

app = graph.compile()

A node is an ordinary function returning a partial state dict, which LangGraph merges. Nodes never mutate shared state — that is what makes them unit-testable with a plain dictionary and no framework.

In this codebase

Nodes are written as (state, deps) functions with no LangGraph import at all, and a single generic adapter converts them to the framework's (state, *, runtime) shape. So the retrieval logic can be tested with a dict and a fake, and the framework stays at the edge.

9.2

What is a reducer and why do you need one?

deepthe differentiator

A reducer defines how two writes to the same key combine. Without one, the default is overwrite — and when two nodes run in the same superstep, one silently wins. 

from typing import Annotated
import operator

class State(TypedDict):
    question: str                                    # overwrite (default)
    trace:    Annotated[list[str], operator.add]     # append
    rankings: Annotated[list[RankedList], merge_by_source]   # custom

The concurrency case is where it matters. Two retriever nodes in the same superstep both write rankings; with the default, you lose one retriever's results and the bug looks like "the lexical retriever is broken".

Custom reducers get interesting when you need semantics operator.add cannot express:

CLEAR = object()      # sentinel

def turn_scoped(existing: list, incoming: list) -> list:
    """Append -- unless the incoming batch begins with CLEAR, which resets."""
    if incoming and incoming[0] is CLEAR:
        return list(incoming[1:])
    return existing + incoming
In this codebase — why the sentinel exists

The chat assistant's working memory must reset each turn: observations from ten minutes ago are not evidence for the current question, and carrying them grows every prompt for the life of the thread. But operator.add cannot express "reset" — every write appends. Hence CLEAR plus turn_scoped. The transcript itself uses LangGraph's add_messages, which appends and merges updates by message id rather than duplicating.

9.3

How do conditional edges and cycles work, and how do you keep them safe?

core

A conditional edge is a pure function of state returning the name of the next node.

def route_after_grading(state) -> str:
    grade = state.get("grade")
    if grade == "weak":
        return "rewrite"        # -> cycles back
    if grade == "empty":
        return "finish"
    return "rerank"

graph.add_conditional_edges(
    "grade", route_after_grading,
    {"rewrite": "rewrite", "rerank": "hydrate", "finish": "finish"},
)
graph.add_edge("rewrite", "embed")     # THE CYCLE

Two properties make a cycle safe, and both are worth naming:

  • The counter lives in state, and the check is in a node — so termination does not depend on the model deciding to stop, which is the usual way an agent loop runs away.
  • Every path reaches a terminal node, so bookkeeping always runs, even on the paths that found nothing.
In this codebase — two independent limits

max_rewrites = 2 is the business rule. LangGraph's recursion_limit = 40 is the safety net for the business rule being wrong — counted in supersteps, set above the worst legitimate path so a genuine run never trips it while a topology bug still fails loudly.

A detail worth stating: the cycle returns to embed, not to guard. Re-guarding a model-generated rewrite would redact labels the model was already given, turning [EMAIL] into [[EMAIL]] on the second pass.

9.4

What happens at compile time, and how do you invoke a graph?

core

compile() validates the topology — unreachable nodes, edges to nothing, missing entry point — and builds an executor. It is worth doing once and caching, since nothing request-specific is baked in. 

@lru_cache(maxsize=1)
def similarity_graph():
    ...
    return graph.compile(name="similarity", checkpointer=False)

result = await similarity_graph().ainvoke(
    state,
    context=deps,                              # runtime dependencies, not state
    config={"recursion_limit": 40},
)

Note the separation: state is data flowing through the graph; context is injected dependencies — ports, limits, a model registry. Putting a database session in state would make it something reducers merge and checkpointers try to serialise.

A real bug: checkpointer inheritance

checkpointer=False is not the same as the default None. A graph invoked inside another graph's node inherits the parent's checkpointer. When a tool ran the retrieval graph from inside a chat graph that persists to Postgres, the parent's saver tried to serialise the child's state — which held dict[UUID, …] — and msgpack rejects non-string keys: 

TypeError: Dict key must a type serializable with OPT_NON_STR_KEYS

The tool caught it and the assistant said it could not search, so nothing crashed — the feature was simply unavailable, silently, while working perfectly elsewhere. False declines the inheritance explicitly.

9.5

What does a checkpointer do?

deep

Persists graph state per thread after every superstep. That buys three things: multi-turn memory without passing history, resume-after-crash, and human-in-the-loop pauses that survive a restart. 

graph = builder.compile(checkpointer=PostgresSaver(conn))

# Turn 1 -- only the new message is supplied; prior state is loaded by thread id
graph.invoke({"messages": [msg]}, config={"configurable": {"thread_id": conv_id}})

The design consequence is that nothing in the process has to still be alive — which is what makes a conversation survive a deploy.

In this codebase — three sharp edges
  • AsyncPostgresSaver cannot run on the Windows ProactorEventLoop, so the sync saver is wrapped with asyncio.to_thread.
  • That wrapper must subclass BaseCheckpointSaver, because LangGraph isinstance-checks the checkpointer rather than duck-typing it.
  • PostgresSaver needs row_factory=dict_row — caught by a type checker before it could lose a conversation.

It also writes to its own langgraph schema, excluded from migration autogeneration so a migration cannot drop the checkpoint tables.

9.6

Explain how information moves through an agent workflow.

explicitly asked

Four mechanisms, and naming all four is the complete answer.

  1. STATE          the shared dict every node reads and writes
                    node returns a PARTIAL dict; framework merges it

  2. REDUCERS       how two writes to one key combine
                    overwrite | append | merge-by-source | reset-on-sentinel

  3. EDGES          control flow -- who runs next
                    fixed edge | conditional edge | fan-out | fan-in

  4. CONTEXT        injected dependencies, NOT state
                    ports, registries, limits -- never merged, never persisted


  one superstep:
      ┌──────────────────────────────────────────────┐
      │ read state ──► node A ──► partial dict ──┐   │
      │ read state ──► node B ──► partial dict ──┼─► reduce ─► new state
      └──────────────────────────────────────────────┘
                 A and B run CONCURRENTLY;
                 the reducer is what makes that safe

Fan-out and fan-in need no barrier code: a node with two incoming edges waits for both branches automatically. That is one of the genuine advantages over a hand-written loop.

In this codebase, concretely

embed writes query_vector. Two retriever nodes in the same superstep each write a RankedList into rankings, merged by a source-keyed reducer. fuse has two incoming edges so it waits for both, then writes candidates. grade reads those and writes grade, which a conditional edge reads to choose between rewriting, re-ranking, or stopping. Every node also appends one line to trace, which is what makes the whole path visible afterwards.

9.7

How do you handle errors inside a graph?

deep

Decide per node whether a failure is fatal or degrading, and make degradation explicit rather than accidental.

async def retrieve_semantic(state, deps):
    vector = state.get("query_vector")
    if not vector:
        # Degrade, don't raise: the other retriever still works, and a
        # partial result beats no result on a page a human is reading.
        return {"rankings": [RankedList(source=SEMANTIC, ticket_ids=())],
                "trace": ["retrieve:semantic:no-vector"]}
    ...

Four rules that hold up in production:

  • Degrade where a partial answer is useful, and record that you degraded — the trace entry is what makes it discoverable later.
  • Route failures to the terminal node rather than throwing out of the graph, so bookkeeping still runs.
  • Retry only idempotent nodes, and only transient errors — never a validation failure.
  • Surface degradation to the caller. A response that silently came from half the pipeline is a lie of omission.
In this codebase

The API response carries a degraded flag, computed from the trace, so the UI can say "one search was unavailable" instead of quietly showing worse results. Re-ranking failure returns a trace entry rather than an exception, and the fused order stands — correct degradation, since the fused results are what shipped before re-ranking existed.

Explain ReAct.

core

Reason + Act, interleaved. The model thinks, acts, observes, and repeats — deciding each step from what it has just learned.

Strength: it adapts. Weakness: cost and latency are unknowable in advance, and errors compound — a bad observation on turn two poisons every later step.

A deterministic prime node runs before the model gets a turn, fetching the ticket by code so the first observation always exists. 10.4

When is planner–executor the right shape?

deep

Three conditions, and it is the right choice when all three hold:

  • The task decomposes into steps that are visible up front.
  • Steps can run in parallel, or their cost is worth pricing before committing.
  • A human should be able to approve the plan before anything executes.
class Plan(BaseModel):
    steps: list[Step]
    estimated_cost: float

plan = await model.generate_structured(PLANNER_PROMPT, ctx, Plan)

if plan.estimated_cost > BUDGET or plan.touches_writes:
    await request_human_approval(plan)      # reviewable ARTEFACT

for step in plan.steps:
    result = await execute(step)
    if result.failed and step.critical:
        plan = await replan(plan, failure=result)   # or escalate

The plan being a data structure is the real benefit: it can be logged, diffed, approved, costed and replayed. An interleaved agent offers no equivalent artefact — by the time you can review it, it has already acted.

The weakness is brittleness. A plan built on a wrong assumption fails wholesale, so any serious planner–executor needs a replanning path, which reintroduces some of the unpredictability you chose the pattern to avoid.

10.5

Reflection and Reflexion — do they work?

be sceptical

Reflection: generate, critique, revise. Reflexion: add memory of past failures so later attempts avoid them. 

answer = await generate(query, context)
for _ in range(MAX_REVISIONS):
    critique = await critic(query, context, answer)
    if critique.acceptable:
        break
    answer = await revise(answer, critique)

Be honest about when it helps, because interviewers have seen it oversold:

  • Works when the critique has an external signal — tests that run, a schema that validates, a citation that either resolves or does not.
  • Works poorly on pure self-critique with no ground truth. A model that could tell its answer was wrong would often have produced the right one; self-reflection can also talk a correct answer into a worse one.
In this codebase — reflection with an external signal

The corrective-RAG loop is reflection where the critique is not a model: grade inspects candidate counts and cross-retriever agreement, then routes to a rewrite. Deterministic, free, and explainable in a log line — asking a model "are these results good?" would cost a call to answer a question two counts already answer.

The output guardrail is the other instance: citations are checked against what was actually retrieved, which is an objective test rather than an opinion.

The line to use

"Reflection is worth it when the critic knows something the generator did not — a test result, a retrieval set, a schema. Self-critique without new information mostly costs 3× and buys variance."

11.2

How do you define and measure task success?

deep

Four sources, in descending order of trustworthiness:

  1. Deterministic checks. Did the ticket get closed? Did the invoice match? Best when the task has an observable outcome.
  2. Human verdicts. Accept / reject, thumbs, edit distance between proposal and what was actually sent.
  3. Downstream signals. Did the user rephrase immediately? Did they escalate anyway? A rephrase within thirty seconds is a strong implicit failure.
  4. LLM judging. Cheapest to add, least reliable — a judge scored one identical sample 0.25, 0.25, 1.00 at temperature 0.
In this codebase

Human verdicts, stored with the relation, confidence and model that produced them — which is what makes calibration answerable later ("are 0.9-confidence duplicates accepted more often than 0.6?"). Re-running the pipeline deletes only pending rows, so decided data survives a model change, and a pair a human already rejected is never re-suggested.

Two accounting bugs worth knowing

Pricing by role instead of by the model that answered. When a fallback dropped to a local model, the run was still billed at the hosted rate — inventing money. Cost per accepted suggestion is only meaningful if the costs in it are real.

Counting daily budgets per model instead of per role. Re-ranking and query-rewriting shared a model, so re-ranking silently exhausted rewriting's budget and rewrites stopped happening — with no error anywhere.

An agent produced a wrong answer. Walk me through debugging it.

the real test

  2. Did it call the right tools?
        no  ──► SELECTION   descriptions ambiguous, or never sent
        yes
  3. Were the arguments right?
        no  ──► SCHEMA      model and schema disagree; coerce or clarify

That answers "did both retrievers run", "how many survived de-duplication", "did the rewrite fire" and "was re-ranking skipped" without attaching a debugger.

12.2

How do authentication and authorization work in a RAG system?

security

The model is never an authorization boundary. If a document reaches the prompt, assume the user has seen it — prompt instructions not to reveal something are not access control.

So enforcement has to happen before retrieval returns:

  • Pre-filter by the caller's permissions at query time, using their identity, not the service's.
  • Index the ACL as metadata so it can be filtered on, and re-index when permissions change — a stale ACL in the index is a leak with a delay.
  • Partition hard boundaries (tenant) rather than filtering them.
In this codebase

Postgres enforces tenant isolation with row-level security and FORCE ROW LEVEL SECURITY across 13 tables, under a role that cannot bypass it — so a forgotten tenant clause is caught by the database rather than by review. The vector store has no equivalent, so isolation there is one namespace per tenant, derived from the authenticated tenant id and never from client input.

The agent's tools take the caller's session, so every tool inherits the same scoping automatically — the model cannot reach data the caller could not.

The subtle one

Caching across users. A cached answer keyed only on the question text will serve user B content retrieved under user A's permissions. Cache keys must include the permission scope, or the cache becomes a leak.

    COMPARISON = "comparison"    # several docs -> deeper retrieval
    CHITCHAT   = "chitchat"      # no retrieval at all

ANALYTICAL is the one people miss. "How many tickets are open per team" is not a retrieval question — no amount of semantic search answers it correctly. It needs an aggregate query. Routing it into RAG produces a confident wrong number built from whatever five documents came back.

In this codebase

13.2

How do you version a prompt?

deep

A hand-maintained VERSION = 3 is wrong the moment somebody edits the text and forgets to bump it — and that is exactly when it matters, because a result has just been attributed to a prompt that is no longer the one that produced it.

Derive the version from the content instead:

def prompt_version(text: str) -> str:
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:6]

PROMPT_VERSIONS = {
    "analysis": prompt_version(ANALYSIS_SYSTEM),   # 1470a7
    "chat":     prompt_version(CHAT_SYSTEM),       # e5ae3d
    "rerank":   prompt_version(RERANK_SYSTEM),     # 63d063
}

Edit a word and the version changes; change nothing and it does not. There is no bump to forget. The trade is that the version is not human-orderable — a3f19c does not announce itself as newer than 7b204e — which is fine, because the question being asked is never "which is newer" but "was this the same prompt". Chronology already lives in git.

Stamp that version onto every evaluation run and every logged call. Without it, a metric that moved between two runs has two candidate explanations and no way to separate them.

13.3

How do you test a prompt change before shipping it?

deep
  1. A fixed evaluation set — 30–100 representative inputs with expected properties, not exact strings.
  2. Assert properties, not text. Valid schema, citations resolve, refuses when it should, no forbidden claim.
  3. Run both versions on the same inputs and diff.
  4. Check the regressions, not the average. A change that improves the mean while breaking three previously-correct cases is usually a bad trade.
  5. Canary on a fraction of live traffic with the acceptance metric watched.
def test_refuses_when_no_evidence(prompt_version):
    answer = run(prompt_version, question="What is the CEO's salary?", context=[])
    assert not REFERENCE_PATTERN.findall(answer)      # invented nothing
    assert any(p in answer.lower() for p in ("cannot", "no data", "not available"))
Why exact-string assertions fail

Model output varies run to run even at temperature 0. Tests that compare strings become flaky, get muted, and then stop protecting anything. Assert the properties you actually care about.

How do you monitor retrieval quality in production, with no labels?

deepgood question

Proxy signals, watched as distributions rather than thresholds:

  • Zero-result rate — rising means the corpus, the query mix or the index changed.
  • Score distribution — a falling median top-1 similarity is drift, often the earliest signal you get.

  • Immediate rephrase — a strong implicit "that was not it".
  • A canary set — a few dozen fixed queries with known answers, run on a schedule against production.
The canary is the one to mention

"Proxy metrics tell you something changed; a canary set tells you what. Fifty queries with known answers, run hourly against production, is cheap and it converts 'quality feels worse' into 'recall on identifier queries dropped from 1.00 to 0.6 at 14:00', which is actionable."

Python & backend engineering

Expect a coding exercise as well as discussion. The AI-specific angle is async, and where it does and does not help.

16.1

Explain async/await, and where it helps in an AI backend.

core

One thread, cooperative scheduling. await yields control while waiting on I/O so other work runs. It buys concurrency, not parallelism — Python still executes one bytecode at a time.

AI backends are almost pure I/O wait: model calls take seconds, vector search hundreds of milliseconds. That is exactly the workload async is for. 

# Sequential: 3 x 200ms = 600ms
sem = await store.search(...)
lex = await lexical.search(...)

# Concurrent: max(200ms, 200ms) = 200ms
sem, lex = await asyncio.gather(store.search(...), lexical.search(...))
The mistake that undoes all of it

One blocking call in an async handler stalls the entire event loop — every concurrent request, not just that one. A synchronous SDK, a CPU-bound loop, or time.sleep will do it. Push those to a thread: 

# The Pinecone SDK is synchronous; a bare call would block every request
raw = await asyncio.to_thread(lambda: index.query(vector=v, top_k=k))
In this codebase

Both vector-store and checkpointer adapters wrap synchronous SDKs in asyncio.to_thread — deliberately one concurrency model in the codebase rather than two. The two retrievers run concurrently because LangGraph places them in the same superstep, which is the framework doing the gather for you.

How does FastAPI dependency injection work, and why use it?

core

Declare what a handler needs as a parameter; FastAPI resolves it, caches it per request, and handles teardown. The benefit is that cross-cutting concerns become impossible to forget rather than merely conventional.

    async with SessionFactory() as session:
        await apply_tenant_scope(session, ctx.tenant_id)   # SET LOCAL app.tenant_id
        try:

A route using ScopedDb cannot issue an unscoped query. The tenant scope is applied before the transaction opens, as a property of asking for a session at all. Permissions work the same way — declared in the type, so a new route cannot omit the check.

A trap specific to this pattern

SET LOCAL is transaction-scoped. Commit mid-request and the tenant scope silently vanishes — which showed up here as two unrelated-looking symptoms (tools reporting "not found", and inserts failing RLS) from one cause. The fix is a helper that re-applies scope after every commit.

How do you structure exception handling in an API?

core

Domain exceptions in the domain, translated to HTTP once at the boundary. Handlers should not build error responses. 

class AppError(Exception): ...
class NotFoundError(AppError): ...
class PermissionDeniedError(AppError): ...
class RateLimitError(AppError): ...
class ServiceUnavailableError(AppError): ...

@app.exception_handler(AppError)

    status = STATUS_BY_TYPE.get(type(exc), 500)
    return JSONResponse(status_code=status, content={
        "type": type(exc).__name__,
        "detail": str(exc),
        "request_id": request.state.request_id,     # correlates to the trace

Three rules that matter more than the structure:

  • Never leak internals. A stack trace or SQL fragment in a response is an information disclosure.
  • Distinguish retryable from terminal. 429 and 503 tell a client to back off; 400 tells it not to bother.
  • Include a request id so a user's complaint maps to a specific trace.
In this codebase — degrade, do not fail

AI failures are treated as degradation rather than errors. If the vector store is unreachable, the retriever returns an empty ranking, the keyword half still works, and the response carries a degraded flag so the UI can say so. A ticket page must render even when the AI layer is down — and the readiness probe deliberately does not mark the service unready for an AI dependency, because no AI call sits on a write path.

16.5

What coding problems should you expect?

practice

Medium difficulty, usually string, list or dictionary manipulation — often dressed in RAG clothing. Three that come up repeatedly:

Sliding window with overlap — chunking in disguise

def chunk(text: str, size: int, overlap: int) -> list[str]:
    if overlap >= size:
        raise ValueError("overlap must be smaller than size")
    step = size - overlap
    return [text[i:i + size] for i in range(0, len(text), step)]

Merge ranked lists — fusion in disguise

def rrf(lists: list[list[str]], k: int = 60) -> list[str]:
    scores: dict[str, float] = defaultdict(float)
    for ranked in lists:
        for rank, doc in enumerate(ranked, start=1):
            scores[doc] += 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

Top-k without sorting everything — O(n log k)

import heapq

def top_k(scores: dict[str, float], k: int) -> list[str]:
    return heapq.nlargest(k, scores, key=scores.get)
How to score well

State the complexity unprompted, name the edge cases before you are asked (overlap >= size, empty input, k larger than the collection), and say what you would do differently at scale. That reads as engineering rather than puzzle-solving.

Four decisions worth defending:

  • Multi-stage — the compiler is a build dependency, not a runtime one, and shipping it enlarges both the image and the attack surface.
  • Non-root — table stakes, and Kubernetes can enforce it.
  • Dependencies before source so the expensive layer caches across code changes.
  • Migrations are not in the entrypoint. Three replicas starting at once would run them three times concurrently. Migrations are a Job that completes before the rollout.
The AI-specific problem

ML dependencies are enormous — torch and CUDA alone can exceed 5 GB. If you serve models in-cluster, use a slim base with a CPU-only wheel index where you can, and keep model weights in a volume or object storage rather than baking them into the image, or every deploy pushes gigabytes.

17.3

What is specific about running AI workloads on Kubernetes?

conceptual
  • Separate deployments for API and workers. They scale on different signals — the API on request rate, the worker on queue depth — and a slow embedding job must never make the API unready.
  • Probes must account for warm-up. A model load can take tens of seconds; use a startupProbe so a slow start is not mistaken for a crash loop.
  • Readiness must not depend on optional dependencies. If the vector store being down marks pods unready, an AI outage becomes a total outage.
  • Long-lived requests need termination grace periods that let an in-flight agent run finish rather than being killed mid-write.
  • GPU scheduling, if you self-host models: node selectors, taints, and the reality that GPU nodes are expensive and should not sit idle.
startupProbe:                 # tolerate a slow model load
  httpGet: { path: /health/live, port: 8000 }
  failureThreshold: 30
  periodSeconds: 5

readinessProbe:               # database only -- NOT the AI dependencies
  httpGet: { path: /health/ready, port: 8000 }

terminationGracePeriodSeconds: 120   # let an in-flight run finish
One thing this codebase already gets right

Health reporting separates the AI dependencies from readiness deliberately — "neither Ollama nor the vector store being down should make the service unready, because no AI call sits on a write path." That is exactly the property the probe configuration above depends on.

The AI-specific stage is the retrieval eval, and its value is that it is free. Recall@k and MRR need no model calls, so they can gate every commit the way unit tests do. Generation metrics cost money and belong in staging, on a schedule, not on every push.

The line that shows you have thought about it

"The hard part isn't the pipeline, it's deciding what should fail a build in a non-deterministic system. My answer is: anything deterministic. Retrieval metrics, structural guardrail checks, schema validation — those are reproducible and can gate. Generation quality is a trend you watch in staging, not a gate, because a flaky gate gets disabled and then protects nothing."

Production software engineering

The section that is not about AI, and often where a senior hire is actually decided.

18.1

How do you go from a vague requirement to a technical design?

core

Take "we want AI to help with support tickets" — deliberately vague, like a real one.

  1. Find the actual pain. Not "add AI" but "agents re-investigate bugs that were already solved last month".
  2. Define success measurably. Reduce duplicate investigation. Measured as: suggestions accepted, and time-to-first-response on duplicates.
  3. Constrain the scope. On the ticket detail page, not the create form — at creation there is nothing to compare yet, and a panel reacting to every keystroke is expensive and distracting.
  4. Name what must not happen. No write access. Severity stays human-entered. The model is never an authorization boundary.
  5. Choose the simplest thing that could work, and write down what would make you revisit it.
The senior instinct

"Step 4 is the one people skip. Writing down the non-goals early is what stops scope creep later — 'the agent should just also close the ticket' is much easier to refuse when 'no write tools' was a documented decision rather than an opinion."

18.2

How do you document architectural decisions?

deep

Decision records, in the repository, versioned with the code. The format matters less than including the alternatives and what would reverse the decision. 

## D-14  Cascade fusion instead of Reciprocal Rank Fusion

Status      Accepted
Context     Two retrievers with incomparable score scales.
Decision    Ship a cascade: leader's order, other's finds appended.
Rejected    Equal-weight RRF -- measured BELOW its own best input on both
            query families (0.986 vs 1.000 R@5; 0.792 vs 1.000 R@20).
            The failure is structural: safety requires w <= 1/(K+2) = 0.016,
            at which point the secondary only orders the tail.
Revisit if  The exact-identifier probe is removed. Unaided, RRF beats the
            cascade on identifier queries -- the cascade only wins because
            that family is answered before ranking runs.

The "revisit if" line is the one that earns its place. It converts a decision from folklore into something a future engineer can re-open with confidence, and it is the difference between documentation and archaeology.

In this codebase

Decisions live in numbered docs alongside the code, and the reasoning is also in the module docstrings — the fusion module carries the derivation of the safe weight bound, so anyone tempted to "restore RRF" meets the arithmetic before they meet the code.

18.4

Monolith or microservices for a GenAI application?

judgement

A modular monolith, until a specific force makes you split. Distribution is a cost you pay for a benefit you should be able to name.

Legitimate forces to split:

  • Different scaling shapes — a GPU inference service and a CRUD API want different hardware and different replica counts.
  • Different release cadence, owned by different teams.
  • Isolation — a failure domain you want bounded.

The costs, which are usually understated:

  • Network calls where method calls used to be — latency, retries, partial failure.
  • Distributed transactions become sagas.
  • Debugging needs distributed tracing to reach parity with a stack trace.
In this codebase — modular, one deployable

Modules communicate through services and domain events, and dependencies point one way: intelligence knows about tickets, tickets knows nothing about intelligence. It emits an event; the AI layer subscribes at startup.

That direction is what would make extraction cheap if it were ever needed — the seam already exists, and it is enforced rather than intended. The worker is already a separate process for exactly the "different scaling shape" reason.
