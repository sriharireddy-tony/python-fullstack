Orientation

What this system actually is

Keka's support team raises bugs that HRMS customers report. Six engineering teams — Platform, CoreHR, Payroll, UI, Performance, Workforce — resolve them. The AI layer exists to answer three questions a human would otherwise answer by memory.

Has this been reported before?

The similar issues panel on a ticket. Hybrid retrieval plus an optional model judgement. This is the RAG core.

What is this bug, and what next?

The analysis agent. An unattended ReAct loop that gathers evidence with read-only tools and writes a triage report.

Anything I can ask in words

The chat assistant. Multi-turn, tool-using, conversation persisted in Postgres, retained 30 days.

The one sentence that explains the architecture

Postgres is the truth. Everything else is a derived index you can throw away. That has been proven, not asserted — the entire vector store was deleted and rebuilt from Postgres in 11.8 seconds during development.

Every design decision downstream follows from it. The vector database holds ids, vectors and filter metadata, and no ticket text. Sensitive content lives in exactly one place, so there is one store to secure, back up, and satisfy a deletion request against.

The colour code on this page

semantic marks the meaning-based retriever, lexical the literal-token one, llm call any stage that costs money, and free any stage that does not. Most of the pipeline is free, and that is deliberate.

Foundations

Where a ticket lives, and who can see it

A ticket is a row in the tickets table in PostgreSQL 18. Not a document, not a file — a row with typed columns, a foreign key to a tenant, and a soft-delete timestamp. That single fact removes an entire category of RAG problem: no parsers, no OCR, no encoding guesses, no loader picking up a temp file.

Tenant isolation is enforced by the database

Thirteen tenant-scoped tables run row-level security with FORCE ROW LEVEL SECURITY. Two database roles exist: os_migrate owns the schema and has BYPASSRLS; os_app owns nothing and cannot bypass. The application connects as os_app.

Every request opens a session, sets app.tenant_id, and the database filters every query from then on. A developer who forgets a WHERE tenant_id = ? is caught by Postgres, not by code review.

The trap this created

set_config(..., is_local => true) is transaction-scoped. Commit mid-run and the tenant scope silently vanishes. The analysis agent commits as it goes, so two unrelated-looking symptoms appeared at once: tools reported "ticket not found", and step inserts violated RLS. One cause. The fix is a helper, commit_preserving_scope(), that re-applies the scope after every commit.

01

Emit, don't call

core/events.py · subscribers.pyfree

The tickets module does not know the AI layer exists. It emits a domain event; intelligence subscribed at startup. The handler receives the emitter's own session, so the outbox row commits or rolls back with the ticket itself.

Handler exceptions are logged and swallowed. A misconfigured AI layer must never block ticket creation — reconciliation picks up what was missed.

02

Claim work safely

jobs/worker.py · repository.pyfree

SELECT ... FOR UPDATE SKIP LOCKED lets N workers run with no broker — contending workers step over locked rows instead of blocking. The claim commits before slow work starts, so holding it never blocks anyone else.

03

Ingest

ingestion/ticket_source.pyfree

Load the ticket (always excluding soft-deleted rows — one definition, so no caller can forget it) and build the metadata stored beside the vector: ticket_number, team_id, client_id, status, priority, created_at, source_hash.

Metadata is chosen for filtering, not display. Adding a field later only affects tickets embedded afterwards, so the list is chosen for what a search might one day need.

04

Chunk — by deciding not to

chunking/policy.pyfree

Chunking exists to fit long documents into a context window and to give retrieval a unit smaller than the whole document. Neither applies: a ticket is ~1–2 KB and is already the unit a human wants back. Returning "paragraph three of OS-1042" would help nobody.

What survives is bounding. Title 300 chars, description 2000, steps 1000 — title first, so if truncation happens the title is what survives.

Deliberately excluded: comments (they change constantly, so the vector never settles), resolution notes (written after the bug is understood — including them leaks the outcome into a triage-time signal and inflates offline scores), and client name (would cluster tickets by customer instead of by problem).

05

Hash, and usually stop

embeddings/service.pyfree

sha256(model | instruction_version | normalised_text). If the stored hash matches, the job ends here having cost one indexed query.

Folding the model name into the hash is the important part: changing the embedding model invalidates every stored vector automatically. That is what made the 4096→1024 migration a one-line config change rather than a data migration.

06

Embed

embeddings/embedder.pysemantic

qwen3-embedding:0.6b via local Ollama, 1024 dimensions. The dimension is probed from the model at startup, never configured — a hardcoded wrong value means rebuilding the index, so the model is the authority.

Qwen3-Embedding is asymmetric: queries take a task-instruction prefix, documents do not. The port exposes embed_query and embed_documents as separate methods precisely so this cannot be got wrong silently — using the wrong one produces no error, just measurably worse recall.

07

Store

vectordb/pinecone_store.pyfree

Pinecone serverless, one index, one namespace per tenant. A query names exactly one namespace and cannot read across them — there is no filter to forget. The namespace name derives from the authenticated tenant id and never accepts client input.

Why 1024 and not 4096

The build started on the 8B Qwen3 model at 4096 dimensions. That was never a decision — it was the default the model emitted. At a million tickets it is the difference between 16 GB of vectors and 4 GB, plus four times the index memory and four times the distance computation per comparison.

Route to 1024Trade
0.6B tag — chosenNative 1024. Smaller and faster on the write path. Lower benchmark scores than 8B
Truncate 8B (Matryoshka)Keeps the stronger model, but pays full 8B inference then discards three quarters of the output

The 0.6B won on a design argument as much as a performance one: the dimension is probed, so a native model kept that intact as one config line. Truncation would have added a slice-and-renormalise step plus a dimension setting — reintroducing exactly the hardcoded value the probe exists to eliminate.

Two stores means drift, so drift is measured

Writing Postgres and Pinecone is a dual write. The outbox makes it recoverable rather than atomic; ai_backfill --reconcile makes it visible. It diffs both directions and reports missing vectors, orphaned vectors, unrecorded in pg, lost from store.

The honest cost of choosing a separate vector database

pgvector would delete this entire problem — vectors inside the database that already enforces RLS, one store, transactional consistency. It is the better engineering choice. A managed vector store was chosen deliberately for the learning goal, and the cost is written down rather than hidden: a dual write, an outbox, and a reconciliation job.

What each node does

01

guard

retrieval/hydrate.py · security/input.pyfree

Bound to 8000 characters, redact anything resembling PII or a credential, screen for injection markers. It is the first node in the graph, so no later node has to wonder whether its text has been through this.

That is the argument for a guardrail as a node rather than a helper: the topology makes it unskippable. If it blocks, a conditional edge jumps straight to finish — control flow lives in edges, which is what keeps the execution trace honest about which nodes actually ran.

02

references & identifiers

retrieval/exact.py · query/parsing.pyfree

OS-1042 and ERR-40001 are facts, not hints. They are looked up with AND semantics and pinned above the ranking.

Pinned only when the lookup matches exactly one ticket. An earlier version pinned anything matching up to three, and a shared /api/v3/... path cost a duplicate query its rank-1 result.

Sequential, not parallel — both write pinned, and the second must see what the first added.

03

embed

embeddings/embed_node.pysemantic

Embeds the query text live. This is the subtlety worth knowing: the read path never looks up the ticket's stored vector. A ticket created one second ago, not yet embedded, still gets working similar-issue results — because the ticket you are looking at is the query, and the stored vectors are the corpus.

04

retrieve, twice, concurrently

retrieval/retrieve.pysemanticlexical

Two nodes in the same LangGraph superstep, so they run concurrently and their writes merge through a reducer keyed by source. Two nodes rather than one because they fail independently and the ablation script disables one without touching the other.

If the query vector is missing, semantic returns an empty ranking rather than raising — a degraded result beats no result on a page a human is already reading.

05

fuse

retrieval/fuse.py · retrieval/fusion.pyfree

A cascade: the leading retriever's order, with the other's finds appended below. See the next section for why this beat Reciprocal Rank Fusion.

The score floor is applied after fusion, not per retriever. A document ranked 40th by both is a better candidate than one ranked 8th by one, and a per-retriever cutoff would discard it before fusion ever saw the agreement.

06

grade — the node that makes this corrective

retrieval/grade.pyfree

No LLM here, deliberately. Asking a model "are these results good?" costs a call and a second of latency to answer a question two counts already answer: how many candidates cleared the floor, and whether the retrievers agreed.

ConditionGradeRoute
A pinned exact match existsgoodrerank — already certain
≥3 candidatesgoodrerank
Too few, rewrites remainingweakrewrite → back to embed
Too few, rewrites exhaustedemptyfinish — "no similar issues" is a real answer
07

hydrate → rerank

retrieval/hydrate.py · rerank/reranker.pyllm call

Hydrate loads candidate text from Postgres — never from vector-store metadata. Rerank then classifies each candidate as duplicate / recurring / related / unrelated, with a confidence, and drops anything at or below 0.55.

The duplicate vs recurring distinction is the one that matters commercially: one means "someone is already working on this", the other means "this was fixed and has come back". They route to entirely different responses.

Optional. With reranking off, the graph returns the fused order unchanged — correct degradation, not failure.

The cycle, and why it cannot run away

rewrite routes back to embed, not to guard. Re-guarding a model-generated rewrite would redact labels the model was already given, turning [EMAIL] into [[EMAIL]] on the second pass.

Two independent limits guard the same loop:

  • max_rewrites = 2 — the business rule, checked in grade, held in state. Termination never depends on a model deciding to stop.
  • recursion_limit = 40 — LangGraph's own backstop, counted in supersteps. The safety net for the business rule being wrong.
Cost is in the topology, not a footnote

Blocked input: 0 LLM calls. Good retrieval, rerank off: 0. Good retrieval, rerank on: 1. Worst case with rewrites: 3. On a 500-request daily free quota those numbers are the design.

The core

Retrieval, in depth

This is the part of the system with real measurements behind it, and the part most worth being able to defend.

Two retrievers that are good at different things

semantic Vector search

Cosine similarity in Pinecone. Finds paraphrases: "salary slip shows no data for contract staff" against "Payslip PDF generates blank for contractors" shares almost no words.

Weak at literal tokens — an embedding flattens 80C and ECR into "something about tax".

lexical Postgres full-text

ts_rank_cd over a GIN-indexed generated column. Catches exactly what embeddings are worst at: error codes, stack-trace fragments, rare product names.

Free — the column and index already existed for the ticket list's search box.

The most important five lines in the module

app/modules/intelligence/lexical/postgres_fts.py 
(
    SELECT string_agg(quote_literal(lexeme), ' | ')
    FROM unnest(tsvector_to_array(to_tsvector('english', :query_text))) AS lexeme
)::tsquery

Two properties, both load-bearing:

  • One tokenizer. The lexemes come from the same analyzer that built search_vector, so query and index cannot disagree about what a token is.
  • OR, not AND. plainto_tsquery joins terms with &, which is right for a search box and wrong here — the query is a whole bug description, so requiring every term matches nothing. Rank by how much overlaps rather than filtering on total overlap.
The bug that made keyword search look useless

Postgres tokenizes ERR-40001 as 'err' + '-40001' — the hyphen stays with the number. The Python-side query builder stripped hyphens and searched for 40001, which appears in no document. Every error-code lookup had been silently returning nothing. It read as "keyword search is just weak at identifiers"; it was returning zero rows.

Fixed by building the tsquery in SQL, so query and index are analysed by the same analyzer and cannot disagree. Recall@5 on identifier queries went from 0.083 to 0.625; recall@20 from 0.583 to 1.000.

Why the fusion is a cascade and not RRF

Reciprocal Rank Fusion is the textbook answer. It was implemented, measured, and lost to its own inputs on both query families.

100-ticket corpus, no verbatim duplicates. 36 paraphrase queries, 24 identifier queries. All configurations unaided (exact probe off).
Configurationdup R@5dup R@20ident R@20
semantic alone1.0001.0000.583
lexical alone0.9310.9861.000
RRF, equal weight0.9861.0000.792
cascade (shipped)1.0001.0000.583 → 1.000 with probe

RRF's whole value is its agreement bonus — a document both retrievers ranked reasonably beats one a single retriever loved. That bonus is also its failure mode when the retrievers are of unequal quality for the query at hand, and on this corpus they always are, in whichever direction the query points: 

1/(60+35) + 1/(60+2)  =  0.0266   >   1/(60+1)  =  0.0164
        weak retriever's rank 2          strong retriever's rank 1

And weighting the secondary down does not fix it — that is provable. Require that an agreement bonus can never lift a document above the leader's own top hit:

1/(K + 2) + w/(K + 1)  ≤  1/(K + 1)
                    w  ≤  1/(K + 2)  =  0.016   at K = 60

At any weight small enough to be safe, the secondary retriever contributes nothing but the ordering of documents below the leader's list. "Keep the agreement bonus" and "never rank worse than the better retriever" are not simultaneously satisfiable. The choice has to be made, not tuned around.

What ships instead

The leader's order, with the other's finds appended below it. Guarantees, at any cutoff up to the leader's depth:

  • the first n results are exactly the leader's first n — never worse than the leader alone;
  • documents only the secondary found are still present further down;
  • agreed is still populated, so the reranker and the UI keep the cross-retriever agreement signal even though ordering no longer uses it.
A dependency worth naming

The cascade is the right fusion given the probe, not on its own merits. Unaided on identifier queries the cascade scores 0.583 and RRF scores 0.792 — RRF's agreement bonus pulls keyword hits into the top 20 while the cascade appends them below the depth cutoff. RRF is genuinely the better fusion for that family.

It loses anyway, because the exact probe answers identifier queries deterministically before ranking runs, and paying RRF's head-precision cost on every paraphrase query to buy a rescue that never fires is a bad trade. Remove the probe and the decision must be re-made — which is why rrf, no probe is a permanent row in the ablation.

The score shown to a human is not the score used for ranking

Fusion ranks by position, so every fused score lands near 0.0164 regardless of how alike two tickets are. Displaying that as a "match score" would look like a measurement and mean nothing. So the raw cosine similarity is carried alongside, display-only, and RankedList still discards scores for ranking purposes.

The actual embedding call

async def _embed(self, inputs: list[str]) -> list[list[float]]:
    async with httpx.AsyncClient(timeout=httpx.Timeout(300.0)) as client:
        response = await client.post(
            f"{self._base_url}/api/embed",             # localhost:11434
            json={"model": self._model, "input": inputs},
        )
        response.raise_for_status()
        payload = response.json()

    vectors = payload.get("embeddings")
    if not vectors or len(vectors) != len(inputs):
        raise RuntimeError(f"Ollama returned {len(vectors or [])} for {len(inputs)}")
    return [[float(v) for v in vector] for vector in vectors]

Scores are deliberately thrown away

def rank_only(hits, source) -> RankedList:
    """Turn scored hits into a ranked list, dropping the scores.

    Dropped *here*, at the boundary, rather than carried along and
    ignored later. If they were still in scope downstream, someone
    would eventually blend them.
    """
    seen, ordered = set(), []
    for ticket_id, _score in sorted(hits, key=lambda pair: -pair[1]):
        if ticket_id not in seen:
            seen.add(ticket_id)
            ordered.append(ticket_id)
    return RankedList(source=source, ticket_ids=tuple(ordered))

Count the AI in journey two

One embedding call at step 02. That is all — with reranking off, no chat model is involved anywhere. Steps 03–07 are cosine arithmetic, a Postgres index scan, list manipulation, and a WHERE id IN (…).

Agent one of two

The analysis agent

An unattended ReAct loop. Reads one ticket, gathers evidence with read-only tools, and writes a triage report. Runs in the worker, not in a request — minutes rather than milliseconds, several LLM calls, and it commits as it goes.

ReAct via structured output, not native tool calling

Each turn the model returns an AgentDecision: either a tool to call with arguments, or a decision to finish. This is deliberately not provider-native tool calling — one port then serves both Gemini and Ollama identically, which is the only reason the fallback chain works at all.

The agent wrote a report from zero evidence

Given an empty observation list, the model produced a fluent, confident, entirely invented report. The failure mode was not being wrong — it was being wrong from nothing.

Fixed with a deterministic prime node: the agent's first observation is the ticket itself, fetched by code before the model gets a turn. It can no longer start from nothing.

The structured related_references field was empty while the prose cheerfully cited OS-193 and OS-201. Validation checked the field, so the invented citations in the sentence a human actually reads went straight through.

Agent two of two

The chat assistant

Same tool registry, same read-only constraint, different shape: multi-turn, and the conversation has to survive a restart.

Persistence, and a Windows problem

LangGraph's AsyncPostgresSaver cannot run on the Windows ProactorEventLoop. The solution is ThreadedPostgresSaver — an async wrapper over the sync PostgresSaver using asyncio.to_thread. It has to subclass BaseCheckpointSaver because LangGraph isinstance-checks the checkpointer rather than duck-typing it.

Two more sharp edges: PostgresSaver needs row_factory=dict_row (caught by mypy before it could lose a conversation), and os_app cannot CREATE SCHEMA, so a bootstrap script runs setup() as the migration role and grants DML.

Turn-scoped state

Observations from ten minutes ago are not evidence for the current question, and carrying them would grow the prompt without bound. But operator.add cannot express "reset" — so a CLEAR sentinel plus a custom turn_scoped reducer does.

The transcript itself uses add_messages, which appends and merges updates by message id rather than duplicating.

The local model invented three ticket numbers

Chat had no citation grounding. Running on the local fallback, it cited OS-1042, OS-1043 and OS-1044 — none of which existed.

Now every claimed reference is validated against this turn's observations plus references already in the transcript — the second half matters, because "what was that ticket number again?" legitimately cites something retrieved three turns ago. Ungrounded citations are marked [unverified: OS-XXXX] and a caveat line is appended.

Three rules that must not erode

  • The model is never an authorization boundary. RLS and permissions decide; the model only ever sees what the caller could already read.
  • The agent has no write tools. Not disabled — absent.
  • Severity and impact stay human-entered. A model could be talked into P1 by the bug reporter.
Two guardrail bugs worth remembering

A silently discarded filter. An injection-shaped status value was safely coerced away — and the query silently widened from "closed" to the entire corpus, with nothing telling the model, which then reasoned confidently about "the closed tickets". Tool results now carry ignored_filters and a warning.

A credential redaction gap. The pattern matched "token: Bearer" and left sk-live-… in the text. Fixed with a scheme-aware pattern plus unlabelled secret-shape patterns.

Rigour

Evaluation, and why most of it is free

Seven full ablations, four re-seeds, three re-embeds of the entire corpus, and one architecture reversal — at a total cost of zero LLM calls.

That zero is the point. Anything needing an LLM judge at $0.002 a call gets run once, believed, and shipped wrong.

Three tiers

TierMeasuresCostRuns
Retrieval metricsrecall@k, MRR, nDCG per query familyfreeevery change

Two query families, because one would have given the wrong answer

Running only paraphrase queries measures what embeddings are best at — keyword search looks like pure overhead, and deleting it would have been justified by a benchmark that never tested what it is for. The second family is an error code pasted from a log.

The harness prints its own verdict: KEEP BOTH — because unaided, no single retriever wins everywhere, and the shipped fusion matches the winner on every family.

The benchmark itself was lying — twice

Run 1: every configuration scored 1.000 on every metric. That reads as success and means the benchmark has no power to distinguish anything. Cause: the golden set paraphrased ticket titles and reused the base description, so the task was exact-text matching.

Run 7: the corpus itself was flattering the results. 220 tickets drawn by weighted sampling from 64 scenarios meant 200 of them sat in an exact-duplicate group — nine tickets sharing a title word for word. Rebuilt as 80 distinct bugs plus 20 hand-written variants. The conclusions held; the margins did not. The case for embeddings on paraphrases shrank from +0.158 to +0.014 — one query.

Six of seven runs were misleading in some way, and none of them looked misleading. The metric was never what was wrong — the setup was.

Preparation

Questions you should expect

Walk me through what happens when a ticket is created.

Row inserted in Postgres; in the same transaction a domain event fires and the intelligence module writes one outbox row. Both commit or neither does. The response returns immediately — no model is called on the write path. A separate worker claims the job with FOR UPDATE SKIP LOCKED, loads the ticket, assembles bounded text, hashes it, and skips if the hash is unchanged. Otherwise it embeds to 1024 dimensions locally and upserts into the tenant's Pinecone namespace, then records the state row for reconciliation.

Why hybrid retrieval? Isn't a good embedding model enough?

I measured it. On paraphrase queries semantic wins at recall@20, 1.000 against 0.986. On error-code queries keyword search wins, 1.000 against 0.583. Neither can be dropped because which one is better keeps changing with the query. I'd add that the honest version of this argument rests almost entirely on the identifier family — the paraphrase margin is a single query.

You used RRF, right? Everyone does.

I implemented it and it lost to its own inputs on both query families. The reason is structural: at K=60 an agreement bonus large enough to matter is large enough to displace the leader's top hit. Requiring that it never does gives w ≤ 1/(K+2) ≈ 0.016, at which point the secondary only orders the tail — which is a cascade. So I shipped the cascade and kept RRF as a permanent ablation row.

How do you know your retrieval is actually good?

I mostly know that it is comparatively better, and I'd be careful to say so. The labels are planted by the seed and written by the same author as the system, and the eval script prints that caveat itself. What the harness genuinely gives me is the ability to tell whether a change helped, on two query families, for free. In production I'd replace synthetic labels with acceptance data — the panel already records whether a human agreed with each suggestion.

What stops prompt injection?

Three things, and the prompt is the weakest. The input guardrail bounds and redacts before anything is sent. The tool layer has no write verb at all, so a successful injection still cannot change data. The output guardrail validates every citation against what was actually retrieved. The prompt's injection notice raises the cost of an attack; the architecture is what makes a successful one survivable.

Why LangGraph rather than a for-loop?

For the similarity pipeline, the cycle: grade routes to rewrite, which routes back to embed. A conditional edge is how you express that without control flow leaking into the nodes. And the topology is what makes the guard unskippable — it is the first node, so no later node has to check. For the chat assistant, the checkpointer: a conversation survives a restart because state is persisted per thread, not held in memory.

Why a separate vector database when you already run Postgres?

Honestly, pgvector would have been the better engineering choice — one store, transactional consistency, and RLS already enforced. I chose a managed vector store deliberately for the learning goal, and the cost is written down rather than hidden: a dual write, an outbox, and a reconciliation job. I'd also point out the port made it swappable — moving from Chroma to Pinecone took one new file and four config lines.

What would break first at 100× the data?

Three things. Retrieval depth — 20 candidates over 100 tickets is generous, over 100,000 it is thin, and HNSW recall stops being free. The reranker — 10 candidates per query at one LLM call each does not scale to a busy queue, so it would need to become selective rather than default-on. And the evaluation — a golden set of 20 pairs is adequate here and meaningless at a million, which is the strongest argument for self-labelling from acceptance data.

What's the weakest part of this system?

No unit tests. There are verification scripts — 71 end-to-end checks, 28 red-team checks, a console suite — but they need a live database, Ollama, and Pinecone, so nothing runs on every change in CI. That is the gap I would close first. The synthetic corpus is second: 100 tickets is small, and the labels and the system share an author.

Built from the code as it stands: 12,621 lines across 21 packages, mypy strict clean, 13 tenant-scoped tables with row-level security enforced, 71 end-to-end checks and 28 structural red-team checks passing.
