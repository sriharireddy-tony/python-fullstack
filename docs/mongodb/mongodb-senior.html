1. Indexing and query performance

1.1 ESR: the one rule you must recite

Compound index field order is Equality, then Sort, then Range. Get this wrong and Mongo does an in-memory sort or scans far more keys than it returns.

// Query: orders for one customer, a few statuses, newest 20
db.orders.find({
  tenantId: "acme",                               // E
  customerId: ObjectId("..."),                    // E
  status: { $in: ["paid","packed","shipped"] }    // E (multi-point)
}).sort({ createdAt: -1 }).limit(20)              // S

db.orders.createIndex(
  { tenantId: 1, customerId: 1, status: 1, createdAt: -1 },
  { name: "ix_orders_customer_status_date" }
)

Now add a range. The query also filters the last 30 days. The index does not change, because createdAt serves as both sort and range and it is already last:

db.orders.find({
  tenantId: "acme", customerId: ObjectId("..."),
  status: { $in: ["paid","packed","shipped"] },
  createdAt: { $gte: ISODate("2026-08-13") }      // R, same field as sort
}).sort({ createdAt: -1 }).limit(20)
// same index works. IXSCAN with tight bounds, no SORT stage.

When the range is a different field, ESR bites. Filter on total > 5000 and sort by createdAt:

// WRONG - range before sort forces an in-memory SORT stage
{ tenantId: 1, customerId: 1, total: 1, createdAt: -1 }

// RIGHT - sort field before the range field
{ tenantId: 1, customerId: 1, createdAt: -1, total: 1 }
// total is not a tight bound here; it filters on the index (no FETCH)
// but Mongo scans more keys. That is the accepted trade for a sorted result.
Sort direction detail An index supports a sort and its exact inverse. {a:1,b:-1} serves sort({a:1,b:-1}) and sort({a:-1,b:1}), but not sort({a:1,b:1}). Single-field indexes are always reversible.

1.2 Reading explain like an SRE

db.orders.find({ tenantId:"acme", status:"paid" })
  .sort({ createdAt:-1 }).limit(20)
  .explain("executionStats")

Only four numbers matter. Read them in this order:

FieldWhat it meansHealthy
nReturnedDocs the client gotyour page size
totalKeysExaminedIndex entries walkedclose to nReturned
totalDocsExaminedFull docs fetched from disk= nReturned, or 0 if covered
executionTimeMillisWall clock on the serversingle-digit ms for OLTP

Stage names decode the plan instantly:

  • COLLSCAN fail no usable index.
  • IXSCAN then FETCH normal index found the keys, then read the docs.
  • PROJECTION_COVERED best answered from the index alone, zero doc reads.
  • SORT with SORT_KEY_GENERATOR smell in-memory sort, dies at 100 MB unless it spills.
  • rejectedPlans non-empty means the planner had a choice. Check the winner is what you expected.

Covered query

db.orders.createIndex({ tenantId:1, customerId:1, createdAt:-1, status:1, total:1 })

db.orders.find(
  { tenantId:"acme", customerId: ObjectId("...") },
  { _id: 0, createdAt: 1, status: 1, total: 1 }   // _id MUST be excluded
).sort({ createdAt:-1 })
// totalDocsExamined: 0  -- the index IS the answer
Covered queries break silently A covered query stops being covered the moment someone adds a field to the projection, or the field is an array (multikey indexes can never cover), or you query on a sharded collection without the shard key in the index. Assert on it in a perf test, never assume it.

1.3 The specialist index types, and exactly when

// PARTIAL - index only the rows you query. Smaller, cheaper writes.
db.orders.createIndex(
  { tenantId:1, createdAt:-1 },
  { partialFilterExpression: { status: { $in: ["pending","paid"] } } }
)
// Caveat: the query must be provably a subset of the filter, else it is ignored.
// find({status:"paid"})              -> uses it
// find({status:{$ne:"shipped"}})     -> does NOT use it

// TTL - auto-delete. Single date field only, background sweep every 60s.
db.sessions.createIndex({ lastSeenAt: 1 }, { expireAfterSeconds: 1800 })
// Per-document TTL: set expireAfterSeconds:0 and store the exact expiry date
db.otps.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 })

// UNIQUE + PARTIAL - unique email per tenant, ignoring soft-deleted rows
db.customers.createIndex(
  { tenantId:1, email:1 },
  { unique:true, partialFilterExpression: { deletedAt: { $exists:false } } }
)

// WILDCARD - unknown/user-defined attribute keys
db.products.createIndex({ "attrs.$**": 1 })
// Good for ad-hoc filters on attrs.color, attrs.fabric...
// Cannot be compound with a normal field, cannot cover, cannot support sort well.
// If you know the top 3 attrs, index them explicitly instead.

// TEXT vs ATLAS SEARCH
db.products.createIndex({ title:"text", "categories":"text" })
// One text index per collection, no fuzzy, no relevance tuning, no autocomplete.
// Senior answer: text index for a checkbox feature; Atlas Search (Lucene) for
// anything user-facing - fuzzy, synonyms, faceting, autocomplete, highlighting.

// COLLATION - case-insensitive search that still uses an index
db.customers.createIndex({ tenantId:1, name:1 }, { collation:{ locale:"en", strength:2 } })
db.customers.find({ tenantId:"acme", name:"ana" }).collation({ locale:"en", strength:2 })
// Beats a $regex with /i, which cannot use an index unless anchored ^

// 2DSPHERE - nearest store
db.stores.createIndex({ loc: "2dsphere" })
db.stores.find({ loc: { $near: { $geometry:{ type:"Point", coordinates:[73.85,18.52] },
                                 $maxDistance: 5000 } } })

1.4 The cost side nobody mentions

  • Every index is written on every insert and on every update that touches its fields. Ten indexes means roughly ten times the index write work.
  • Indexes must fit in RAM to be fast. db.orders.stats().indexSizes against your instance memory is the real capacity question.
  • MongoDB uses one index per query in almost all cases. Index intersection exists but the planner rarely picks it. Build the compound index instead of hoping for intersection.
  • Build indexes on a live system with a rolling build across replica set members, or in Atlas use a rolling index build. Never a foreground build on a primary.
  • Find dead weight: db.orders.aggregate([{ $indexStats: {} }]) and drop anything with accesses.ops near zero.
Interview question "You added an index and the query got slower. Explain."
Mid-levelThat should not happen, maybe the cache was cold.
SeniorThree real causes. One, the planner cached a worse plan. Plans are cached per query shape and re-evaluated only after ~1000 works or a write threshold. Two, the new index has better estimated cardinality but worse real selectivity, so it scans more keys and then fetches. Three, the write amplification from the extra index slowed the whole workload. I would confirm with explain on both plans, then hint() to force a comparison, and clear the plan cache to test cleanly.

2.2 The six patterns that get named in interviews

// 1. EXTENDED REFERENCE - copy the 2-3 fields you display, keep the id
order = { customerId: ObjectId(),
          customer: { name: "Ana", email: "a@x.com", tier: "gold" } }
// Kills the $lookup on every order list screen.
// Cost: staleness. Refresh via change stream on customers, or accept it -
// an order should show the name AS IT WAS at purchase time anyway.

// 2. COMPUTED - store the aggregate, do not recompute per read
db.products.updateOne({ _id: pid }, [{
  $set: {
    ratingCount: { $add: ["$ratingCount", 1] },
    ratingAvg: { $divide: [ { $add: [ { $multiply: ["$ratingAvg","$ratingCount"] }, 5 ] },
                            { $add: ["$ratingCount", 1] } ] }
  }
}])
// Pipeline update = read-modify-write in one atomic server-side op.

// 3. BUCKET - collapse many small docs into one doc per window
{ tenantId:"acme", productId, day: ISODate("2026-09-12"),
  count: 340, views: [ { ts, sessionId }, ... ] }
// 500M event docs -> 5M bucket docs. Index size drops an order of magnitude.

// 4. OUTLIER - the 0.1% of docs that break your model
{ _id: celebUser, followers: [ ...first 1000... ], hasOverflow: true }
// Overflow rows live in a followers_overflow collection. App checks the flag.

// 5. SCHEMA VERSIONING - ship migrations without downtime
{ _v: 2, name: { first:"Ana", last:"K" } }   // v1 had a single `name` string
// Read path handles both, a background job rewrites v1 -> v2 in batches.

// 6. SUBSET - hot slice embedded, cold tail referenced
product = { reviewsTop: [ ...10 newest... ], reviewCount: 4211 }
// Product page renders with one read. "See all reviews" hits the reviews collection.

2.3 Unbounded arrays: the classic trap

Anti-pattern { _id: userId, notifications: [ ...grows forever... ] }
Three separate failures. The document crosses 16 MB and writes start failing. Every update rewrites the whole document, so write throughput collapses. A multikey index over that array becomes enormous and can never cover a query. 
// Fix A: cap the array on write, keep the overflow elsewhere
db.users.updateOne({ _id: uid }, {
  $push: { recent: { $each: [ notif ], $position: 0, $slice: 50 } }
})
// $slice:50 keeps only the newest 50, atomically. No unbounded growth.

// Fix B: own collection + TTL (the default for feeds)
db.notifications.createIndex({ tenantId:1, userId:1, createdAt:-1 })
db.notifications.createIndex({ createdAt:1 }, { expireAfterSeconds: 60*60*24*30 })

2.4 Array update operators you must know cold

// positional $ - first matching element
db.orders.updateOne(
  { _id: oid, "items.sku": "TSHIRT-RED-M" },
  { $set: { "items.$.qty": 3 } })

// arrayFilters - all elements matching a condition (the one people forget)
db.orders.updateOne(
  { _id: oid },
  { $set: { "items.$[el].price": 799 } },
  { arrayFilters: [ { "el.price": { $gt: 799 } } ] })

// $[] - every element
db.orders.updateMany({}, { $set: { "items.$[].currency": "INR" } })

// $elemMatch - one array element satisfies ALL conditions
db.orders.find({ items: { $elemMatch: { sku:"TSHIRT-RED-M", qty: { $gte: 2 } } } })
// Without $elemMatch, {"items.sku":"X","items.qty":{$gte:2}} matches if
// DIFFERENT elements satisfy each clause. Classic bug, classic interview probe.

// $addToSet vs $push - set semantics vs append
db.products.updateOne({_id:pid}, { $addToSet: { categories: "sale" } })
Interview question "Order items: embed or separate collection?"
Mid-levelEmbed, because items belong to the order.
SeniorEmbed. Items are bounded at a realistic cart size, always read with the order, and immutable after checkout, which is exactly the embed profile. I would denormalise sku, title and price into each item so an order is a true historical record even when the product later changes price. The one case I would reconsider is a B2B system with thousands of line items per order, where I would bucket items or move them out.

3. Aggregation at production scale

3.1 Rewriting the pipeline you brought

Your original ran $unwind before $lookup and pushed whole child arrays into a group. Here is the same intent, production shape:

// BEFORE (yours, ported to orders): unwind -> lookup -> group -> push everything
db.orders.aggregate([
  { $match: { createdAt: { $gte: ISODate("2026-01-01") } } },
  { $unwind: "$items" },                          // x5 fan-out
  { $lookup: { from:"products", localField:"items.productId",
               foreignField:"_id", as:"product" } },   // x5 lookups
  { $group: { _id: "$shipping.city",
              orders: { $push: "$$ROOT" },        // memory bomb
              count: { $sum: 1 } } },
  { $sort: { count: -1 } }, { $limit: 5 }
])

// AFTER: filter early, project narrow, lookup once, never push raw docs
db.orders.aggregate([
  { $match: { tenantId:"acme", createdAt:{ $gte: ISODate("2026-01-01") } } }, // IXSCAN
  { $project: { shipping:1, total:1, items:1 } },        // drop fat fields NOW
  { $unwind: "$items" },
  { $group: {
      _id: { city: "$shipping.city", sku: "$items.sku" },
      units: { $sum: "$items.qty" },
      revenue: { $sum: { $multiply: ["$items.qty","$items.price"] } } } },
  { $sort: { revenue: -1 } },
  { $limit: 50 },
  { $lookup: { from:"products", localField:"_id.sku", foreignField:"sku",
               as:"p", pipeline: [ { $project: { title:1, _id:0 } } ] } }, // 50 lookups, not 5M
  { $set: { title: { $first: "$p.title" } } },
  { $unset: "p" }
], { allowDiskUse: true })
The five rules this demonstrates
  1. $match first, on indexed fields, so stage one is an IXSCAN not a COLLSCAN.
  2. $project or $unset immediately after, to shrink every document flowing downstream.
  3. $lookup after reduction, never before a fan-out stage. Always index the foreignField.
  4. Never $push: "$$ROOT". Push ids or counts. Group stages cap at 100 MB and output docs at 16 MB.
  5. $sort immediately followed by $limit becomes a bounded top-k, which is memory-safe. Split them and it is not.

3.2 $lookup done properly

// Pipeline form: filter and shape the joined side BEFORE it lands
{ $lookup: {
    from: "orders",
    let: { cid: "$_id", t: "$tenantId" },
    pipeline: [
      { $match: { $expr: { $and: [ { $eq: ["$customerId","$$cid"] },
                                   { $eq: ["$tenantId","$$t"] } ] },
                  status: "delivered" } },        // plain filters here use the index
      { $sort: { createdAt: -1 } },
      { $limit: 5 },
      { $project: { _id:1, total:1, createdAt:1 } }
    ],
    as: "recentOrders" } }

Mandatory index for that join: db.orders.createIndex({ tenantId:1, customerId:1, status:1, createdAt:-1 }). Without it this is one collection scan per input document. Say that out loud in the interview.

On a sharded cluster $lookup and $graphLookup historically required the from collection to be unsharded. Modern versions relaxed this, but the merge still happens on one node and it is slow. Senior answer: on sharded data, denormalise with an extended reference instead of joining at read time.

3.3 The stages that separate mid from senior

// $facet - many aggregations over ONE pass. Perfect for search pages.
db.products.aggregate([
  { $match: { tenantId:"acme", categories:"apparel" } },
  { $facet: {
      page:       [ { $sort:{ price:1 } }, { $skip:0 }, { $limit:20 } ],
      byColor:    [ { $group:{ _id:"$attrs.color", n:{ $sum:1 } } } ],
      priceBands: [ { $bucket: { groupBy:"$price",
                                 boundaries:[0,500,1000,5000],
                                 default:"5000+", output:{ n:{$sum:1} } } } ],
      total:      [ { $count: "n" } ]
  } }
])
// Caveat: each facet sub-pipeline cannot use an index - the $match already
// materialised the set. Keep the $match selective.

// $setWindowFields - SQL window functions. Running totals, rank, moving average.
db.orders.aggregate([
  { $match: { tenantId:"acme" } },
  { $setWindowFields: {
      partitionBy: "$customerId",
      sortBy: { createdAt: 1 },
      output: {
        runningSpend: { $sum:"$total", window:{ documents:["unbounded","current"] } },
        movingAvg7:   { $avg:"$total", window:{ documents:[-6,0] } },
        orderNo:      { $rank: {} },
        prevTotal:    { $shift: { output:"$total", by:-1 } } } } }
])

// $merge - incremental materialised view. THE answer to "dashboard is slow".
db.orders.aggregate([
  { $match: { createdAt: { $gte: lastRunAt } } },          // incremental!
  { $group: { _id: { tenant:"$tenantId",
                     d:{ $dateTrunc:{ date:"$createdAt", unit:"day" } } },
              revenue:{ $sum:"$total" }, orders:{ $sum:1 } } },
  { $merge: { into:"daily_sales", on:"_id",
              whenMatched:"merge", whenNotMatched:"insert" } }
])
// $out replaces the whole target collection. $merge upserts. Use $merge.

// $graphLookup - recursive. Category trees, org charts, referral chains.
db.categories.aggregate([
  { $match: { slug: "apparel" } },
  { $graphLookup: { from:"categories", startWith:"$_id",
      connectFromField:"_id", connectToField:"parentId",
      as:"descendants", maxDepth: 5, depthField:"depth" } }
])

// $unionWith - combine collections (e.g. hot + archived orders)
db.orders.aggregate([
  { $match:{ tenantId:"acme" } },
  { $unionWith: { coll:"orders_archive", pipeline:[ { $match:{ tenantId:"acme" } } ] } },
  { $group:{ _id:"$status", n:{ $sum:1 } } }
])

// $densify + $fill - no gaps in a time chart
{ $densify: { field:"day", range:{ step:1, unit:"day", bounds:"full" } } },
{ $fill:    { output: { revenue: { value: 0 } } } }

4. Transactions and consistency

4.1 The rule: avoid transactions by designing better

A single-document update is always atomic, including nested fields and arrays. Most "I need a transaction" cases are really "my data is in the wrong shape".

// No transaction needed - one atomic conditional update
const res = await Product.updateOne(
  { _id: pid, available: { $gte: qty } },     // guard in the FILTER
  { $inc: { available: -qty, reserved: +qty } }
);
if (res.modifiedCount === 0) throw new OutOfStockError();
// The filter and the update are one atomic operation. Two concurrent
// requests for the last item: exactly one wins. No race, no lock, no retry.

4.2 When you genuinely need one

const session = client.startSession();
try {
  await session.withTransaction(async () => {
    const order = (await orders.insertOne(
      { tenantId, customerId, items, status:"pending", total },
      { session }))
    for (const it of items) {
      const r = await products.updateOne(
        { _id: it.productId, available: { $gte: it.qty } },
        { $inc: { available: -it.qty } },
        { session });
      if (r.modifiedCount === 0) throw new Error("OUT_OF_STOCK"); // aborts all
    }
    await ledger.insertOne({ orderId: order.insertedId, amount: total }, { session });
  }, {
    readConcern:  { level: "snapshot" },
    writeConcern: { w: "majority" },
    readPreference: "primary"          // transactions always read the primary
  });
} finally { await session.endSession(); }
Five things interviewers check
  1. Transactions require a replica set or sharded cluster. A standalone mongod cannot run them.
  2. Default 60 second limit (transactionLifetimeLimitSeconds). Keep transactions short, never wrap an HTTP call inside one.
  3. Every operation must pass { session }. A missed session means that write silently escapes the transaction. Most common bug.
  4. withTransaction retries automatically on TransientTransactionError and UnknownTransactionCommitResult, so the callback must be idempotent. Never put non-database side effects inside.
  5. Write conflicts cause aborts. Under high contention on the same document, transactions perform worse than a single atomic update.

5. Real-time: change streams and time series

5.1 Change stream, production shape

const pipeline = [
  { $match: {
      "ns.coll": "orders",
      operationType: { $in: ["insert","update","replace"] },
      "fullDocument.tenantId": "acme",
      "updateDescription.updatedFields.status": { $exists: true }  // only status flips
  } }
];

const stream = db.collection("orders").watch(pipeline, {
  fullDocument: "updateLookup",          // updates carry the whole doc
  fullDocumentBeforeChange: "whenAvailable", // needs changeStreamPreAndPostImages
  resumeAfter: await loadToken(),        // survive a restart
  maxAwaitTimeMS: 1000
});

for await (const change of stream) {
  io.to(`tenant:acme`).emit("order:update", change.fullDocument);
  await saveToken(change._id);           // PERSIST the resume token
}
The four facts that mark a senior answer
  • Change streams read the oplog and only return majority-committed changes, so you never see data that later rolls back.
  • resumeAfter works only while the token is still in the oplog window. If the process is down longer than the oplog covers, resume fails with ChangeStreamHistoryLost and you must fall back to a full resync. Size the oplog for your worst expected outage.
  • $match inside the stream pipeline filters server-side. Filtering in Node means every change crosses the network.
  • Each open stream holds a cursor and consumes connection and oplog-read resources. One stream per service, fanned out internally, not one per websocket client.

Outbox pattern: inside the same transaction as the business write, insert into an outbox collection. A change stream on outbox publishes to Kafka. This gives exactly-once-ish delivery without dual-write inconsistency.

5.3 Time series collections

db.createCollection("events", {
  timeseries: { timeField: "ts", metaField: "meta", granularity: "seconds" },
  expireAfterSeconds: 60*60*24*90
});
// meta = the low-cardinality labels you filter/group by
db.events.insertOne({ ts: new Date(),
  meta: { tenantId:"acme", type:"view", productId },
  value: 1 });

db.events.createIndex({ "meta.tenantId":1, "meta.type":1, ts:-1 });

Mongo buckets these internally, giving roughly 3-10x storage reduction and much faster range scans. Trade-offs to state: documents cannot be updated or deleted individually (only via the TTL or a whole-bucket delete in newer versions), and the metaField must be low cardinality. Do not put a session id in it.

// Bad: recount on every dashboard render

6. Replication and sharding

6.1 Replica set facts worth 30 seconds each

  • One primary, N secondaries. Secondaries replay the primary's oplog, a capped collection of idempotent operations.
  • Elections need a strict majority of voting members, which is why you run an odd number. Typical failover is 10 to 12 seconds.
  • An arbiter votes but holds no data. It lets a 2-node set elect, but it breaks w:"majority" durability. Avoid in production.
  • Replication lag is why secondaryPreferred reads can be stale. Watch it with rs.printSecondaryReplicationInfo().
  • Rollback happens when a primary that accepted un-replicated writes rejoins as a secondary. w:"majority" prevents you from ever acknowledging such a write.
  • Driver-level retryable writes and retryable reads are on by default and mask a failover for a single operation.

6.2 Shard key selection, the whole interview in one section

Judge any candidate key on four axes: cardinality, frequency (no hot value), monotonicity (no ever-increasing prefix), and query alignment (the key is in your common filters).

// BAD: monotonic - every insert lands on the max chunk = one hot shard
sh.shardCollection("app.orders", { createdAt: 1 })
sh.shardCollection("app.orders", { _id: 1 })          // ObjectId is time-ordered

// BAD: low cardinality - 5 statuses = at most 5 chunks = jumbo chunks
sh.shardCollection("app.orders", { status: 1 })

// BAD: perfect distribution, terrible reads - every query is scatter-gather
sh.shardCollection("app.orders", { _id: "hashed" })

// GOOD: tenant isolation + spread inside a tenant + targeted queries
sh.shardCollection("app.orders", { tenantId: 1, customerId: 1 })
// find({tenantId, customerId})  -> targeted, single shard
// find({tenantId})              -> hits only that tenant's shards
// Risk: one giant tenant. Mitigate with zone sharding or a refined key.

// GOOD for pure time-series writes: hashed prefix spreads, time enables range scans
sh.shardCollection("app.events", { "meta.tenantId": "hashed", ts: 1 })
Say these two things and you sound like you have run a cluster Refining a shard key is possible since 4.4 by adding suffix fields (refineCollectionShardKey), and full resharding exists since 5.0, but it copies the entire collection. Plan the key properly the first time.

Targeted vs scatter-gather: a query containing the shard key prefix goes to one shard. Without it, mongos broadcasts to every shard and merges. Sorting a scatter-gather result makes the merge expensive. Check with explain() and look at shards in the output.

8.2 Security checklist a senior is expected to list

  • RBAC, least privilege. The app user gets readWrite on one database, never root. Analytics gets a separate read-only user pointed at a secondary.
  • TLS in transit, encryption at rest (WiredTiger encryption or cloud volume encryption).
  • Queryable Encryption / CSFLE for PII such as email or PAN. The server stores ciphertext and cannot read it, yet equality and range queries still work.
  • Never build a query from raw user input. Operator injection is real in Node: a JSON body of {"password": {"$ne": null}} bypasses a naive login. Cast to string, or validate with Zod or Joi before it reaches the query.
  • Auditing for compliance, IP allowlist or private endpoint, no public bind.
  • Backups: continuous cloud backup with point-in-time recovery. Test the restore. A backup you have never restored is not a backup.

S3. Scenario: inventory and overselling

Ask: Flash sale, 100 units, 50,000 concurrent buyers. Zero overselling allowed.

// Step 1 - RESERVE atomically. This alone prevents overselling.
const r = await products.findOneAndUpdate(
  { _id: pid, available: { $gte: qty } },
  { $inc: { available: -qty, reserved: qty } },
  { returnDocument: "after" });
if (!r) return { error: "OUT_OF_STOCK" };

// Step 2 - reservation doc with a TTL, so abandoned carts self-heal
await reservations.insertOne({ pid, qty, orderId, expiresAt: new Date(Date.now()+15*60000) });
db.reservations.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 });

// Step 3 - on payment success, convert reserved -> sold
await products.updateOne({ _id: pid }, { $inc: { reserved: -qty, sold: qty } });

// Step 4 - a change stream on reservation deletes releases expired stock
reservations.watch([{ $match: { operationType: "delete" } }],
                   { fullDocumentBeforeChange: "required" });
// -> $inc available back. TTL deletes emit a delete event, so this is reliable.

9.1 Comparison

{ price: { $eq: 899 } }              // equals (implicit: { price: 899 })
{ price: { $ne: 899 } }              // not equal        SCANS - no tight bound
{ price: { $gt: 500, $lt: 2000 } }   // range, both bounds on one field
{ price: { $gte: 500, $lte: 2000 } }
{ status: { $in: ["paid","packed"] } }   // multi-point, index-friendly
{ status: { $nin: ["cancelled"] } }      // SCANS - prefer a positive $in

9.2 Logical

{ $and: [ { price:{$gt:500} }, { "attrs.color":"red" } ] }   // implicit when keys differ
{ $or:  [ { status:"paid" }, { total:{ $gt: 10000 } } ] }    // needs an index on EACH branch
{ price: { $not: { $gt: 500 } } }                            // also matches missing field!
{ $nor: [ { status:"paid" }, { status:"packed" } ] }         // neither
Two gotchas interviewers love $or uses a separate index scan per branch and de-duplicates; if any branch lacks an index the whole query scans. $not and $ne match documents where the field is absent, which silently returns rows you did not expect.

Round 1: fundamentals

QuestionCompressed answer
BSON vs JSONBinary, typed, length-prefixed. Adds Date, ObjectId, Decimal128, Binary, and int vs long. Faster to traverse, 16 MB document cap.
When would you pick MongoDB over Postgres?Evolving or per-tenant-variable schema, document-shaped aggregates read as a unit, horizontal write scaling, geo-distributed data. Pick Postgres for heavy multi-table joins, strong relational constraints, and complex reporting SQL.
Is MongoDB ACID?Yes. Single-document always. Multi-document since 4.0 on replica sets, 4.2 across shards, with snapshot isolation.
WiredTiger storage engineDocument-level concurrency via MVCC, compression on by default, checkpoints every 60s, journal for durability between them. Cache defaults to half of RAM minus 1 GB.
What is the working set?Indexes plus frequently-accessed documents. It must fit in RAM or every query pages from disk. The main capacity-planning number.
Document vs collection vs databaseRow, table, schema. Collections are lazily created and have no enforced structure unless you add a JSON schema validator.
Null vs missing vs undefined{a:null} and a missing a both match {a:null}. Distinguish with $exists. This bites on optional fields constantly.

Round 2: indexing

QuestionCompressed answer
Explain the ESR ruleEquality fields, then Sort fields, then Range fields. Violating it forces an in-memory SORT stage or a wide index scan.
Index prefix ruleAn index on {a,b,c} serves queries on a, a+b, a+b+c, but never b alone. Order your compound indexes so the common prefix is shared.
How many indexes are too many?64 hard limit; practically, watch write latency and whether index size still fits RAM. Audit with $indexStats and drop unused ones, hiding first.
What makes a query covered?Every field in filter, sort and projection is in the index, and _id is excluded. totalDocsExamined is 0. Impossible on multikey indexes.
Why can't a compound index have two array fields?The cartesian product of index entries would explode. Mongo rejects it at creation.
Index intersection, when?Rarely chosen by the planner and usually slower than one good compound index. Mention it to show awareness, then say you would build the compound index.
Building an index on a live 50M collectionRolling build: one secondary at a time with the member out of the set, then step down the primary. In Atlas, use the rolling index build option. Never a foreground build.
Query used the wrong index. Fix?Confirm with explain and allPlansExecution, clear the plan cache, and if it is genuinely a planner mistake, pin it with hint() or an index filter. Fix the root cause: usually a missing or badly ordered compound index.

Round 3: aggregation

QuestionCompressed answer
Which stages can use an index?Only stages before the first document-transforming stage: $match, $sort, $geoNear, $limit, $skip at the head. After a $group or $unwind, everything is in memory.
Optimisations the planner does for youMoves $match before $sort and before $lookup when provably safe, merges adjacent $sort+$limit into top-k, coalesces $limits, pushes $project down. You still write it correctly, because it cannot reorder past $unwind on the same field.
$group vs $bucket vs $facetGroup by key, bucket by numeric boundaries, facet runs many independent pipelines in one pass.
$out vs $merge$out replaces the target collection entirely and drops its indexes. $merge upserts and supports incremental rollups. Use $merge.
Aggregation vs findfind for simple filter+sort+project; it has lower overhead. Aggregation when you need grouping, joins, reshaping or computed fields.
How do you paginate an aggregation?Keyset on an indexed sort field if possible. If you need a total, use $facet with a page branch and a $count branch so you scan once.
Aggregation on a sharded clusterStages run on each shard in parallel, then a merge stage runs on one shard or on mongos. $group and $sort force a merge, so keep the shard-local $match as selective as possible.

Round 4: schema design

QuestionCompressed answer
How do you start a schema design?From access patterns, not entities. List every read, its frequency, its latency budget, then shape documents so the hot reads are single-document fetches.
One-to-few / one-to-many / one-to-squillionsEmbed / reference with a child-side index / reference plus a bucket or subset pattern. Naming these three tiers signals you have read the MongoDB design guidance.
Many-to-manyArray of ids on the side queried most, or a join collection when the relationship itself has attributes such as role or joinedAt.
How do you keep denormalised copies fresh?Change stream updating copies, a scheduled reconciliation job, or accept staleness where the copy is a historical snapshot. State which one and why.
Storing moneyInteger minor units or Decimal128. Never a double, because binary floating point cannot represent 0.1 exactly.
Tree structuresParent reference for cheap writes, array of ancestors for cheap subtree reads, materialised path for prefix queries, nested sets almost never. $graphLookup traverses a parent reference.
Soft deletedeletedAt plus a partial index that excludes deleted rows, so indexes stay small and unique constraints still work.

Round 5: transactions and consistency

QuestionCompressed answer
When do you NOT use a transaction?When one atomic document update does the job, and under high contention on a hot document where write conflicts cause repeated aborts.
What isolation do transactions give?Snapshot isolation with readConcern:"snapshot". Readers see a consistent point in time; writers conflict and abort rather than block indefinitely.
What is a TransientTransactionError?A retryable failure such as a write conflict or a failover. withTransaction retries it for you, which is why the callback must be idempotent and free of external side effects.
Read-your-own-write on a secondaryUse the same client session for both operations. Causal consistency makes the secondary wait until it has replicated your write.
What does w:"majority" actually guarantee?The write reached a majority of data-bearing voting members, so it survives any single failover and can never be rolled back.
Two-phase commit across servicesDo not. Use the outbox pattern or a saga with compensating actions, because a MongoDB transaction cannot span an HTTP call.

Round 6: replication, sharding, scaling

QuestionCompressed answer
When do you shard?When one replica set can no longer hold the working set in RAM, or write throughput exceeds one primary, or you need data residency per region. Not before: sharding adds real operational cost.
Pick a shard key for orders{tenantId:1, customerId:1}. High cardinality, no monotonic prefix, aligned with the common query, and it isolates tenants. Risk is a whale tenant, mitigated by zone sharding.
Hashed vs rangedHashed spreads writes perfectly but makes every range query a scatter-gather. Ranged keeps range scans targeted but risks hot chunks on monotonic keys. Compound of both is often the answer.
What is a jumbo chunk?A chunk that cannot be split because all its documents share one shard key value. It stops balancing. Caused by low-cardinality keys.
What does mongos do?Routes queries using config-server metadata, targets shards when the key is present, broadcasts and merges when it is not, and handles sorting and limiting of merged results.
Can you change a shard key?Refine by adding suffix fields since 4.4; full resharding since 5.0, but it rewrites the entire collection. Design it right the first time.
Read scaling without shardingAdd secondaries and route reports to secondaryPreferred, accepting replication lag. Add caching. Sharding is for write and data-size scaling.

Round 7: Node, Mongoose, application layer

QuestionCompressed answer
How does the driver connection pool work?One pool per process per cluster, sized by maxPoolSize. Requests beyond that queue for a connection. Total connections equals pods times pool size, which must stay under the cluster limit.
Mongoose: pros and when to drop itSchema, validation, middleware, population, typed models. Drop to the raw driver for bulk pipelines, high-throughput writes, and anywhere hydration overhead matters.
lean() tradeoffReturns plain objects, three to five times faster, but you lose virtuals, getters, setters and save(). Always use it on read-only list endpoints.
populate() vs $lookuppopulate is a second query from the app; $lookup is a server-side join. populate is easier and lets you cache the child separately; $lookup avoids the round trip. Neither scales across shards.
How do you export a million rows?A cursor streamed to the response with backpressure, never an array in memory. Read from a secondary, use lean() and a projection.
NoSQL injection in ExpressA JSON body can smuggle operators, for example {"password":{"$ne":null}}. Validate and coerce every input with Zod or Joi before it touches a query.
How do you handle schema migrations?Additive changes first, dual-read with a _v field, backfill in batches with bulkWrite and a rate limit, then flip the write path, then clean up. Never a blocking updateMany over 50M rows.

Round 8: the gotcha questions

QuestionCompressed answer
Why did my $ne query return documents without the field?A missing field is not equal to the value, so it matches. Add $exists:true.
Why does {"a.b":1,"a.c":2} behave oddly on arrays?Different array elements can satisfy each clause. Use $elemMatch.
Why is my sort returning inconsistent pages?The sort key is not unique, so ties order arbitrarily across queries. Always add _id as the final tiebreaker.
Why did updateMany lock up the server?It is not a single atomic operation; it yields between documents, so other writes interleave and the oplog floods. Batch it.
Why is countDocuments slow?It genuinely counts matching documents. Use a covered index, a maintained counter, or the estimate when no filter is needed.
Why did my unique index creation fail?Existing duplicates. Find them with a $group plus $match: {n:{$gt:1}}, resolve, then build.
Why did the TTL not delete on time?The sweeper runs once a minute and only on the primary, and it is best effort under load. TTL means eventually, not exactly.
Why is an upsert inserting duplicates?Concurrent upserts on a non-unique filter both insert. A unique index on the filter fields is what actually makes upsert safe.

Red flags and power phrases

Never say
  • "MongoDB is schemaless." It is schema-flexible, and production systems enforce a schema.
  • "It doesn't support joins." It has $lookup, $graphLookup and $unionWith.
  • "It doesn't support transactions." Multi-document ACID since 4.0, sharded since 4.2.
  • "I'd add an index" as a complete answer, with no mention of measuring first.
  • "I'd use skip for pagination."
Say instead
  • "I'd design the schema around the access patterns, so let me ask what the read path looks like first."
  • "Let me check explain before I change anything."
  • "That works, but it breaks at 10x because..."
  • "I'd avoid the transaction here by making this a single atomic document update."
  • "That's a denormalisation trade-off: faster reads, and here is how I keep it consistent."
The closing move Every design answer should end with the trade-off you accepted and the failure mode you are watching. Interviewers hire the person who volunteers what breaks, not the person with the tidiest diagram.
