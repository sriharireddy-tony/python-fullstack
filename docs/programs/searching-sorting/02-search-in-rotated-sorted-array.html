Searching & sorting · Problem 02

Search in Rotated Sorted Array

The array was sorted, then somebody rotated it. Binary search seems dead — and it is not, because of one saving observation: however you cut a rotated sorted array in half, at least one of the two halves is still sorted.

Step 1

The problem

An array of distinct values was sorted ascending, then rotated at some unknown pivot. Find the index of a target in O(log n), or return -1.

ArrayTargetAnswer
[4,5,6,7,0,1,2]04
[4,5,6,7,0,1,2]3-1
[4,5,6,7,0,1,2]62
[1]0-1
[1,2,3,4,5]43

Picture what rotation does. The array is two sorted runs stuck together, and everything in the first run is larger than everything in the second:

  originally sorted:   0  1  2  4  5  6  7
  rotated by 3:        4  5  6  7 | 0  1  2
                       \________/   \_____/
                        run A         run B

  Both runs are sorted. Every value in A is bigger than every
  value in B. The "cliff" between 7 and 0 is the pivot.
Note the last row

A rotation by 0 — or by the full length — leaves the array untouched. So a normally sorted array is a valid input, and your solution must handle it. It is the case where the “second run” is empty.

Step 2

Think first — the obvious answers

Version 0a — just scan it
function searchLinear(nums, target) {
  for (let i = 0; i < nums.length; i++) {
    if (nums[i] === target) return i;
  }
  return -1;
}

console.log(searchLinear([4,5,6,7,0,1,2], 0));   // 4
console.log(searchLinear([4,5,6,7,0,1,2], 3));   // -1
console.log(searchLinear([1], 0));               // -1

// O(n). Completely correct, and completely ignores the structure
// the problem handed you. Say it out loud, then beat it.
Version 0b — find the pivot, then search a half
// Two binary searches: one to locate the rotation point, one to
// search the correct half.
function findPivot(nums) {
  // the index of the SMALLEST value -- where the cliff lands
  let lo = 0, hi = nums.length - 1;
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] > nums[hi]) lo = mid + 1;   // the cliff is to the right
    else hi = mid;                             // mid could be the smallest
  }
  return lo;
}

function plainBinary(nums, target, lo, hi) {
  while (lo <= hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] === target) return mid;
    if (nums[mid] < target) lo = mid + 1;
    else hi = mid - 1;
  }
  return -1;
}

function searchTwoPass(nums, target) {
  if (nums.length === 0) return -1;

  const pivot = findPivot(nums);

  // the target is in whichever half its value belongs to
  if (target >= nums[pivot] && target <= nums[nums.length - 1]) {
    return plainBinary(nums, target, pivot, nums.length - 1);
  }
  return plainBinary(nums, target, 0, pivot - 1);
}

console.log(findPivot([4,5,6,7,0,1,2]));            // 4  (the 0)
console.log(findPivot([1,2,3,4,5]));                // 0  (no rotation)
console.log('');
console.log(searchTwoPass([4,5,6,7,0,1,2], 0));     // 4
console.log(searchTwoPass([4,5,6,7,0,1,2], 6));     // 2
console.log(searchTwoPass([4,5,6,7,0,1,2], 3));     // -1
console.log(searchTwoPass([1,2,3,4,5], 4));         // 3
console.log(searchTwoPass([1], 0));                 // -1
console.log(searchTwoPass([5,1,3], 3));             // 2

// Two O(log n) passes, so still O(log n). Perfectly good, and a
// genuinely easier thing to reason about than the one-pass version.

The two-pass version is worth knowing well. “Find the pivot, then binary search the right half” is easy to explain and easy to get right — and it is a complete answer to the question.

Step 3

Why the scan is not good enough

Not slow in absolute terms — O(n) is fine for a thousand elements. But the problem explicitly asks for O(log n), and the rotation is a hint, not an obstacle.

Timing demo
const N = 2000000;
const sorted = [];
for (let i = 0; i < N; i++) sorted.push(i * 2);

function rotatedBinary(a, t) {

Step 4

The better idea — one half is always sorted

The unlock

Cut the array anywhere. The cliff can only be in one of the two halves — so the other half is a plain sorted run. Identify the sorted half, and you can test in O(1) whether the target lies inside it. If it does, search there. If it does not, search the other half.

  [4, 5, 6, 7, 0, 1, 2]      lo=0  hi=6  mid=3 (value 7)

  left half:  4 5 6 7     nums[lo]=4 <= nums[mid]=7   -> SORTED
  right half: 0 1 2       contains the cliff

  Because the left half is sorted, "is the target in it?" is a
  single range check:  target >= 4 AND target < 7


  [6, 7, 0, 1, 2, 4, 5]      lo=0  hi=6  mid=3 (value 1)

  left half:  6 7 0 1     nums[lo]=6 > nums[mid]=1    -> NOT sorted
  right half: 2 4 5       -> SORTED

  So check:  target > 1 AND target <= 5

The test for which half is sorted

one comparison decides it
if (nums[lo] <= nums[mid]) {
  // the left half [lo..mid] is sorted
} else {
  // the right half [mid..hi] is sorted
}

Why <= and not <? Because lo can equal mid — a range of one or two elements — and a single element is trivially sorted. With <, that case falls into the wrong branch and the search goes astray on small ranges.

Get the range checks right, and use both ends

Once you know the left half [lo..mid] is sorted, the target is inside it exactly when target >= nums[lo] && target < nums[mid]. Both bounds matter — checking only target < nums[mid] would send a target smaller than everything in the left half into the wrong half.

The comparison against nums[mid] is strict because mid itself was already tested and did not match.

Step 6

Version 1 — without built-in methods

Version 1 — one pass, loops only
function searchRotatedManual(nums, target) {
  let lo = 0;
  let hi = nums.length - 1;

  while (lo <= hi) {
    const mid = lo + ((hi - lo) - ((hi - lo) % 2)) / 2;

    if (nums[mid] === target) {
      return mid;
    }

    // <= because lo can equal mid, and one element is sorted
    if (nums[lo] <= nums[mid]) {
      // the LEFT half is a plain sorted run
      if (target >= nums[lo] && target < nums[mid]) {
        hi = mid - 1;         // the target lies inside it
      } else {
        lo = mid + 1;         // it must be in the other half
      }
    } else {
      // the RIGHT half is a plain sorted run
      if (target > nums[mid] && target <= nums[hi]) {
        lo = mid + 1;
      } else {
        hi = mid - 1;
      }
    }
  }

  return -1;
}

function search(nums, target) {
  let lo = 0, hi = nums.length - 1;
  while (lo <= hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] === target) return mid;
    if (nums[lo] <= nums[mid]) {

    }

}

Version 2 — with built-in methods

Version 2 — the interview answer
function search(nums, target) {
  let lo = 0;
  let hi = nums.length - 1;

  while (lo <= hi) {
    const mid = lo + Math.floor((hi - lo) / 2);

    if (nums[mid] === target) return mid;

    if (nums[lo] <= nums[mid]) {
      // left half sorted
      if (target >= nums[lo] && target < nums[mid]) hi = mid - 1;
      else lo = mid + 1;
    } else {
      // right half sorted
      if (target > nums[mid] && target <= nums[hi]) lo = mid + 1;
      else hi = mid - 1;
    }
  }

  return -1;
}

the related problems this unlocks
// 1. Find the minimum in a rotated sorted array -- the pivot itself
function findMin(nums) {
  let lo = 0, hi = nums.length - 1;
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    // compare with the RIGHT end, not the left -- see the note below
    if (nums[mid] > nums[hi]) lo = mid + 1;
    else hi = mid;
  }
  return nums[lo];
}

console.log(findMin([4,5,6,7,0,1,2]));   // 0
console.log(findMin([3,4,5,1,2]));       // 1
console.log(findMin([11,13,15,17]));     // 11  -- not rotated
console.log(findMin([2,1]));             // 1

// 2. How many places was it rotated by?
function rotationAmount(nums) {
  let lo = 0, hi = nums.length - 1;
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] > nums[hi]) lo = mid + 1;
    else hi = mid;
  }
  return lo;
}

console.log(rotationAmount([4,5,6,7,0,1,2]));   // 4
console.log(rotationAmount([1,2,3]));           // 0

// 3. With DUPLICATES allowed, O(log n) becomes impossible.
// [1,1,1,0,1,1,1]: nums[lo], nums[mid] and nums[hi] are all 1,
// so you cannot tell which half is sorted. The fix is to shrink
// the range by one and fall back towards O(n) in the worst case.
function searchWithDuplicates(nums, target) {
  let lo = 0, hi = nums.length - 1;
  while (lo <= hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] === target) return true;

    if (nums[lo] === nums[mid] && nums[mid] === nums[hi]) {
      lo++; hi--;                       // cannot decide -- shrink by one
    } else if (nums[lo] <= nums[mid]) {
      if (target >= nums[lo] && target < nums[mid]) hi = mid - 1;
      else lo = mid + 1;
    } else {
      if (target > nums[mid] && target <= nums[hi]) lo = mid + 1;
      else hi = mid - 1;
    }
  }
  return false;
}

console.log(searchWithDuplicates([2,5,6,0,0,1,2], 0));   // true
console.log(searchWithDuplicates([2,5,6,0,0,1,2], 3));   // false
console.log(searchWithDuplicates([1,1,1,0,1,1,1], 0));   // true
Why findMin compares with nums[hi]

Comparing nums[mid] with nums[lo] does not work for finding the minimum, because on an unrotated array nums[mid] > nums[lo] is true and would send you right — away from the answer. Comparing with the right end is unambiguous: if nums[mid] > nums[hi] the cliff must be to the right of mid; otherwise mid is in the second run and could itself be the minimum.

Two very similar problems, two different reference points. Trace both by hand once.

Step 8

Complexity, in sentences

SolutionTimeSpace
Linear scanO(n)O(1)
Find pivot, then binary searchO(log n)O(1)
One-pass modified binary searchO(log n)O(1)
With duplicates allowedO(n) worst caseO(1)

Every iteration still discards half the range, so it is O(log n) exactly as plain binary search is. The extra branch costs one comparison, not an extra pass.

The duplicates row is the honest caveat. When nums[lo], nums[mid] and nums[hi] are all equal you cannot tell which half is sorted, so you shrink by one and the worst case — an array of all equal values — degrades to O(n). That is not a flaw in the solution; it is provably unavoidable.

Say this in the interview

“Wherever I cut it, the rotation point can only be in one half, so at least one half is plainly sorted. I detect which by comparing nums[lo] with nums[mid] — using <= so a single-element range counts as sorted. Then I check in O(1) whether the target falls inside that sorted half’s value range: if so I search it, otherwise I search the other half. Either way half the range is discarded, so O(log n) time and O(1) space. With duplicates the sortedness test becomes ambiguous and the worst case degrades to O(n).”

Step 9

Mistakes people actually make

1. Using < instead of <= in the sortedness test

Broken — single-element ranges misclassified
function broken(nums, target) {
  let lo = 0, hi = nums.length - 1;
  while (lo <= hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] === target) return mid;
    if (nums[lo] < nums[mid]) {                  // < instead of <=
      if (target >= nums[lo] && target < nums[mid]) hi = mid - 1;
      else lo = mid + 1;
    } else {
      if (target > nums[mid] && target <= nums[hi]) lo = mid + 1;
      else hi = mid - 1;
    }
  }
  return -1;
}

console.log(broken([4,5,6,7,0,1,2], 0));   // 4   fine
console.log(broken([3,1], 1));             // -1  WRONG, should be 1
console.log(broken([5,1,3], 3));           // -1  WRONG, should be 2
console.log(broken([1,3], 3));             // 1   fine

// On [3,1] with target 1: lo=0, hi=1, mid=0. nums[0]=3 and
// nums[0]=3, so 3 < 3 is FALSE -- it takes the "right half sorted"
// branch, checks 1 > 3, and goes left. The answer is lost.
// A range where lo === mid must count as sorted.

2. Checking only one end of the sorted range

Broken — incomplete range test
function broken(nums, target) {
  let lo = 0, hi = nums.length - 1;
  while (lo <= hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] === target) return mid;
    if (nums[lo] <= nums[mid]) {
      if (target < nums[mid]) hi = mid - 1;      // missing target >= nums[lo]
      else lo = mid + 1;
    } else {
      if (target > nums[mid]) lo = mid + 1;      // missing target <= nums[hi]
      else hi = mid - 1;
    }
  }
  return -1;
}

console.log(broken([4,5,6,7,0,1,2], 6));   // 2   fine
console.log(broken([4,5,6,7,0,1,2], 0));   // -1  WRONG, should be 4
console.log(broken([4,5,6,7,0,1,2], 1));   // -1  WRONG, should be 5

// Target 0 is smaller than everything in the sorted left half
// [4,5,6,7], so "0 < 7" sends it left -- into the half it is not in.
// The range check needs BOTH bounds.

3. Trying to search both halves

correct but no longer logarithmic
function bothHalves(nums, target, lo = 0, hi = nums.length - 1) {
  if (lo > hi) return -1;
  const mid = lo + Math.floor((hi - lo) / 2);
  if (nums[mid] === target) return mid;

  const left = bothHalves(nums, target, lo, mid - 1);
  if (left !== -1) return left;
  return bothHalves(nums, target, mid + 1, hi);
}

console.log(bothHalves([4,5,6,7,0,1,2], 0));   // 4   correct
console.log(bothHalves([4,5,6,7,0,1,2], 3));   // -1  correct

// It works because it eventually visits everything -- which is
// exactly the problem. Recursing into BOTH halves is O(n), not
// O(log n). The whole point is deciding which half to discard.

4. Assuming the array is rotated at all

[1,2,3,4,5] is a valid input. The left half is always sorted for it, the branch reduces to plain binary search, and it works — but only if the <= in the sortedness test is right. Always include an unrotated array in your tests.

Step 10

Practice before you move on

  1. Write the two-pass version first — find the pivot, then binary search the right half. It is easier to defend, and it is a complete O(log n) answer.
  2. Then write the one-pass version from memory and run the exhaustive test in Step 6. If it passes every rotation of every size, you have it.
  3. Find Minimum in Rotated Sorted Array. In Step 7 — and work out why it compares with nums[hi] rather than nums[lo].
  4. Search in Rotated Sorted Array II (duplicates allowed). Add the “cannot decide” branch and explain why O(log n) is no longer possible.
  5. Find how many times the array was rotated. It is the index of the minimum. One line once you have findMin.
What to carry forward

Binary search survives as long as you can decide which half to discard. The array does not have to be fully sorted — it only has to be structured enough that one comparison rules out half the possibilities. That is the same insight behind Find Peak Element, binary search on the answer, and searching a 2D sorted matrix. When a problem looks like “binary search does not apply here”, ask instead: what single test would let me throw away half?
