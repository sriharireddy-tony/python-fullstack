Searching & sorting · Problem 05

Merge Sorted Arrays

Two sorted arrays into one. The forward version is the merge step of merge sort, and worth knowing cold. The in-place version has one trick worth the whole page: fill backwards, because that is the only direction with free space.

Step 1

The problem

Two versions, and they are genuinely different exercises.

A — return a new array. Given two sorted arrays, return one sorted array containing everything.

B — merge in place. nums1 has length m + n, where the first m slots hold sorted values and the last n are empty padding. Merge nums2 (n values) into it.

nums1mnums2nResult
[1,2,3,_,_,_]3[2,5,6]3[1,2,2,3,5,6]
[1]1[]0[1]
[_]0[1]1[1]
[4,5,6,_,_,_]3[1,2,3]3[1,2,3,4,5,6]
Why the in-place version is interesting

Merging forwards would write into nums1[0], nums1[1] and so on — slots that still hold values you have not read yet. You would have to shift everything along, which is O(m · n).

But the back of nums1 is empty. Writing there destroys nothing. So fill from the end, taking the largest remaining value each time.

Row four is the worst case for the naive approach: every value in nums2 belongs before every value in nums1, so a forward merge would shift the entire array three times.

Step 2

Think first — concatenate and sort

Version 0 — the one-liner
function mergeSimple(a, b) {
  return [...a, ...b].sort((x, y) => x - y);
}

console.log(mergeSimple([1,2,3], [2,5,6]));   // [1,2,2,3,5,6]
console.log(mergeSimple([4,5,6], [1,2,3]));   // [1,2,3,4,5,6]
console.log(mergeSimple([], [1]));            // [1]
console.log(mergeSimple([1], []));            // [1]

// The in-place variant, using splice and sort:
function mergeInPlaceSort(nums1, m, nums2, n) {
  nums1.splice(m, n, ...nums2);         // overwrite the padding
  nums1.sort((a, b) => a - b);
  return nums1;
}

const a = [1,2,3,0,0,0];
console.log(mergeInPlaceSort(a, 3, [2,5,6], 3));   // [1,2,2,3,5,6]

// O((m+n) log(m+n)). Correct, short, and it throws away the fact
// that both inputs were ALREADY SORTED.

Say this out loud, quote its complexity, and then point out what it wastes: sorting rediscovers an order you were handed. Merging two sorted lists is linear.

Timing demo — forward with shifting vs backward
const M = 20000, N = 20000;

function build() {
  const a = [];
  for (let i = 0; i < M; i++) a.push(i + N);      // all LARGER than nums2
  for (let i = 0; i < N; i++) a.push(0);           // padding
  const b = [];
  for (let i = 0; i < N; i++) b.push(i);
  return [a, b];
}

function forwardWithShifting(nums1, m, nums2, n) {
  let i = 0, j = 0, count = m;
  while (j < n) {
    if (i >= count || nums2[j] < nums1[i]) {
      // make room: shift everything from i onwards right by one
      for (let k = count; k > i; k--) nums1[k] = nums1[k - 1];
      nums1[i] = nums2[j];
      count++; i++; j++;
    } else {
      i++;
    }
  }
  return nums1;
}

function backwardMerge(nums1, m, nums2, n) {
  let i = m - 1, j = n - 1, k = m + n - 1;
  while (j >= 0) {
    if (i >= 0 && nums1[i] > nums2[j]) nums1[k--] = nums1[i--];
    else nums1[k--] = nums2[j--];
  }
  return nums1;
}

Step 4

The better idea — two pointers, and the direction

Version A: forward merge into a new array

The unlock

Point at the front of each array. Compare the two heads and take the smaller, advancing that pointer. Repeat. When one array runs out, copy the rest of the other.

  a = [1, 2, 3]      b = [2, 5, 6]
       i                  j

  1 vs 2  ->  take 1    out = [1]           i++
  2 vs 2  ->  take 2 from a (see below)   out = [1,2]   i++
  3 vs 2  ->  take 2 from b   out = [1,2,2]   j++
  3 vs 5  ->  take 3    out = [1,2,2,3]     i++
  a is exhausted  ->  copy the rest of b:  5, 6

  out = [1,2,2,3,5,6]

On a tie, take from a — use a[i] <= b[j]. That makes the merge stable: equal elements keep their original relative order, with everything from a before everything from b. It is invisible for plain numbers and matters enormously when you are sorting objects by one field.

Version B: backward merge, in place

The unlock

Write into the last slot of nums1 and walk backwards, taking the larger of the two remaining tails each time.

Why it is safe: the write pointer starts at m + n - 1 and the read pointer into nums1 starts at m - 1. The write pointer is always ahead of the read pointer, so it can never overwrite a value that has not been read.

  nums1 = [1, 2, 3, _, _, _]        m = 3
  nums2 = [2, 5, 6]                 n = 3

           i           k                i = m-1 = 2   (last real value)
                                        j = n-1 = 2   (last of nums2)
                                        k = m+n-1 = 5 (last slot)

  nums1[2]=3  vs  nums2[2]=6   ->  6 is larger  ->  nums1[5] = 6
  nums1[2]=3  vs  nums2[1]=5   ->  5 is larger  ->  nums1[4] = 5
  nums1[2]=3  vs  nums2[0]=2   ->  3 is larger  ->  nums1[3] = 3
  nums1[1]=2  vs  nums2[0]=2   ->  tie, take nums2  ->  nums1[2] = 2
  nums2 exhausted  ->  done. [1,2] is already in place.

  nums1 = [1, 2, 2, 3, 5, 6]
The loop only needs to run while nums2 has values left

If nums1 runs out first, the remaining nums2 values must still be copied in. But if nums2 runs out first, the remaining nums1 values are already in their correct positions — they were never moved. So while (j >= 0) is the whole loop, and there is no clean-up pass.

That asymmetry is a genuinely satisfying detail, and interviewers ask about it.

Version 1a — forward merge into a new array
function mergeForwardManual(a, b) {
  const out = [];
  let i = 0;      // index into a
  let j = 0;      // index into b
  let k = 0;      // index into out

  // while BOTH have values, take the smaller head
  while (i < a.length && j < b.length) {
    if (a[i] <= b[j]) {         // <= keeps the merge STABLE
      out[k] = a[i];
      i = i + 1;
    } else {
      out[k] = b[j];
      j = j + 1;
    }
    k = k + 1;
  }

  // one of them is empty -- copy whatever is left of the other
  while (i < a.length) { out[k] = a[i]; i = i + 1; k = k + 1; }
  while (j < b.length) { out[k] = b[j]; j = j + 1; k = k + 1; }

  return out;
}

Version 1b — backward merge, in place
function mergeInPlaceManual(nums1, m, nums2, n) {
  let i = m - 1;            // last real value in nums1
  let j = n - 1;            // last value in nums2
  let k = m + n - 1;        // where we write

  // only nums2 needs draining: leftover nums1 values are already
  // sitting in their final positions
  while (j >= 0) {

    if (i >= 0 && nums1[i] > nums2[j]) {
      nums1[k] = nums1[i];
      i = i - 1;
    } else {
      nums1[k] = nums2[j];
      j = j - 1;
    }

    k = k - 1;
  }

  return nums1;
}

function show(nums1, m, nums2, n) {
  const copy = [...nums1];
  mergeInPlaceManual(copy, m, nums2, n);
  return copy;
}

Version 2 — both, the interview answers
// A: new array, forward merge
function merge(a, b) {
  const out = [];
  let i = 0, j = 0;

  while (i < a.length && j < b.length) {
    out.push(a[i] <= b[j] ? a[i++] : b[j++]);
  }

  // whichever is left over is already sorted
  return out.concat(a.slice(i), b.slice(j));
}

console.log(merge([], [1]));            // [1]

// B: in place, backward merge
function mergeInPlace(nums1, m, nums2, n) {
  let i = m - 1, j = n - 1, k = m + n - 1;

  while (j >= 0) {
    nums1[k--] = (i >= 0 && nums1[i] > nums2[j]) ? nums1[i--] : nums2[j--];
  }

  return nums1;
}

// Naive: merge them one at a time.
function mergeTwo(a, b) {
  const out = [];
  let i = 0, j = 0;
  while (i < a.length && j < b.length) out.push(a[i] <= b[j] ? a[i++] : b[j++]);
  return out.concat(a.slice(i), b.slice(j));
}

function mergeKSequential(lists) {
  let acc = [];
  for (const list of lists) acc = mergeTwo(acc, list);
  return acc;
}

// Better: merge in PAIRS, halving the number of lists each round.
function mergeKPairwise(lists) {
  let current = lists;
  while (current.length > 1) {
    const next = [];
    for (let i = 0; i < current.length; i += 2) {
      next.push(i + 1 < current.length ? mergeTwo(current[i], current[i + 1])
                                       : current[i]);
    }
    current = next;
  }
  return current[0] || [];
}

merging objects, and why stability matters
// Merging by one field. With `<=` the merge is STABLE: when two
// records tie, the one from the FIRST list comes first.
function mergeBy(a, b, keyOf) {
  const out = [];
  let i = 0, j = 0;
  while (i < a.length && j < b.length) {
    out.push(keyOf(a[i]) <= keyOf(b[j]) ? a[i++] : b[j++]);
  }
  return out.concat(a.slice(i), b.slice(j));
}

const teamA = [{ n: 'ana', score: 5 }, { n: 'bo', score: 9 }];
const teamB = [{ n: 'cy', score: 5 }, { n: 'di', score: 9 }];

console.log(mergeBy(teamA, teamB, p => p.score).map(p => p.n + ':' + p.score));
// ana:5  cy:5  bo:9  di:9      -- team A wins every tie

// Change <= to < and the ties flip:
function mergeByUnstable(a, b, keyOf) {
  const out = [];
  let i = 0, j = 0;
  while (i < a.length && j < b.length) {
    out.push(keyOf(a[i]) < keyOf(b[j]) ? a[i++] : b[j++]);
  }
  return out.concat(a.slice(i), b.slice(j));
}

console.log(mergeByUnstable(teamA, teamB, p => p.score).map(p => p.n + ':' + p.score));

Step 8

Complexity, in sentences

SolutionTimeExtra space
Concatenate and sortO((m+n) log(m+n))O(m+n)
Forward merge, new arrayO(m + n)O(m+n)
Forward merge, in place with shiftingO(m · n)O(1)
Backward merge, in placeO(m + n)O(1)

Every element is written exactly once, and each write costs one comparison. So O(m + n) — and that is optimal, since you must touch every element to place it.

The backward version is the only one that is both linear and constant-space. That combination is the reason the problem is posed the way it is, with the padding at the end of nums1.

Say this in the interview

“Both arrays are already sorted, so I merge with two pointers rather than sorting again: O(m+n) instead of O((m+n) log(m+n)). For the in-place version I fill backwards from index m+n-1, taking the larger of the two tails, because the free space is at the end of nums1 — and the write pointer is always ahead of the read pointer, so nothing unread is overwritten. The loop only needs to drain nums2: whatever is left in nums1 is already in place. O(m+n) time, O(1) space.”

Mistakes people actually make

1. Merging in place forwards

Broken — overwrites unread values
function broken(nums1, m, nums2, n) {
  let i = 0, j = 0, k = 0;
  while (i < m && j < n) {
    if (nums1[i] <= nums2[j]) nums1[k++] = nums1[i++];   // writing over nums1!

// Adding a nums1 drain loop is not WRONG -- it just never does
// anything useful, and its presence suggests you have not seen why.
function withExtraLoop(nums1, m, nums2, n) {
  let i = m - 1, j = n - 1, k = m + n - 1;
  while (i >= 0 && j >= 0) {
    nums1[k--] = nums1[i] > nums2[j] ? nums1[i--] : nums2[j--];
  }
  while (j >= 0) nums1[k--] = nums2[j--];
  let moved = 0, realMoves = 0;
  while (i >= 0) {
    if (k !== i) realMoves++;          // did it actually move anything?
    nums1[k--] = nums1[i--];
    moved++;
  }
  console.log('  nums1 drain ran ' + moved + ' times, ' +
              realMoves + ' of which moved a value');
  return nums1;
}

console.log(withExtraLoop([1,2,3,0,0,0], 3, [2,5,6], 3));
console.log(withExtraLoop([4,5,6,0,0,0], 3, [1,2,3], 3));
console.log(withExtraLoop([1,2,3,0,0,0], 3, [4,5,6], 3));

// "0 of which moved a value" every time. When nums2 empties, every
// remaining nums1 value is already at its final index -- k and i
// are equal, so nums1[k] = nums1[i] is a no-op. The loop can run,
// but it never has anything to do.

4. Using < and quietly losing stability

Shown in Step 7. For numbers it makes no observable difference. For objects sorted by one field it reverses every tie — and merge sort’s reputation for being stable rests entirely on this one character. Use <= and know why.

5. Trusting nums1.length instead of m

Broken — counts the padding as data
function broken(nums1, m, nums2, n) {
  let i = nums1.length - 1;        // should be m - 1
  let j = n - 1;
  let k = m + n - 1;
  while (j >= 0) {
    if (i >= 0 && nums1[i] > nums2[j]) nums1[k--] = nums1[i--];
    else nums1[k--] = nums2[j--];
  }
  return nums1;
}

console.log(broken([1,2,3,0,0,0], 3, [2,5,6], 3));
// [6,6,6,6,6,6] plus junk at NEGATIVE indexes -- total nonsense

console.log(broken([4,5,6,0,0,0], 3, [1,2,3], 3));
// [3,3,3,3,3,3] plus junk -- the padding zeros were read as data,
// they compared smaller than everything, and the write pointer ran
// off the front of the array into negative indexes.

// nums1.length is m + n. The last n slots are PADDING, not data.
// The problem gives you m precisely so you know where the real
// values end -- use it.
Step 10

Practice before you move on

  1. Write the forward merge from memory, including both leftover loops. It is the core of merge sort, which is the next page.
  2. Write the backward in-place merge from memory, then say why there is no nums1 drain loop.
  3. Merge k sorted arrays. In Step 7 — do the pairwise version and work out why it beats merging one at a time. With a min-heap you can also do it in one pass.
  4. Intersection of two sorted arrays. The same two pointers: advance the smaller one, and record a value only when both match. Then do the union, and the difference.
  5. Median of two sorted arrays. The famously hard one. Merging gives O(m+n); the O(log(min(m,n))) solution binary-searches the split point. Try the merge version first, then read about the fast one.
What to carry forward

Fill from the end when the free space is at the end. Squares of a Sorted Array used the same move for a different reason; here it is the difference between O(m+n) and O(m·n). The general question when writing into an array you are also reading: where is the space I am allowed to destroy, and can I arrange for the write pointer to stay ahead of the read pointer?
