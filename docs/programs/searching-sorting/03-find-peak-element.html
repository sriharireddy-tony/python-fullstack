Searching & sorting · Problem 03

Find Peak Element

The array is not sorted, and binary search works anyway. This is the problem that breaks the habit of thinking “binary search needs a sorted array” — what it actually needs is a rule for discarding half.

Step 1

The problem

A peak is an element strictly greater than both its neighbours. Return the index of any peak. Treat the positions just outside the array as -Infinity, so the first and last elements only need to beat their one real neighbour.

InputValid answers
[1, 2, 3, 1]2
[1, 2, 1, 3, 5, 6, 4]1 or 5
[1, 2, 3, 4, 5]4 — the last element
[5, 4, 3, 2, 1]0 — the first
[7]0
Why a peak always exists

Start anywhere and keep walking uphill. You cannot walk forever — the array is finite — so eventually you stop, and the place you stop is higher than both sides. That is a peak.

The -Infinity boundary is what guarantees you never walk off the end: an increasing array peaks at its last element, a decreasing one at its first.

The problem usually adds nums[i] !== nums[i + 1] — no two neighbours are equal. That matters: with plateaus, “which way is uphill?” can be unanswerable, and the logarithmic solution collapses.

Step 2

Think first — just look at every element

Version 0 — linear scan
function findPeakLinear(nums) {
  for (let i = 0; i < nums.length; i++) {
    const left  = i === 0 ? -Infinity : nums[i - 1];
    const right = i === nums.length - 1 ? -Infinity : nums[i + 1];

    if (nums[i] > left && nums[i] > right) return i;
  }
  return -1;
}

console.log(findPeakLinear([1,2,3,1]));         // 2
console.log(findPeakLinear([1,2,1,3,5,6,4]));   // 1
console.log(findPeakLinear([1,2,3,4,5]));       // 4
console.log(findPeakLinear([5,4,3,2,1]));       // 0
console.log(findPeakLinear([7]));               // 0

// O(n), obviously correct. And there is an even simpler version:
// the first index where the value STARTS falling is a peak.
function findPeakSimpler(nums) {
  for (let i = 0; i < nums.length - 1; i++) {
    if (nums[i] > nums[i + 1]) return i;    // it was climbing, now it falls
  }
  return nums.length - 1;                    // it climbed all the way
}

console.log('');
console.log(findPeakSimpler([1,2,3,1]));        // 2
console.log(findPeakSimpler([1,2,1,3,5,6,4]));  // 1
console.log(findPeakSimpler([1,2,3,4,5]));      // 4

The second version is worth pausing on. “The first place it stops rising” is always a peak, because everything before it was climbing. That observation is the seed of the fast solution.

Step 3

Why we can do better than O(n)

O(n) is fine, and the problem asks for O(log n) — which sounds impossible, because the array is unsorted and a peak could be anywhere. The resolution is that you are not asked to find a particular peak, only a peak.

Timing demo
// A long climb then a long descent -- the peak is right in the
// middle, so the linear scan has to walk half the array.
const N = 4000000;
const nums = [];
for (let i = 0; i < N / 2; i++) nums.push(i);
for (let i = N / 2; i > 0; i--) nums.push(i);

function linear(a) {
  for (let i = 0; i < a.length - 1; i++) if (a[i] > a[i + 1]) return i;
  return a.length - 1;
}

function binary(a) {
  let lo = 0, hi = a.length - 1;
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (a[mid] < a[mid + 1]) lo = mid + 1;    // uphill to the right
    else hi = mid;                            // mid could be the peak
  }
  return lo;
}

  (i === 0 || a[i] > a[i - 1]) && (i === a.length - 1 || a[i] > a[i + 1]);

Step 4

The better idea — walk uphill, halving

The unlock

Look at nums[mid] and nums[mid + 1].

If nums[mid] < nums[mid + 1] — it is going up to the right — then a peak is guaranteed somewhere in [mid + 1, hi]. Discard the left half.

If nums[mid] > nums[mid + 1] — going down — then a peak is guaranteed in [lo, mid]. Discard the right half.

Why the guarantee holds

This is the whole problem, so read it slowly. Suppose nums[mid] < nums[mid + 1]. Start walking right from mid + 1. Either the values keep rising until you fall off the end — in which case the last element is a peak, because the boundary is -Infinity — or at some point they stop rising, and that point is a peak.

Either way, the right side must contain a peak. You do not know where, and it does not matter. That is enough to throw away everything to the left.

  [1, 2, 1, 3, 5, 6, 4]
   0  1  2  3  4  5  6

  lo=0 hi=6   mid=3   nums[3]=3  vs  nums[4]=5
              3 < 5  ->  climbing right  ->  a peak exists to the right
              lo = 4        (indexes 0..3 discarded)

  lo=4 hi=6   mid=5   nums[5]=6  vs  nums[6]=4
              6 > 4  ->  falling  ->  a peak exists at or before 5
              hi = 5        (index 6 discarded)

  lo=4 hi=5   mid=4   nums[4]=5  vs  nums[5]=6
              5 < 6  ->  climbing  ->  lo = 5

  lo === hi === 5  ->  stop.   index 5 is a peak (6 > 5 and 6 > 4).
Two details that make the loop safe

while (lo < hi), not <=. The loop narrows until exactly one candidate remains, and that survivor is the answer — there is no separate “did we find it?” check.

hi = mid, not mid - 1. When the values are falling, mid itself might be the peak, so it must stay in the range. And since mid < hi always holds inside the loop, hi = mid still shrinks the range — no infinite loop.

Note this is the half-open shape from the binary search page: narrow to one survivor, never compare against a target, never return early.

Step 6

Version 1 — without built-in methods

Version 1 — loops only
function findPeakManual(nums) {
  let lo = 0;
  let hi = nums.length - 1;

  // narrow until ONE candidate remains -- that survivor is the answer
  while (lo < hi) {
    const mid = lo + ((hi - lo) - ((hi - lo) % 2)) / 2;

    if (nums[mid] < nums[mid + 1]) {
      // climbing to the right: a peak must exist in [mid+1, hi]
      lo = mid + 1;
    } else {
      // falling: a peak must exist in [lo, mid] -- mid itself may be it
      hi = mid;
    }
  }

  return lo;
}

// a checker, so we can trust the answers
function isPeak(nums, i) {
  const left  = i === 0 ? -Infinity : nums[i - 1];
  const right = i === nums.length - 1 ? -Infinity : nums[i + 1];
  return nums[i] > left && nums[i] > right;
}

Step 7

Version 2 — with built-in methods

Version 2 — the interview answer
function findPeakElement(nums) {
  let lo = 0;
  let hi = nums.length - 1;

  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);

    if (nums[mid] < nums[mid + 1]) lo = mid + 1;   // uphill -> go right
    else hi = mid;                                  // downhill -> mid may be it
  }

  return lo;
}

console.log(findPeakElement([1,2,3,1]));         // 2
console.log(findPeakElement([1,2,1,3,5,6,4]));   // 5
console.log(findPeakElement([1,2,3,4,5]));       // 4
console.log(findPeakElement([5,4,3,2,1]));       // 0
console.log(findPeakElement([7]));               // 0
console.log(findPeakElement([1,2]));             // 1

Six lines, no target, no -1 return, no equality check. The loop narrows to one survivor and that survivor is correct by construction. That is a different shape of binary search from “find this value”, and it is worth recognising as its own pattern.

the same shape, other problems
// 1. Find Minimum in Rotated Sorted Array -- narrow to one survivor
function findMin(nums) {
  let lo = 0, hi = nums.length - 1;
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] > nums[hi]) lo = mid + 1;
    else hi = mid;
  }
  return nums[lo];
}
console.log('min of rotated:', findMin([4,5,6,7,0,1,2]));   // 0

// 2. First bad version -- the predicate goes false...false...true
function firstBadVersion(n, isBad) {
  let lo = 1, hi = n;
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (isBad(mid)) hi = mid;
    else lo = mid + 1;
  }
  return lo;
}
console.log('first bad:', firstBadVersion(100, v => v >= 37));   // 37

// 3. Peak in a MOUNTAIN array (guaranteed to rise then fall)
function peakIndexInMountain(nums) {
  let lo = 0, hi = nums.length - 1;
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] < nums[mid + 1]) lo = mid + 1;
    else hi = mid;
  }
  return lo;
}
console.log('mountain peak:', peakIndexInMountain([0,2,5,9,4,1]));   // 3

the 2D version, for completeness
// Peak in a matrix: greater than all four neighbours.
// Binary search on COLUMNS, taking the row maximum of each.
function findPeakGrid(mat) {
  let lo = 0, hi = mat[0].length - 1;

  while (lo <= hi) {
    const midCol = lo + Math.floor((hi - lo) / 2);

    // the largest value in this column
    let maxRow = 0;
    for (let r = 0; r < mat.length; r++) {
      if (mat[r][midCol] > mat[maxRow][midCol]) maxRow = r;
    }

    const leftBigger  = midCol > 0 && mat[maxRow][midCol - 1] > mat[maxRow][midCol];
    const rightBigger = midCol < mat[0].length - 1 &&
                        mat[maxRow][midCol + 1] > mat[maxRow][midCol];

    if (!leftBigger && !rightBigger) return [maxRow, midCol];
    if (leftBigger) hi = midCol - 1;
    else lo = midCol + 1;
  }

  return [-1, -1];
}

const grid = [[1,4],[3,2]];
console.log(findPeakGrid(grid));         // [1,0] -- value 3, beats 1 above and 2 right
// note [0,1] (value 4) is ALSO a valid peak -- any one will do

const grid2 = [[10,20,15],[21,30,14],[7,16,32]];
console.log(findPeakGrid(grid2));        // [1,1] -- value 30, beats 20/16/21/14

// O(rows * log columns). The same "one side must contain a peak"
// argument, applied to columns instead of positions.
Step 8

Complexity, in sentences

SolutionTimeSpace
Linear scanO(n)O(1)
Binary searchO(log n)O(1)
2D grid versionO(rows · log cols)O(1)

Each iteration halves the range, so O(log n) — and remarkably, the algorithm never looks at most of the array. On four million elements it inspects about twenty two of them.

That is only possible because the question asks for any peak. Finding the global maximum is provably O(n): you cannot skip an element without risking that it was the largest. Being asked for “any valid answer” rather than “the best answer” is a hint worth noticing in a problem statement.

Say this in the interview

“The array is not sorted, but binary search only needs a rule for discarding half. I compare nums[mid] with nums[mid+1]: if it is rising, a peak must exist to the right, because the values either keep rising to the end — where the boundary is −infinity — or turn over somewhere. If it is falling, the same argument puts a peak at or before mid. I narrow with lo < hi and hi = mid until one candidate remains, which is the answer. O(log n) time, O(1) space.”

Step 9

Mistakes people actually make

1. Writing hi = mid - 1

Broken — discards the peak itself
function broken(nums) {
  let lo = 0, hi = nums.length - 1;
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] < nums[mid + 1]) lo = mid + 1;
    else hi = mid - 1;                    // should be hi = mid
  }
  return lo;
}

function isPeak(a, i) {
  const l = i === 0 ? -Infinity : a[i - 1];
  const r = i === a.length - 1 ? -Infinity : a[i + 1];
  return a[i] > l && a[i] > r;
}

const a = [1,2,3,1];
console.log('returned', broken(a), 'is a peak:', isPeak(a, broken(a)));   // 2, true -- lucky

const b = [1,3,2];
console.log('returned', broken(b), 'is a peak:', isPeak(b, broken(b)));   // 0, FALSE

const c = [1,4,3,2];
console.log('returned', broken(c), 'is a peak:', isPeak(c, broken(c)));   // 0, FALSE

// On [1,3,2]: mid=1, nums[1]=3 > nums[2]=2, so it is falling and
// index 1 IS the peak -- but hi = mid - 1 = 0 discards it. The loop
// ends on index 0, which is not a peak at all.
// When the values are falling, mid ITSELF might be the peak.

2. Writing while (lo <= hi)

Broken — infinite loop
function broken(nums) {
  let lo = 0, hi = nums.length - 1;
  let guard = 0;
  while (lo <= hi) {                       // should be lo < hi
    if (++guard > 50) return 'INFINITE LOOP -- bailed out';
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] < nums[mid + 1]) lo = mid + 1;
    else hi = mid;

console.log(broken([1,2,3,1]));   // INFINITE LOOP

// When lo === hi, mid === lo === hi. If the values are falling,
// hi = mid leaves everything unchanged and the condition lo <= hi
// is still true. The half-open shape must stop AT one survivor.

3. Reading nums[mid + 1] off the end

why it is actually safe

// lo <= mid < hi. So mid + 1 <= hi <= length - 1 -- always in range.

4. Comparing with nums[mid - 1] as well

You only need one comparison. Checking both neighbours turns a two-way decision into a three-way one and forces you to handle mid === 0 as a special case — more code, more chances to be wrong, and no benefit. The single comparison against mid + 1 already determines which half to keep.

5. Assuming plateaus are allowed

Broken — equal neighbours
function findPeak(nums) {
  let lo = 0, hi = nums.length - 1;
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] < nums[mid + 1]) lo = mid + 1;
    else hi = mid;
  }
  return lo;
}

function isStrictPeak(a, i) {
  const l = i === 0 ? -Infinity : a[i - 1];
  const r = i === a.length - 1 ? -Infinity : a[i + 1];
  return a[i] > l && a[i] > r;
}

const plateau = [1, 2, 2, 2, 1];
const i = findPeak(plateau);
console.log('returned', i, 'value', plateau[i],
            'strict peak:', isStrictPeak(plateau, i));

// With equal neighbours, "which way is uphill?" has no answer, and
// the halving argument collapses -- a strict peak may exist on
// either side of a plateau. The problem guarantees
// nums[i] !== nums[i+1] precisely to rule this out. If plateaus

Step 10

Practice before you move on

  1. Write the six-line version from memory, then say the “a peak must exist to the right” argument out loud. The code is trivial; the argument is the answer.
  2. Peak Index in a Mountain Array. Same code, with the extra guarantee that the array rises then falls. Confirm nothing needs to change.
  3. Find Minimum in Rotated Sorted Array. The same narrow-to-one-survivor shape. It is in Step 7.
  4. First Bad Version. Also in Step 7 — and notice there is no array at all, only a predicate that flips once.
  5. Find a peak in a 2D grid. In Step 7. Work out why taking the row maximum of the middle column is what makes the halving argument survive in two dimensions.
What to carry forward

Binary search needs a discard rule, not a sorted array. If one comparison lets you prove “an answer definitely exists on this side”, you can halve — whatever the data looks like. And notice the second lesson hiding in the problem statement: being asked for any valid answer rather than the best one is often what makes a logarithmic solution possible at all.
