Searching & sorting · Problem 07

Custom Comparator Sorting

The most useful page in this topic, and the one where JavaScript has a genuine trap waiting: [10, 9].sort() gives [10, 9]. This is about comparators — how they work, and how to write them for real data.

Step 1

The problem

Sort things by a rule of your choosing: numerically, by a field, by several fields, ascending here and descending there.

The trap, first
console.log([10, 9, 100, 20].sort());
// [10, 100, 20, 9]   -- NOT sorted numerically

console.log([10, 9, 100, 20].sort((a, b) => a - b));
// [9, 10, 20, 100]   -- correct

console.log([1, 5, 10].sort());
// [1, 5, 10]   -- "works", which is exactly why the bug survives

console.log([1, 5, 10, 15].sort());
// [1, 10, 15, 5]   -- and now it does not
Why the default sort does this

Array.prototype.sort() with no comparator converts every element to a string and sorts those strings in code-unit order. So "10" comes before "9", because "1" is before "9" — exactly as “apple” comes before “banana”.

It is not a bug in JavaScript; it is a documented default that happens to be almost never what you want. Single-digit arrays hide it perfectly, which is why it reaches production.

GoalComparator
numbers ascending(a, b) => a - b
numbers descending(a, b) => b - a
strings ascending(a, b) => a.localeCompare(b)
by a numeric field(a, b) => a.age - b.age
by a string field(a, b) => a.name.localeCompare(b.name)
by two fields(a, b) => a.x - b.x || a.y - b.y
Step 2

Think first — what is a comparator, exactly?

A comparator is a function you hand to sort. It receives two elements and answers one question: which of these should come first?

The contract — the whole thing

compare(a, b) must return:

  • a negative number if a should come before b
  • a positive number if a should come after b
  • zero if their order does not matter

That is why a - b works: if a is smaller the result is negative, so a goes first — which is ascending. And b - a flips every sign, which is descending. There is nothing else to it.

watching the comparator get called
const nums = [3, 1, 4, 1, 5];

const sorted = [...nums].sort((a, b) => {
  const result = a - b;
  const verdict = result < 0 ? a + ' first'
                : result > 0 ? b + ' first'
                : 'tie';
  console.log('compare(' + a + ', ' + b + ') = ' + result + '   -> ' + verdict);
  return result;
});

console.log('');
console.log('sorted:', sorted);
console.log('');
console.log('Note: the engine decides WHICH pairs to compare and in');
console.log('what order. Your job is only to answer each question');
console.log('correctly and consistently.');
only the SIGN matters
const nums = [3, 1, 4, 1, 5];

// all of these sort ascending -- the magnitude is irrelevant
console.log([...nums].sort((a, b) => a - b));
console.log([...nums].sort((a, b) => (a - b) * 1000));
console.log([...nums].sort((a, b) => a < b ? -1 : a > b ? 1 : 0));
console.log([...nums].sort((a, b) => Math.sign(a - b)));

// and these all sort descending
console.log([...nums].sort((a, b) => b - a));
console.log([...nums].sort((a, b) => a > b ? -1 : a < b ? 1 : 0));

// A boolean is NOT a valid comparator: true becomes 1, false
// becomes 0 -- so it can say "after" or "tie" but never "before".
console.log('boolean comparator:', [...nums].sort((a, b) => a > b));
// may look sorted on small arrays, and is not reliable
Step 3

Why the default hurts, and where else it bites

the default sort, on everything
// numbers
console.log('numbers   :', [1, 5, 10, 50, 100].sort());
// [1, 10, 100, 5, 50]

// mixed sign
console.log('negatives :', [-1, -10, -2].sort());
// [-1, -10, -2]   -- "-1" < "-10" as strings

// booleans
console.log('booleans  :', [true, false, true].sort());
// [false, true, true]  -- alphabetical: "false" < "true". Correct by luck.

// undefined and holes go to the END, always, comparator or not
console.log('undefined :', [3, undefined, 1].sort((a, b) => a - b));
// [1, 3, undefined]

// dates: the default calls toString(), which starts with the DAY
// NAME -- so it sorts by "Fri" vs "Mon" vs "Wed". Useless.
const dates = [new Date('2024-03-01'), new Date('2023-01-15'), new Date('2024-01-02')];
console.log('dates, default   :',
  [...dates].sort().map(d => d.toISOString().slice(0, 10)));
console.log('dates, comparator:',
  [...dates].sort((a, b) => a - b).map(d => d.toISOString().slice(0, 10)));
// The default left them in their original order here, which is
// pure coincidence. a - b works because subtraction coerces a Date
// to milliseconds -- that is the idiomatic date comparator.
Two more things about sort() that surprise people

It mutates. arr.sort() reorders arr itself and returns the same array. To keep the original, sort a copy: [...arr].sort(...) or arr.toSorted(...) in newer runtimes.

undefined is special-cased. Undefined elements are moved to the end without ever being passed to your comparator. So a comparator cannot control where they go.

mutation, demonstrated
const original = [3, 1, 2];
const result = original.sort((a, b) => a - b);

console.log('original:', original);          // [1,2,3] -- changed
console.log('result  :', result);            // [1,2,3]
console.log('same object?', original === result);   // true

// the safe versions
const safe = [3, 1, 2];
const copy = [...safe].sort((a, b) => a - b);
console.log('safe   :', safe, '  copy:', copy);

if (Array.prototype.toSorted) {
  const s2 = [3, 1, 2];
  console.log('toSorted:', s2.toSorted((a, b) => a - b), ' original:', s2);
}

// A real bug this causes: sorting inside a render function or a
// getter silently reorders shared state.
const config = { levels: [3, 1, 2] };
function getSortedLevelsBad() { return config.levels.sort((a, b) => a - b); }
function getSortedLevelsGood() { return [...config.levels].sort((a, b) => a - b); }

getSortedLevelsBad();
console.log('config after the bad getter:', config.levels);   // reordered
Step 4

The better idea — compose comparators

Real sorting is almost never by one field. “By department, then by salary descending, then by name” is the normal case.

The unlock — the || chain

(a, b) => compareFirst(a, b) || compareSecond(a, b) || compareThird(a, b)

It works because a tie returns 0, which is falsy — so || moves on to the next comparison. A non-zero result is truthy and short-circuits immediately. The tie-breaking falls out of JavaScript’s own semantics.

  sort by team, then by score descending, then by name

  (a, b) =>
       a.team.localeCompare(b.team)      // different teams? done.
    || b.score - a.score                 // same team, higher score first
    || a.name.localeCompare(b.name)      // same score, alphabetical

  If the first returns 0 (a tie), || evaluates the second.
  If that returns 0 too, || evaluates the third.
The one hazard in the || chain

0 means “tie”, and || also treats NaN as falsy. So if a field is missing, a.score - b.score is NaN, the chain silently moves on, and you get a plausible-looking but arbitrary order — with no error. Guard missing fields explicitly.

The three comparator building blocks

memorise these
numbers   :  (a, b) => a - b
strings   :  (a, b) => a.localeCompare(b)
booleans  :  (a, b) => (a ? 1 : 0) - (b ? 1 : 0)     // false first
dates     :  (a, b) => a - b                          // coerces to ms

reverse anything:  (a, b) => -inner(a, b)

Why localeCompare rather than a < b for strings? Because < compares UTF-16 code units, which puts every uppercase letter before every lowercase one ("Z" before "a") and mis-orders accented characters. localeCompare gives human-expected ordering.

Step 6

Version 1 — without built-in methods

Writing a sort that accepts a comparator makes it obvious what Array.prototype.sort is actually doing with your function.

Version 1 — a stable merge sort taking a comparator
function sortWith(input, compare) {
  // default to the ascending-numbers comparator, like sort() should have
  const cmp = compare || function (a, b) { return a < b ? -1 : a > b ? 1 : 0; };

  const a = [];
  for (let i = 0; i < input.length; i++) a[i] = input[i];

  const buffer = [];
  for (let i = 0; i < a.length; i++) buffer[i] = 0;

  function sortRange(lo, hi) {
    if (hi - lo < 1) return;
    const mid = lo + ((hi - lo) - ((hi - lo) % 2)) / 2;
    sortRange(lo, mid);
    sortRange(mid + 1, hi);

    let i = lo, j = mid + 1, k = lo;

    while (i <= mid && j <= hi) {
      // <= 0 means "a comes first OR it is a tie" -- taking the LEFT
      // element on a tie is what makes this sort STABLE
      if (cmp(a[i], a[j]) <= 0) {
        buffer[k] = a[i];
        i = i + 1;
      } else {
        buffer[k] = a[j];
        j = j + 1;
      }
      k = k + 1;
    }

    while (i <= mid) { buffer[k] = a[i]; i = i + 1; k = k + 1; }
    while (j <= hi)  { buffer[k] = a[j]; j = j + 1; k = k + 1; }

    for (let x = lo; x <= hi; x++) a[x] = buffer[x];
  }

  sortRange(0, a.length - 1);
  return a;
}

console.log(sortWith([10, 9, 100, 20], (a, b) => a - b));   // [9,10,20,100]
console.log(sortWith([10, 9, 100, 20], (a, b) => b - a));   // [100,20,10,9]
console.log(sortWith(['banana', 'apple', 'cherry']));       // alphabetical

const people = [
  { n: 'ana', age: 30 }, { n: 'bo', age: 25 }, { n: 'cy', age: 30 }
];
console.log(sortWith(people, (a, b) => a.age - b.age).map(p => p.n + ':' + p.age));
// bo:25  ana:30  cy:30   -- ana before cy, their original order (stable)

console.log(sortWith([], (a, b) => a - b));                 // []
console.log(sortWith([1], (a, b) => a - b));                // [1]
comparator factories — the reusable version
// Instead of writing comparators by hand, build them.
const byNumber = (keyOf) => (a, b) => keyOf(a) - keyOf(b);
const byString = (keyOf) => (a, b) => String(keyOf(a)).localeCompare(String(keyOf(b)));
const desc     = (cmp)  => (a, b) => -cmp(a, b);
const then     = (...cmps) => (a, b) => {
  for (const c of cmps) {
    const r = c(a, b);
    if (r !== 0) return r;
  }
  return 0;
};

const players = [
  { name: 'ana',  team: 'red',  score: 30 },
  { name: 'bo',   team: 'blue', score: 30 },
  { name: 'cy',   team: 'red',  score: 45 },
  { name: 'di',   team: 'blue', score: 45 },
  { name: 'ed',   team: 'red',  score: 30 }
];

const byTeamThenScoreDescThenName = then(
  byString(p => p.team),
  desc(byNumber(p => p.score)),
  byString(p => p.name)
);

for (const p of [...players].sort(byTeamThenScoreDescThenName)) {
  console.log(p.team.padEnd(5) + String(p.score).padStart(4) + '  ' + p.name);
}

console.log('');
// and any other ordering, for free
console.log('by score only:',
  [...players].sort(byNumber(p => p.score)).map(p => p.name).join(' '));
console.log('by name desc :',
  [...players].sort(desc(byString(p => p.name))).map(p => p.name).join(' '));

// `then` uses an explicit !== 0 check rather than ||, so a NaN from
// a missing field cannot silently fall through.

the pattern that beats an expensive comparator
// If the sort key is expensive to compute, do NOT compute it inside
// the comparator -- it runs O(n log n) times. Compute it once per
// element, sort the pairs, then unwrap. (This is a Schwartzian
// transform, or "decorate-sort-undecorate".)
function expensiveKey(s) {
  // pretend this is slow
  let h = 0;
  for (let i = 0; i < s.length; i++) {
    for (let k = 0; k < 60; k++) h = (h * 31 + s.charCodeAt(i)) | 0;
  }
  return Math.abs(h) % 1000;
}

const words = [];
for (let i = 0; i < 4000; i++) words.push('word' + i);

// naive: the key is recomputed on every comparison
let t = performance.now();
const naive = [...words].sort((a, b) => expensiveKey(a) - expensiveKey(b));
const naiveMs = performance.now() - t;

// decorated: one key per element, then sort the pairs
t = performance.now();
const decorated = words
  .map(w => ({ w, k: expensiveKey(w) }))
  .sort((a, b) => a.k - b.k)
  .map(pair => pair.w);
const decoratedMs = performance.now() - t;

console.log('key inside the comparator : ' + naiveMs.toFixed(1) + ' ms');
console.log('key computed once each    : ' + decoratedMs.toFixed(1) + ' ms');
console.log('same result:', naive.length === decorated.length &&
            expensiveKey(naive[0]) === expensiveKey(decorated[0]));
console.log('');
console.log('n elements need n keys, not 2 x n log n keys.');
Step 8

Complexity, in sentences

AspectCost
ComparisonsO(n log n)
Your comparator runsO(n log n) times
Key computed inside the comparatorO(n log n) computations
Key computed once per elementO(n) computations + O(n log n) comparisons

The comparator is called about n log n times. For 10,000 elements that is roughly 130,000 calls. Anything expensive inside it — a regex, a date parse, a property lookup chain, a toLowerCase() — is paid 130,000 times instead of 10,000. That is the single most useful performance fact on this page.

Array.prototype.sort has been required to be stable since ES2019, so equal elements keep their relative order. Before that it was implementation-defined, and older code sometimes adds an index tie-breaker to force stability. You no longer need to.

Say this in the interview

“sort() with no comparator stringifies the elements, so [10, 9] stays [10, 9] — numbers always need (a, b) => a - b. A comparator returns negative, positive or zero for before, after or tie, and multi-field sorts chain with || because a tie returns 0, which is falsy. It mutates, so I sort a copy. And if the sort key is expensive I compute it once per element rather than inside the comparator, which runs O(n log n) times.”

Step 9

Mistakes people actually make

1. No comparator on numbers

Step 1. It is the most common JavaScript sorting bug there is, and single-digit test data hides it completely.

2. Returning a boolean

Broken — booleans are not comparators
const nums = [5, 3, 9, 1, 7, 2, 8, 6, 4, 10, 12, 11];

console.log('boolean :', [...nums].sort((a, b) => a > b));
console.log('correct :', [...nums].sort((a, b) => a - b));

// `a > b` gives true or false, which coerce to 1 and 0.
// So the comparator can say "after" (1) or "tie" (0) -- and never
// "before" (-1). The engine has no way to move an element left.
console.log('');
console.log('true  becomes', Number(true));    // 1
console.log('false becomes', Number(false));   // 0
console.log('there is no -1 anywhere in that range');

3. An inconsistent comparator

Broken — the comparator contradicts itself
const nums = [3, 1, 4, 1, 5, 9, 2, 6];

// A random comparator: the answer to compare(a,b) changes between
// calls, so no consistent order exists.
console.log('random  :', [...nums].sort(() => Math.random() - 0.5));
console.log('random  :', [...nums].sort(() => Math.random() - 0.5));

// People use this to "shuffle". It is not a shuffle: the result is
// biased and depends on the engine's sort algorithm.
const counts = new Map();
for (let trial = 0; trial < 20000; trial++) {
  const shuffled = [1, 2, 3].sort(() => Math.random() - 0.5);
  const key = shuffled.join('');
  counts.set(key, (counts.get(key) || 0) + 1);
}
console.log('');
console.log('20000 "shuffles" of [1,2,3] -- a fair shuffle would give');
console.log('about 3333 of each of the 6 orderings:');
for (const [k, v] of [...counts].sort()) console.log('  ' + k + ': ' + v);

console.log('');
console.log('For a real shuffle use Fisher-Yates:');
function shuffle(a) {
  const arr = [...a];
  for (let i = arr.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [arr[i], arr[j]] = [arr[j], arr[i]];
  }
  return arr;
}
const fair = new Map();
for (let trial = 0; trial < 20000; trial++) {
  const k = shuffle([1,2,3]).join('');
  fair.set(k, (fair.get(k) || 0) + 1);
}
for (const [k, v] of [...fair].sort()) console.log('  ' + k + ': ' + v);

4. Sorting the original when you meant a copy

Broken — mutating shared state
const state = { items: [3, 1, 2], name: 'shared' };

// looks read-only, is not
function displayOrder(s) {
  return s.items.sort((a, b) => a - b);
}

console.log('before:', [...state.items]);
displayOrder(state);
console.log('after :', state.items);        // reordered

// A worse version: sort() returns the SAME array, so a caller
// holding both references sees them both change.
const view = displayOrder(state);
view.push(99);
console.log('state.items now:', state.items);   // the 99 is in here too

// The fix, every time:
function displayOrderSafe(s) {
  return [...s.items].sort((a, b) => a - b);
}

6. Computing the key inside the comparator

Shown in Step 7. It is correct and it does n log n key computations instead of n. On a date-parse or a regex that is the difference between instant and noticeable.

Step 10

Practice before you move on

  1. Recite the comparator contract — negative, positive, zero — and then write the four building blocks from memory: numbers, strings, booleans, reverse.
  2. Sort an array of objects by three fields, one of them descending, using the || chain. Then do it again with the then(...) factory from Step 6 and say which you would ship.
  3. Sort by a fixed priority list. In Step 7 — build the rank Map from an array so the order is data rather than code.
  4. Write Fisher–Yates from memory, and be ready to explain why sort(() => Math.random() - 0.5) is not a shuffle.
  5. Sort, filter and paginate an array of records in one function. That is a Tier 4 problem in this collection and it is mostly this page plus slice.
What to carry forward

Three habits. Always pass a comparator — the default is a string sort and will eventually bite you. Always sort a copy unless you have decided to mutate. And compute expensive keys once per element, not once per comparison. Of everything in this whole collection, these three are the ones you will use most often in real code.
