Object & data shaping · Problem 06

Nested Tree → Flat List

The same trip backwards, and easier — until you are asked which order the list should be in. Depth-first and breadth-first give completely different answers, and one of them is what a collapsible tree UI needs.

Why you would do this

Saving to a database. A tree has to become rows with a parent_id.

Rendering a virtualised list. A collapsible tree of ten thousand nodes is drawn as a flat list of visible rows, each with a depth for indentation. React Window, TanStack Virtual and every large file explorer work this way.

Searching. A flat list is trivial to filter; a tree is not.

// DEPTH FIRST, pre-order: a node, then all of its descendants
function preOrder(nodes) {
  const out = [];
  for (const n of nodes) { out.push(n.id); out.push(...preOrder(n.children)); }
  return out;
}

// DEPTH FIRST, post-order: descendants first, then the node
function postOrder(nodes) {
  const out = [];
  for (const n of nodes) { out.push(...postOrder(n.children)); out.push(n.id); }
  return out;
}

// BREADTH FIRST: level by level
function breadthFirst(nodes) {
  const out = [];
  const queue = [...nodes];
  while (queue.length) {
    const n = queue.shift();
    out.push(n.id);
    queue.push(...n.children);
  }
  return out;
}

Step 3

Why the spread version costs, and where it actually breaks

out.push(...treeToList(children)) builds a new array at every level and copies it upward. A node at depth d is copied d times, so the cost is O(n · d) — and the honest measurement below shows that on a shallow tree that barely matters, while on a deep one it matters a lot and on a wide one it throws outright.

Timing demo — spread-and-merge versus one accumulator
function buildTree(depth, width, nextId = { v: 1 }) {
  const out = [];
  for (let i = 0; i < width; i++) {
    const id = nextId.v++;
    out.push({ id, children: depth > 1 ? buildTree(depth - 1, width, nextId) : [] });
  }
  return out;
}

// (a) a new array per level, spread upward
function withSpread(nodes, parentId = null) {
  const out = [];
  for (const { children = [], ...node } of nodes) {
    out.push({ ...node, parentId });
    out.push(...withSpread(children, node.id));
  }
  return out;
}

// (b) one shared accumulator
function withAccumulator(nodes) {
  const out = [];
  (function walk(list, parentId, depth) {
    for (const node of list) {
      const { children = [], ...rest } = node;
      out.push({ ...rest, parentId, depth });
      walk(children, node.id, depth + 1);
    }
  })(nodes, null, 0);
  return out;
}

Step 4

The better idea — carry the context down

  walk(nodes, parentId, depth, path):

      for each node:
          split off `children`, keep the rest

          out.push({
              ...rest,
              parentId,           <-- from the caller
              depth,              <-- from the caller
              path: [...path, node.id],
          })

          walk(children, node.id, depth + 1, [...path, node.id])


  Three things travel DOWN the recursion, and each answers a
  question the flat list needs to answer:

      parentId  ->  how to rebuild the tree
      depth     ->  how far to indent the row
      path      ->  breadcrumbs, and "is X an ancestor of Y"

  And one thing travels UP: nothing. The accumulator is shared,
  so the return value is unused. That is what makes it O(n).
The extra fields that make it useful

depth for indentation. parentId for reconstruction. path for breadcrumbs. hasChildren so a renderer can draw a disclosure triangle without having the children. index to preserve sibling order across a database round trip.

The last one matters more than it looks: if the tree order is meaningful, it must survive being flattened, stored and rebuilt — and the only place to put it is an explicit column.

a round trip, and what it loses without an index
function treeToList(nodes) {
  const out = [];
  (function walk(list, parentId, depth) {
    list.forEach((node, index) => {
      const { children = [], ...rest } = node;
      out.push({ ...rest, parentId, depth, index, hasChildren: children.length > 0 });
      walk(children, node.id, depth + 1);
    });
  })(nodes, null, 0);
  return out;
}

function listToTree(rows, { sortByIndex }) {
  const byId = new Map();
  for (const row of rows) {
    const { parentId, depth, index, hasChildren, ...rest } = row;
    byId.set(row.id, { ...rest, children: [] });
  }
  const roots = [];
  for (const row of rows) {
    const node = byId.get(row.id);
    const parent = byId.get(row.parentId);
    (parent ? parent.children : roots).push(node);
  }
  if (sortByIndex) {
    const indexOf = new Map(rows.map((r) => [r.id, r.index]));
    (function sort(nodes) {
      nodes.sort((a, b) => indexOf.get(a.id) - indexOf.get(b.id));
      for (const n of nodes) sort(n.children);
    })(roots);
  }
  return roots;
}

// Pre-order with a stack: push children in REVERSE so they pop in
// the original order.
function treeToListIterative(nodes) {
  const out = [];
  const stack = [];

  for (let i = nodes.length - 1; i >= 0; i--) {
    stack.push({ node: nodes[i], parentId: null, depth: 0, index: i });
  }

  while (stack.length) {
    const { node, parentId, depth, index } = stack.pop();
    const children = node.children || [];
    const { children: _, ...rest } = node;

    out.push({ ...rest, parentId, depth, index });

    for (let i = children.length - 1; i >= 0; i--) {
      stack.push({ node: children[i], parentId: node.id, depth: depth + 1, index: i });
    }
  }

  return out;
}

function treeToListRecursive(nodes) {
  const out = [];
  (function walk(list, parentId, depth) {
    list.forEach((node, index) => {
      const { children = [], ...rest } = node;
      out.push({ ...rest, parentId, depth, index });
      walk(children, node.id, depth + 1);
    });
  })(nodes, null, 0);
  return out;
}

Version 1b — breadth first, with a proper queue
// The obvious BFS uses queue.shift(), which is O(n) per call --
// so the whole traversal is O(n^2).
function bfsShift(nodes) {
  const out = [];
  const queue = nodes.map((n) => ({ node: n, depth: 0 }));
  while (queue.length) {
    const { node, depth } = queue.shift();          // O(n)
    out.push({ id: node.id, depth });
    for (const c of node.children || []) queue.push({ node: c, depth: depth + 1 });
  }
  return out;
}

// A head index instead of shifting: O(1) per dequeue.
function bfsIndex(nodes) {
  const out = [];
  const queue = nodes.map((n) => ({ node: n, depth: 0 }));
  let head = 0;
  while (head < queue.length) {
    const { node, depth } = queue[head++];
    out.push({ id: node.id, depth });
    for (const c of node.children || []) queue.push({ node: c, depth: depth + 1 });
  }
  return out;
}

// level by level, which is often what you actually want
function byLevel(nodes) {
  const levels = [];
  let current = nodes;
  while (current.length) {
    levels.push(current.map((n) => n.id));
    current = current.flatMap((n) => n.children || []);
  }
  return levels;
}

function treeToList(nodes, options = {}) {
  const {
    childrenKey = 'children',
    idKey = 'id',
    order = 'pre',            // 'pre' | 'post' | 'breadth'
    keepChildren = false,
    maxDepth = Infinity,
    filter = null,            // (node, depth) => boolean; false prunes the subtree
  } = options;

  const out = [];
  const seen = new Set();     // guards a cyclic tree

  function makeRow(node, parentId, depth, index, path) {
    const children = node[childrenKey] || [];
    const row = keepChildren ? { ...node } : (() => {
      const copy = { ...node };
      delete copy[childrenKey];
      return copy;
    })();
    return {
      ...row,
      parentId,
      depth,
      index,
      path: path.join('/'),
      hasChildren: children.length > 0,
      childCount: children.length,
    };
  }

  if (order === 'breadth') {
    const queue = nodes.map((n, i) =>
      ({ node: n, parentId: null, depth: 0, index: i, path: [n[idKey]] }));
    let head = 0;
    while (head < queue.length) {
      const item = queue[head++];
      if (seen.has(item.node)) continue;
      seen.add(item.node);
      if (item.depth > maxDepth) continue;
      if (filter && !filter(item.node, item.depth)) continue;

      out.push(makeRow(item.node, item.parentId, item.depth, item.index, item.path));

      const children = item.node[childrenKey] || [];
      children.forEach((c, i) => queue.push({
        node: c, parentId: item.node[idKey], depth: item.depth + 1,
        index: i, path: [...item.path, c[idKey]],
      }));
    }
    return out;
  }

  (function walk(list, parentId, depth, path) {
    if (depth > maxDepth) return;
    list.forEach((node, index) => {
      if (seen.has(node)) return;
      seen.add(node);
      if (filter && !filter(node, depth)) return;

      const nextPath = [...path, node[idKey]];
      const row = makeRow(node, parentId, depth, index, nextPath);

      if (order === 'pre') out.push(row);
      walk(node[childrenKey] || [], node[idKey], depth + 1, nextPath);
      if (order === 'post') out.push(row);
    });
  })(nodes, null, 0, []);

  return out;
}

// A tree UI never flattens the whole tree. It flattens the VISIBLE
// rows, given a set of expanded ids -- and re-flattens on every
// expand or collapse.
function visibleRows(nodes, expanded, depth = 0, parentId = null, out = []) {
  for (const node of nodes) {
    const children = node.children || [];
    const isExpanded = expanded.has(node.id);

    out.push({
      id: node.id,
      name: node.name,
      depth,
      parentId,
      hasChildren: children.length > 0,
      isExpanded,

the generator version, and lazy search
// A generator gives you the rows one at a time, so you can stop
// early -- which matters for "find the first matching node".
function* walkTree(nodes, depth = 0, parentId = null, path = []) {
  for (const [index, node] of nodes.entries()) {
    const nextPath = [...path, node.id];
    yield { node, depth, parentId, index, path: nextPath };
    yield* walkTree(node.children || [], depth + 1, node.id, nextPath);
  }
}

const build = (depth, width, id = { v: 1 }) => {
  const out = [];
  for (let i = 0; i < width; i++) {
    const myId = id.v++;
    out.push({ id: myId, name: 'n' + myId,
               children: depth > 1 ? build(depth - 1, width, id) : [] });
  }
  return out;
};

// eager: flatten everything, then find
function eagerFind(nodes, predicate) {
  const rows = [];
  (function w(list, depth, parentId) {
    for (const n of list) { rows.push({ node: n, depth, parentId }); w(n.children, depth + 1, n.id); }
  })(nodes, 0, null);
  return { found: rows.find((r) => predicate(r.node)), visited: rows.length };
}

// lazy: stop at the first match
function lazyFind(nodes, predicate) {
  let visited = 0;
  for (const entry of walkTree(nodes)) {
    visited++;
    if (predicate(entry.node)) return { found: entry, visited };
  }
  return { found: null, visited };
}

Step 8

Complexity, in sentences

ApproachTimeSpace
recursive, one accumulatorO(n)O(n) output, O(d) stack
recursive, spread per levelO(n · d)O(n · d) allocated
iterative with a stackO(n)O(width) heap
BFS with queue.shift()O(n2)O(n)
BFS with a head indexO(n)O(n)
generator, stopping at kO(k)O(d)

Every node is visited once and pushed once, so the accumulator version is O(n). Two rows are traps: spreading per level re-copies each row once per level above it, and queue.shift() is O(n) per call because it re-indexes the array.

The stack version's space is the interesting one: it holds the current frontier, which for a deep narrow tree is tiny and for a wide shallow tree is the whole width. The recursive version's stack is the opposite — O(depth), fine for wide trees and fatal for deep ones. Pick based on the shape you expect.

Say this in the interview

“One recursion with a shared accumulator, carrying parentId and depth down. I push a row for each node before recursing, which gives pre-order — a parent immediately above its children, which is both what an indented list needs and what a foreign-key insert needs. Post-order is the same code with the push moved after the recursion, and that is what you want for deletes. I use a shared output array rather than spreading a returned array per level, and if the tree could be pathologically deep I would use an explicit stack, pushing children in reverse so they pop in order. For a tree UI you would not flatten the whole tree at all — only the visible rows, given the set of expanded ids.”

function flattenAll(nodes, out = [], depth = 0, path = []) {
  for (const n of nodes) {
    const p = [...path, n.id];
    out.push({ id: n.id, depth, path: p, hasChildren: n.children.length > 0 });
    flattenAll(n.children, out, depth + 1, p);

}
function visibleFromAll(nodes, expanded) {
  const all = flattenAll(nodes);
  return all.filter((r) => r.path.slice(0, -1).every((id) => expanded.has(id)));

}

Practice before you move on

  1. Write the five-line version from memory, then say which order it produces and why that is the right default.
  2. Convert it to post-order by moving one line, and say when you would want that.
  3. Write the iterative stack version and explain the reversed push.

What to carry forward

Carry the context down, accumulate into one array, and choose the order deliberately. Pre-order puts a parent above its children, which is what indentation and foreign keys both want; post-order handles children first, which is what deletes and rolled-up totals want. And the biggest practical win on this page is not an algorithm: it is not flattening the parts of the tree nobody is looking at.
