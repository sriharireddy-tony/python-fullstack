Hash map · Problem 02

Subarray With Given Sum

The companion to Subarray Sum Equals K. Here the numbers are all positive, and that single guarantee is worth an entire algorithm: it makes the running sum monotonic, which is exactly the property a sliding window needs.

Step 1

The problem

Given an array of positive integers and a target, find a contiguous subarray that sums to exactly the target. Return its start and end indexes, or an indication that none exists.

InputtargetAnswer
[1, 4, 20, 3, 10, 5]33indexes 2–4 → [20, 3, 10]
[1, 4, 0, 0, 3, 10, 5]7indexes 1–4 → [4, 0, 0, 3]
[1, 4]0none
[5]5indexes 0–0
[2, 3, 4]100none
The guarantee is the algorithm

“All positive” means the running sum of a window only grows when you extend it and only shrinks when you contract it. That is monotonicity, and it is what tells you which pointer to move: too small, extend on the right; too big, shrink on the left. Without it there is no rule, and the window is useless.

Zeros are usually allowed and are harmless — they neither grow nor shrink the sum, so the monotonicity is non-strict, which is enough. Negatives are not allowed, and if they were, you would need the prefix-sum-plus-map solution from the arrays topic instead.

Step 2

Think first — the obvious answer

Version 0 — every subarray
function findSubarrayBrute(nums, target) {
  for (let start = 0; start < nums.length; start++) {
    let sum = 0;

    for (let end = start; end < nums.length; end++) {
      sum += nums[end];

      if (sum === target) return { from: start, to: end, values: nums.slice(start, end + 1) };
      if (sum > target) break;      // positives only: it can only grow from here
    }
  }

  return null;
}

console.log(findSubarrayBrute([1, 4, 20, 3, 10, 5], 33));      // 2..4
console.log(findSubarrayBrute([1, 4, 0, 0, 3, 10, 5], 7));     // 1..4
console.log(findSubarrayBrute([1, 4], 0));                     // null
console.log(findSubarrayBrute([5], 5));                        // 0..0
console.log(findSubarrayBrute([2, 3, 4], 100));                // null

Note the break. It is only legal because all the numbers are positive: once the sum overshoots, extending further can never bring it back down. That early exit is the same insight as the real solution, applied timidly.

Step 3

Why it is slow

Even with the break, the worst case is O(n²): an array of small numbers with a large target, where each start walks a long way before overshooting.

Timing demo
// The worst case: NO subarray matches, and the target is larger than
// the whole array's total -- so the `break` never fires and every
// start position walks all the way to the end.
const N = 12000;
const nums = new Array(N).fill(2);
const target = 2 * N + 1;         // impossible: bigger than the total

function brute(a, t) {
  for (let s = 0; s < a.length; s++) {
    let sum = 0;
    for (let e = s; e < a.length; e++) {
      sum += a[e];
      if (sum === t) return [s, e];
      if (sum > t) break;
    }
  }
  return null;
}

function window(a, t) {
  let left = 0, sum = 0;
  for (let right = 0; right < a.length; right++) {
    sum += a[right];
    while (sum > t && left <= right) { sum -= a[left]; left++; }
    if (sum === t && left <= right) return [left, right];
  }
  return null;
}

let x = performance.now();
const p = brute(nums, target);
const bruteMs = performance.now() - x;

x = performance.now();
const q = window(nums, target);
const fastMs = performance.now() - x;

console.log('every subarray :', JSON.stringify(p), 'in', bruteMs.toFixed(1) + ' ms');
console.log('sliding window :', JSON.stringify(q), 'in', fastMs.toFixed(2) + ' ms');
console.log('same answer:', JSON.stringify(p) === JSON.stringify(q));
console.log('speed-up:', Math.round(bruteMs / Math.max(fastMs, 0.01)) + 'x');
Step 4

The better idea — one window, two rules

The brute force throws the window away and rebuilds it from the next position. But when it overshoots, it already knows something useful: the current window is too big. The fix is not to start over — it is to make the window smaller from the left.

The unlock

Keep one window and its running sum.

  • Sum too small → extend on the right. (Only adding can help.)
  • Sum too big → shrink on the left. (Only removing can help.)
  • Sum exact → you have the answer.

Each rule is forced, and that is only true because the numbers are positive. Spell out why:

  sum is too SMALL:
     shrinking would remove a positive number, making it smaller
     still -- strictly worse. So extend.

  sum is too BIG:
     extending would add a positive number, making it bigger still
     -- strictly worse. So shrink.

  With a negative number in the array, BOTH of those arguments
  collapse: adding could shrink the sum, removing could grow it.
  There is no forced move, and the window is not applicable.

Both pointers only ever move forward, so together they cross the array once: O(n).

The guard that matters when the target is 0

The shrink loop must stop before left passes right, or the window becomes empty and its sum is 0 — which then “matches” a target of 0 at every position. Writing while (sum > target && left <= right) and checking left <= right before reporting a match keeps the window non-empty.

Step 5

Dry run — trace it by hand

nums = [1, 4, 20, 3, 10, 5], target = 33.

left = 0   sum = 0

right=0   add 1     sum = 1     1 < 33, keep growing
right=1   add 4     sum = 5     5 < 33
right=2   add 20    sum = 25    25 < 33
right=3   add 3     sum = 28    28 < 33
right=4   add 10    sum = 38    38 > 33  ->  shrink
            remove nums[0] = 1   sum = 37   left = 1   still > 33
            remove nums[1] = 4   sum = 33   left = 2   EXACT

answer: indexes 2..4  ->  [20, 3, 10]

Watch the shrink at right=4: it removed two elements before landing exactly on the target. The brute force would have restarted from index 1 and re-added 4, 20, 3, 10 from scratch.

Now a case with no answer, nums = [2, 3, 4], target = 100:

right=0   sum = 2    < 100
right=1   sum = 5    < 100
right=2   sum = 9    < 100
end of array, never reached 100  ->  null

Note the window never shrank at all -- with a target larger than
the total, the sum is always too small and the right pointer just
runs off the end.

Step 6

Version 1 — without built-in methods

Version 1 — sliding window, loops only
function findSubarrayManual(nums, target) {
  let left = 0;
  let sum = 0;

  for (let right = 0; right < nums.length; right++) {
    sum = sum + nums[right];          // grow on the right

    // too big? shrink from the left until it is not
    while (sum > target && left <= right) {
      sum = sum - nums[left];
      left = left + 1;
    }

    // left <= right keeps the window non-empty, which matters when
    // target is 0 -- an empty window sums to 0 and would "match"
    if (sum === target && left <= right) {
      return [left, right];
    }
  }

  return [-1, -1];
}

console.log(findSubarrayManual([1, 4, 20, 3, 10, 5], 33));    // [2, 4]
console.log(findSubarrayManual([1, 4, 0, 0, 3, 10, 5], 7));   // [1, 4]
console.log(findSubarrayManual([5], 5));                      // [0, 0]
console.log(findSubarrayManual([1, 4], 0));                   // [-1, -1]
console.log(findSubarrayManual([2, 3, 4], 100));              // [-1, -1]
console.log(findSubarrayManual([], 5));                       // [-1, -1]
console.log(findSubarrayManual([1, 2, 3], 6));                // [0, 2]
console.log(findSubarrayManual([10, 2, 3], 5));               // [1, 2]
variation — count every matching subarray
// How MANY windows sum to the target? Same window, but we must not
// stop at the first match -- we record it and then shrink past it.
function countSubarrays(nums, target) {
  let left = 0, sum = 0, count = 0;

  for (let right = 0; right < nums.length; right++) {
    sum += nums[right];

    while (sum > target && left <= right) {
      sum -= nums[left];
      left++;
    }

    if (sum === target && left <= right) count++;
  }

  return count;
}

console.log(countSubarrays([1, 2, 3], 3));      // 2  -> [1,2] and [3]
console.log(countSubarrays([1, 1, 1], 2));      // 2  -> [1,1] twice
console.log(countSubarrays([5, 5, 5], 5));      // 3
console.log(countSubarrays([1, 2, 3], 100));    // 0

// Careful: this counts at most ONE window per right endpoint, which
// is correct here because with strictly positive numbers there is at
// most one window ending at each position with a given sum. Add a
// zero to the array and that stops being true -- [1,0,2] with target
// 3 has both [1,0,2] and, if you shrink, nothing else. Try it.
Step 7

Version 2 — with built-in methods

Version 2 — the interview answer
function subarrayWithSum(nums, target) {
  let left = 0;
  let sum = 0;

  for (let right = 0; right < nums.length; right++) {
    sum += nums[right];

    while (sum > target && left <= right) sum -= nums[left++];

    if (sum === target && left <= right) {
      return { from: left, to: right, values: nums.slice(left, right + 1) };
    }
  }

  return null;
}

console.log(subarrayWithSum([1, 4, 20, 3, 10, 5], 33));    // 2..4
console.log(subarrayWithSum([1, 4, 0, 0, 3, 10, 5], 7));   // 1..4
console.log(subarrayWithSum([1, 2, 3, 7, 5], 12));         // 1..3
console.log(subarrayWithSum([2, 3, 4], 100));              // null
the prefix-sum version — works with negatives too
// If the guarantee "all positive" is removed, the window breaks and
// you need the prefix-sum map from the arrays topic.
function subarrayAnySign(nums, target) {
  const firstSeen = new Map([[0, -1]]);   // running sum -> earliest index
  let running = 0;

  for (let i = 0; i < nums.length; i++) {
    running += nums[i];

    if (firstSeen.has(running - target)) {
      const start = firstSeen.get(running - target) + 1;
      return { from: start, to: i, values: nums.slice(start, i + 1) };
    }

    if (!firstSeen.has(running)) firstSeen.set(running, i);
  }

  return null;
}

console.log(subarrayAnySign([1, 4, 20, 3, 10, 5], 33));   // 2..4  same answer
console.log(subarrayAnySign([10, -5, 5], 5));             // 0..2  -- window fails here
console.log(subarrayAnySign([1, -1, 5], 5));              // 0..2
console.log(subarrayAnySign([3, 4, -7, 1, 2], 0));        // 0..2

// And watch the window get it wrong on the same input:
function windowVersion(a, t) {
  let l = 0, sum = 0;
  for (let r = 0; r < a.length; r++) {
    sum += a[r];
    while (sum > t && l <= r) sum -= a[l++];
    if (sum === t && l <= r) return [l, r];
  }
  return null;
}
console.log('window on [10,-5,5] target 5:', windowVersion([10, -5, 5], 5));
// null -- it threw the 10 away and never recovered
Which one to write

Read the constraints. “Positive integers” is an invitation to use the window: O(n) time, O(1) space, no map. No such guarantee means prefix sums plus a map: O(n) time, O(n) space. Naming both and explaining the condition that separates them is a much stronger answer than producing either one on its own.

Step 8

Complexity, in sentences

SolutionTimeSpaceNegatives?
Every subarrayO(n²)O(1)yes
Sliding windowO(n)O(1)no
Prefix sums + mapO(n)O(n)yes

Why the window is O(n). The while inside the for looks quadratic but is not: it only advances left, and left travels 0 to n once across the whole run. Total moves: at most 2n.

The window is the better solution when it applies — same time, constant space instead of linear. That is the reward for reading the constraint.

Say this in the interview

“Because all the values are positive, the window sum is monotonic: extending only increases it, shrinking only decreases it. So when the sum is below the target I extend right, and when it is above I shrink from the left — each move is forced. Both pointers only go forward, so O(n) time and O(1) space. If negatives were allowed, that monotonicity is gone and I would use prefix sums with a hash map instead.”

Step 9

Mistakes people actually make

1. Using the window when negatives are possible

Demonstrated in Step 7. The window discards elements it will need again. This is the single most important thing to get right about this problem, and it is a reading mistake, not a coding one.

2. Shrinking with >= instead of >

Broken — shrinks past the answer
function broken(nums, target) {
  let left = 0, sum = 0;
  for (let right = 0; right < nums.length; right++) {
    sum += nums[right];
    while (sum >= target && left <= right) {    // >= -- bug
      sum -= nums[left];
      left++;
    }
    if (sum === target && left <= right) return [left, right];
  }
  return null;
}

console.log(broken([1, 4, 20, 3, 10, 5], 33));   // null  WRONG, should be [2,4]
console.log(broken([1, 2, 3], 3));               // null  WRONG, should be [0,1]

// The moment the sum REACHES the target, the loop removes an element
// and destroys it. Shrink only while the sum is strictly greater.

3. Forgetting the non-empty guard when the target is 0

Broken — the empty window matches
function broken(nums, target) {
  let left = 0, sum = 0;
  for (let right = 0; right < nums.length; right++) {
    sum += nums[right];
    while (sum > target) { sum -= nums[left]; left++; }   // no left <= right
    if (sum === target) return [left, right];             // no guard either
  }
  return null;
}

console.log(broken([1, 4, 20], 33));   // null  fine
console.log(broken([1, 4], 0));        // [1, 0]  WRONG -- left > right, empty window

// With target 0, the shrink loop empties the window (sum becomes 0)
// and then 0 === 0 reports a match spanning nothing.
// Guard with left <= right in both places.

4. Not resetting the sum in the brute force

let sum = 0 must be inside the outer loop. Declared outside, it carries over from the previous start position and every answer is nonsense. The same slip appears in Maximum Subarray’s quadratic version.

5. Returning the values but not the indexes (or vice versa)

Decide which the question wants. Returning [20, 3, 10] when it asked for [2, 4] is a full mark lost for a one-line difference. And note that many versions of this problem use 1-based indexes — read the examples in the statement, not just the prose.

Step 10

Practice before you move on

  1. Say the monotonicity argument out loud. Why is each pointer move forced? What breaks if a negative appears? That is the whole interview.
  2. Shortest subarray with sum at least the target. Same window, but you record the length while the sum is at or above the target and keep shrinking. It is the “shortest” shape from Minimum Window Substring.
  3. Longest subarray with sum at most the target. The other direction: shrink while the sum is too big, record the length afterwards.
  4. Subarray product less than K. Products of positive numbers are monotonic too, so the window applies. Watch for values of 1, and for a K of 0 or 1.
  5. Redo it with negatives allowed. Write the prefix-sum version from memory, then test both on [10, -5, 5] with target 5 and watch one of them fail.
What to carry forward

A sliding window needs monotonicity. Before you write one, ask: does growing the window always move the quantity in one direction? Sums of positives, counts of distinct characters, products of positives — yes. Sums with negatives, or any quantity that can go both ways — no, and you need a different tool. Getting this check into your reflexes prevents the most common wrong answer in the whole sliding-window family.
