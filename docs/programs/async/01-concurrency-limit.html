Async patterns · Problem 01

Run N Promises With a Concurrency Limit

The most-asked async interview question, and the one where Promise.all is the wrong answer. You need at most k requests in flight, and the results still in input order — which is the worker-pool pattern in about fifteen lines.

Step 1

The problem

You have 200 URLs to fetch. Two obvious approaches, both wrong.

ApproachIn flightTime for 200 × 100 msProblem
for...of with await1~20 sneedlessly slow
Promise.all(map)200~100 msrate limits, socket exhaustion, memory
a pool of kk~200/k × 100 ms—
Why the middle row is a real problem, not a theoretical one

Browsers cap concurrent connections per host (roughly six). Node's default agent has its own pool. An API returns 429 and starts rejecting. A database runs out of connections. And every in-flight response body sits in memory at once.

“All at once” is not concurrency, it is a denial-of-service attack on your own dependencies.

Step 4

The better idea — k workers sharing a cursor

  Do not think "run k at a time". Think:

      k WORKERS, all pulling from one shared queue,
      each taking the next item as soon as it is free.

  items   [ 0  1  2  3  4  5  6  7  8 ]
            ^
          next = 0        one shared cursor

  start 3 workers. Each loops:

      while next < items.length:
          i = next++              <-- claim an index
          results[i] = await fn(items[i])

  worker A takes 0, B takes 1, C takes 2      next = 3
  B finishes first -> takes 3                 next = 4
  C finishes       -> takes 4                 next = 5
  A finishes       -> takes 5                 next = 6
  ...
  when next reaches the end, each worker's loop exits and its
  promise resolves. Promise.all over the k worker promises means
  "everything is done".

  Concurrency is EXACTLY k, because there are exactly k loops and
  each is inside at most one await at a time.
Why i = next++ is safe

JavaScript is single-threaded, so next++ cannot be interleaved — there is no race. Each worker claims a unique index. In a language with real threads this would need a lock; here the event loop is the lock.

Write the index into results[i], never results.push(). Push gives you completion order; the caller almost always wants input order.

1b — the "executing set" version
// Start each task in turn; when the set of in-flight promises hits
// the limit, race them and wait for one to finish.
async function limitedRace(items, limit, fn) {
  const results = new Array(items.length);
  const executing = new Set();

  for (let i = 0; i < items.length; i++) {
    const p = Promise.resolve()
      .then(() => fn(items[i], i))
      .then((value) => { results[i] = value; });

    // remove itself from the set when it settles
    const tracked = p.then(() => executing.delete(tracked));
    executing.add(tracked);

    if (executing.size >= limit) await Promise.race(executing);
  }

  await Promise.all(executing);
  return results;
}

1c — a reusable limiter, like p-limit
// Instead of a function over a list, a limiter you wrap each call
// in. This is the shape a real library exposes, because the calls
// may come from anywhere, at any time.
function createLimiter(concurrency) {
  let active = 0;
  const queue = [];

  function next() {
    if (active >= concurrency || queue.length === 0) return;
    active++;
    const { fn, resolve, reject } = queue.shift();
    Promise.resolve()
      .then(fn)
      .then(resolve, reject)
      .finally(() => { active--; next(); });
  }

  function limit(fn) {
    return new Promise((resolve, reject) => {
      queue.push({ fn, resolve, reject });
      next();
    });
  }

  limit.activeCount = () => active;
  limit.pendingCount = () => queue.length;
  return limit;
}

// A: fail fast -- the first rejection rejects the whole thing
async function poolAll(items, limit, fn) {
  const results = new Array(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length) {
      const i = next++;

  return results;

// B: settle all -- never rejects, reports per item
async function poolAllSettled(items, limit, fn) {
  const results = new Array(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length) {
      const i = next++;
      try {
        results[i] = { status: 'fulfilled', value: await fn(items[i], i) };
      } catch (reason) {
        results[i] = { status: 'rejected', reason };
      }
    }
  }
  await Promise.all(Array.from({ length: limit }, worker));
  return results;
}

// Two things are needed: stop CLAIMING new work, and tell the
// in-flight work to abandon itself.
async function poolCancellable(items, limit, fn, signal) {
  const results = new Array(items.length);
  let next = 0;
  let claimed = 0;

  async function worker() {
    while (next < items.length) {
      if (signal.aborted) return;          // stop claiming
      const i = next++;
      claimed++;
      results[i] = await fn(items[i], i, signal);
    }
  }

  await Promise.all(Array.from({ length: limit }, worker));
  return { results, claimed };
}

// a tiny AbortController stand-in, so this runs anywhere
function makeController() {
  const listeners = [];
  const signal = {
    aborted: false,
    addEventListener: (_, fn) => listeners.push(fn),
  };
  return {
    signal,
    abort() { signal.aborted = true; listeners.forEach((f) => f()); },
  };
}

  signal.addEventListener('abort', () => {
    clearTimeout(timer);                    // actually stop the work
    reject(new Error('aborted'));
  });
});

Step 8

Complexity, in sentences

Wall clockPeak memory
Sequentialsum of all durations1 response
Promise.allthe single longestn responses
Pool of kabout total / kk responses

The pool is O(n) in bookkeeping: one array of results, k worker promises, one cursor. Peak memory is k in-flight responses rather than n, and that is usually the reason the limit exists at all.

Choosing k is not a code question. For network calls it is bounded by the remote service's rate limit and by connection pooling — six to ten is a normal browser default. For CPU work in Node it is the core count. For a database it is the connection-pool size. Pick a number you can defend, and make it configurable.

Say this in the interview

“I run k worker loops sharing one cursor. Each worker claims the next index with i = next++, awaits the task, writes into results[i], and loops until the cursor passes the end; Promise.all over the k workers tells me everything is done. Writing by index keeps the results in input order even though they complete out of order. The important precondition is that the pool takes inputs and a function — not an array of promises, because those have already started. Batching with Promise.all per chunk also works but wastes time waiting for each batch's slowest member.”

correct, for a reason worth knowing

// a recursive worker
async function poolRecursive(items, limit, fn) {
  const results = new Array(items.length);
  let next = 0;

  async function run() {
    if (next >= items.length) return;
    const i = next++;
    results[i] = await fn(items[i], i);
    return run();                             // recurse for the next item
  }

  await Promise.all(Array.from({ length: limit }, run));
  return results;
}

async function poolLoop(items, limit, fn) {
  const results = new Array(items.length);
  let next = 0;
  async function run() {
    while (next < items.length) {
      const i = next++;
      results[i] = await fn(items[i], i);
    }
  }
  await Promise.all(Array.from({ length: limit }, run));
  return results;
}

console.log('the stack. So it is correct.');
console.log('');

4. Forgetting that a rejection abandons the results, not the work

Broken — the pool "stopped" and kept going

async function pool(items, limit, fn) {
  const results = new Array(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length) {
      const i = next++;
      results[i] = await fn(items[i], i);
    }
  }
  await Promise.all(Array.from({ length: limit }, worker));
  return results;
}

// with a stop flag
sideEffects = 0;
async function poolStopping(items, limit, fn) {
  const results = new Array(items.length);
  let next = 0;
  let failed = null;
  async function worker() {
    while (next < items.length && !failed) {
      const i = next++;
      try { results[i] = await fn(items[i], i); }
      catch (e) { failed = failed || e; return; }
    }
  }
  await Promise.all(Array.from({ length: limit }, worker));
  if (failed) throw failed;
  return results;
}

5. Setting the limit from the wrong thing

a limit that does not limit what you think
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function pool(items, limit, fn) {
  const results = new Array(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length) { const i = next++; results[i] = await fn(items[i], i); }
  }
  await Promise.all(Array.from({ length: limit }, worker));
  return results;
}

let apiCalls = 0, peakApi = 0;
const callApi = async () => {
  apiCalls++; peakApi = Math.max(peakApi, apiCalls);
  await sleep(20);
  apiCalls--;
};

// each "item" makes THREE API calls
const processUser = async (id) => {
  await Promise.all([callApi(), callApi(), callApi()]);
  return id;
};

peakApi = 0;
await pool([1, 2, 3, 4, 5, 6], 2, processUser);
console.log('pool limit 2, but each item makes 3 calls');
console.log('  peak concurrent API calls:', peakApi);
console.log('');
console.log('The limit caps ITEMS, not requests. Two items in flight,');
console.log('three calls each, is six concurrent requests -- three');
console.log('times what you thought you configured.');

// the fix: limit the resource, not the loop
function createLimiter(n) {
  let active = 0; const queue = [];
  function next() {
    if (active >= n || !queue.length) return;
    active++;
    const { fn, res, rej } = queue.shift();
    Promise.resolve().then(fn).then(res, rej)
      .finally(() => { active--; next(); });
  }
  return (fn) => new Promise((res, rej) => { queue.push({ fn, res, rej }); next(); });
}

const apiLimit = createLimiter(2);
const limitedCall = () => apiLimit(callApi);
const processUser2 = async (id) => {
  await Promise.all([limitedCall(), limitedCall(), limitedCall()]);
  return id;
};

peakApi = 0;
await pool([1, 2, 3, 4, 5, 6], 4, processUser2);
console.log('');
console.log('with a limiter around the API call itself:');
console.log('  pool limit 4, API limit 2');
console.log('  peak concurrent API calls:', peakApi);
console.log('');
console.log('Put the limiter next to the thing you are protecting.');

What to carry forward

A promise is already running. Everything about rate limiting, retrying, debouncing async work and cancelling it follows from that one fact: you can only control when a promise is created, never what it does once it exists. That is why every one of these APIs takes a function, not a promise.
