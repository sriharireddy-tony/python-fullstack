Async patterns · Problem 05

Race With Timeout

Four lines with Promise.race, and three things almost everyone gets wrong: the timer that keeps the process alive, the fact that a timeout does not stop anything, and what happens to the loser.

Step 1

The problem

A request might hang. Give it 500 ms; if it has not answered by then, fail instead of waiting forever.

Version 0 — the four-line answer
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error('timed out after ' + ms + ' ms')), ms)
  );
  return Promise.race([promise, timeout]);
}

const fast = async () => { await sleep(20); return 'fast answer'; };
const slow = async () => { await sleep(200); return 'slow answer'; };

console.log('fast, 100 ms budget:', await withTimeout(fast(), 100));

try {
  await withTimeout(slow(), 100);
} catch (e) {
  console.log('slow, 100 ms budget:', e.message);
}

console.log('');
console.log('Promise.race settles as soon as ANY input settles, in');
console.log('either direction. So racing your work against a rejecting');
console.log('timer gives you "whichever happens first" -- exactly the');
console.log('shape of a timeout.');
Why race and not any

Promise.race settles on the first promise to settle either way — so a rejecting timer wins the race and rejects the whole thing. That is what you want.

Promise.any ignores rejections and waits for the first fulfilment. A rejecting timer would never win, so the timeout would never fire.

race versus any, on the same inputs
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const work = async () => { await sleep(120); return 'the real answer'; };
const timer = (ms) => new Promise((_, rej) =>
  setTimeout(() => rej(new Error('timeout')), ms));

// race: the timer wins and rejects
try {
  console.log('race :', await Promise.race([work(), timer(40)]));
} catch (e) {
  console.log('race :', e.message, ' <- the timeout fired, as intended');
}

// any: the rejection is ignored, so the slow work still wins
try {
  console.log('any  :', await Promise.any([work(), timer(40)]));
} catch (e) {
  console.log('any  :', e.message);
}
console.log('  -- any waited the full 120 ms. The timeout did nothing.');

// and what any is actually for: the first SUCCESS out of several
const mirrorA = async () => { await sleep(80); throw new Error('mirror A down'); };
const mirrorB = async () => { await sleep(30); return 'from mirror B'; };
const mirrorC = async () => { await sleep(60); return 'from mirror C'; };

console.log('');
console.log('any over three mirrors:', await Promise.any([mirrorA(), mirrorB(), mirrorC()]));
console.log('  -- the fastest SUCCESS, ignoring the one that failed.');

try {
  await Promise.any([mirrorA(), mirrorA()]);
} catch (e) {
  console.log('all mirrors down      :', e.constructor.name,
              'with', e.errors.length, 'errors');
}
Step 2

Think first — the timer nobody clears

Version 0 works, and it leaks. The setTimeout is still pending after the fast promise wins — and a pending timer keeps a Node process alive.

Version 0 — the timer outlives the race
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

let firedAfterWinning = 0;

function leakyTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => {
      firedAfterWinning++;                  // still runs, uselessly
      reject(new Error('timed out'));
    }, ms)
  );
  return Promise.race([promise, timeout]);
}

console.log('');
console.log('Five useless timer callbacks, five rejected promises that');
console.log('nobody is listening to, and -- the part that actually');
console.log('bites -- for 200 ms after each call finished, Node had a');

console.log('');
console.log('In a CLI that means the process hangs after doing its job.');
console.log('In a test runner it means "Jest did not exit one second');

Version 0b — clear it in a finally
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

let fired = 0;

function withTimeout(promise, ms) {
  let timer;

  const timeout = new Promise((_, reject) => {
    timer = setTimeout(() => {
      fired++;
      reject(new Error('timed out after ' + ms + ' ms'));
    }, ms);
  });

  // finally runs whichever way the race settles
  return Promise.race([promise, timeout]).finally(() => clearTimeout(timer));
}

const slow = async () => { await sleep(300); return 'never seen'; };

await sleep(300);
console.log('5 fast calls, 200 ms timeout');
console.log('  timer callbacks that ran:', fired, '-- all cleared');

fired = 0;
try { await withTimeout(slow(), 50); }
catch (e) { console.log(''); console.log('a genuine timeout:', e.message); }
await sleep(100);
console.log('  timer callbacks that ran:', fired, '-- exactly the one that fired');

console.log('');
console.log('`.finally` is the right hook: it fires on fulfilment, on');
console.log('rejection, and it passes the value or reason straight');
console.log('through, so it cannot change the result.');
console.log('');
console.log('Proof it does not interfere:');
console.log('  value passes through:', await withTimeout(fast(), 100));
Step 3

Why a timeout is not a cancellation

The timeout rejects your promise. The work carries on. This is the single most misunderstood thing about the pattern.

Demo — the work keeps running
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

  let timer;
  const timeout = new Promise((_, reject) => {
    timer = setTimeout(() => reject(new Error('timed out')), ms);
  });
  return Promise.race([promise, timeout]).finally(() => clearTimeout(timer));
}

Step 4

The better idea — abort the work, do not just stop waiting

  TIMEOUT ONLY -- you stop waiting

      caller  --race--> [ work ...................... still going ]
                        [ timer -X ]
                             |
                        you reject here, and walk away


  TIMEOUT + ABORT -- the work stops too

      caller  --race--> [ work --- abort! ---X ]
                        [ timer -X ]
                             |
                        reject AND signal the work to tear down


  The signal has to be understood by whatever is doing the work:

      fetch(url, { signal })          native support
      a database driver               usually has a query timeout
      a setTimeout-based mock         clearTimeout in the abort handler
      pure CPU work                   cannot be aborted at all
The three-part answer

1. Race against a timer so the caller gets an answer within the budget.

2. Clear the timer in a finally so nothing is left pending.

3. Pass an AbortSignal into the work so the timeout actually stops it.

Modern platforms give you all three in one call: AbortSignal.timeout(ms).

all three parts together
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

// an abortable operation: it listens to the signal and tears down
function abortableWork(label, ms, signal) {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) return reject(new Error('aborted before starting'));

    const timer = setTimeout(() => {
      committed.push(label);
      resolve(label);
    }, ms);

    signal?.addEventListener('abort', () => {
      clearTimeout(timer);                     // the work actually stops
      reject(new Error('aborted'));
    });
  });
}

let committed = [];

async function withTimeoutAndAbort(makeWork, ms) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), ms);
  try {
    return await makeWork(controller.signal);
  } finally {
    clearTimeout(timer);
  }
}

committed = [];
console.log('fast work, 100 ms budget:',
            await withTimeoutAndAbort((s) => abortableWork('fast', 20, s), 100));

committed = [];
try {
  await withTimeoutAndAbort((s) => abortableWork('slow', 200, s), 40);
} catch (e) {
  console.log('slow work, 40 ms budget :', e.message);
}
await sleep(250);
console.log('  side effects committed  :', JSON.stringify(committed),
            '<- nothing. The work was torn down.');

console.log('');
console.log('Compare the race-only version from Step 3, which left the');
console.log('write to land 160 ms after the caller gave up.');

  }

  console.log('  One call: it creates the signal, fires the abort, and');

  console.log('    fetch(url, { signal: AbortSignal.timeout(5000) })');
}
Step 5

Dry run — who wins, and what happens to the loser

  Promise.race([work, timer])

  work settles first (at 20 ms, timer set for 100):

      20 ms   work resolves 'ok'
              race resolves 'ok'
              finally -> clearTimeout    timer never fires
      caller gets 'ok'


  timer settles first (work takes 300, timer set for 100):

      100 ms  timer rejects
              race rejects
              finally -> clearTimeout    (already fired; harmless)
      caller gets the timeout error

      300 ms  work resolves 'ok'
              ... into nothing. The promise is settled; race
              already ignored it. No error, no warning, no leak
              -- race DID attach a handler to it.


  Both losers are harmless: a cleared timer never runs, and a
  late-resolving winner is simply discarded. The only case that
  is NOT harmless is a late-REJECTING loser in a race you built
  by hand without passing every promise to race.
the race, narrating itself
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const t0 = Date.now();
const at = () => String(Date.now() - t0).padStart(4) + ' ms  ';

function withTimeoutLoud(makePromise, ms, label) {
  console.log(at() + 'starting "' + label + '" with a ' + ms + ' ms budget');

  let timer;
  const timeout = new Promise((_, reject) => {
    timer = setTimeout(() => {
      console.log(at() + '  TIMER fires -> rejecting');
      reject(new Error('timed out after ' + ms + ' ms'));
    }, ms);
  });

  const work = makePromise().then(
    (v) => { console.log(at() + '  WORK resolves with ' + JSON.stringify(v)); return v; },
    (e) => { console.log(at() + '  WORK rejects with ' + e.message); throw e; }
  );

  return Promise.race([work, timeout]).finally(() => {
    console.log(at() + '  finally -> clearTimeout');
    clearTimeout(timer);
  });
}

  async () => { await sleep(20); return 'ok'; }, 100, 'fast'));

console.log('nowhere -- which is fine, but it is not cancellation.');

// Sometimes the right answer to "too slow" is a fallback, not a
// failure -- a cached value, an empty list, a placeholder.
function withTimeoutDefault(promise, ms, fallback) {
  let timer;

const TIMED_OUT = Symbol('timed out');
async function withTimeoutFlag(promise, ms) {
  let timer;
  const timeout = new Promise((resolve) => {
    timer = setTimeout(() => resolve(TIMED_OUT), ms);
  });
  const result = await Promise.race([promise, timeout]).finally(() => clearTimeout(timer));

// a deadline: one budget for the entire operation
function makeDeadline(totalMs) {
  const end = Date.now() + totalMs;
  return {
    remaining: () => Math.max(0, end - Date.now()),
    expired: () => Date.now() >= end,
    guard(promise) {
      const left = this.remaining();
      if (left === 0) return Promise.reject(new Error('deadline already passed'));
      return withTimeout(promise, left);
    },
  };
}

3. timeout plus retry, in the right order
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

function withTimeout(promise, ms) {
  let timer;
  const t = new Promise((_, rej) => {
    timer = setTimeout(() => rej(Object.assign(new Error('timeout'), { timeout: true })), ms);
  });
  return Promise.race([promise, t]).finally(() => clearTimeout(timer));
}

async function retry(makePromise, { attempts = 3, delay = 20, perAttemptMs } = {}) {
  let last;
  for (let i = 0; i < attempts; i++) {
    try {
      // the timeout goes INSIDE the retry, so each attempt is bounded
      return perAttemptMs
        ? await withTimeout(makePromise(i), perAttemptMs)
        : await makePromise(i);
    } catch (e) {
      last = e;
      if (i < attempts - 1) await sleep(delay);
    }
  }
  throw last;
}

let attempt = 0;
const flaky = () => {
  attempt++;
  const ms = attempt < 3 ? 300 : 20;      // hangs twice, then responds
  return sleep(ms).then(() => 'ok on attempt ' + attempt);
};

// timeout inside retry: each hang costs 50 ms, not 300
attempt = 0;
let t0 = Date.now();
console.log('timeout INSIDE retry :', await retry(flaky, {
  attempts: 5, delay: 10, perAttemptMs: 50,
}), ' ~' + (Date.now() - t0) + ' ms');

// timeout outside retry: the first hang eats the whole budget
attempt = 0;
t0 = Date.now();
try {
  await withTimeout(retry(flaky, { attempts: 5, delay: 10 }), 200);

  console.log('timeout OUTSIDE retry:', e.message, ' ~' + (Date.now() - t0) + ' ms');
  console.log('  the first 300 ms hang used the entire 200 ms budget,');
  console.log('  so the retries never got a chance.');
}

console.log('  per-attempt timeout -> "no single try may hang"');

Step 7

Version 2 — the one to write

Version 2 — the interview answer
class TimeoutError extends Error {
  constructor(ms) {
    super('operation timed out after ' + ms + ' ms');
    this.name = 'TimeoutError';
    this.timeout = true;
    this.ms = ms;
  }
}

function withTimeout(promise, ms, options = {}) {
  if (!(ms > 0)) return Promise.resolve(promise);        // no budget = no timeout

  // `'fallback' in options`, not `options.fallback !== undefined` --
  // { fallback: undefined } is a deliberate "resolve with undefined"
  const hasFallback = 'fallback' in options;
  const { fallback, signal } = options;

  let timer;
  const race = new Promise((resolve, reject) => {
    timer = setTimeout(() => {
      if (hasFallback) resolve(fallback);
      else reject(new TimeoutError(ms));
    }, ms);

    signal?.addEventListener('abort', () => reject(new Error('aborted')));
  });

  return Promise.race([Promise.resolve(promise), race])
    .finally(() => clearTimeout(timer));
}

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const fast = () => sleep(20).then(() => 'fast');
const slow = () => sleep(200).then(() => 'slow');

}

the other useful races
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

// 1. hedged requests: after a short delay, send a SECOND copy and
//    take whichever answers first. Trades load for tail latency.
async function hedged(makeRequest, hedgeAfterMs) {
  let sent = 0;
  const first = makeRequest(++sent);
  const second = sleep(hedgeAfterMs).then(() => makeRequest(++sent));
  const winner = await Promise.race([first, second]);
  return { winner, requestsSent: sent };
}

let call = 0;
const variableLatency = () => {
  call++;
  const ms = call === 1 ? 200 : 20;        // the first one is unlucky
  return sleep(ms).then(() => 'answer from request ' + call);
};

// 3. a heartbeat: fail if there is no progress for N ms, rather
//    than after a fixed total
async function withIdleTimeout(steps, idleMs) {
  const seen = [];
  for (const step of steps) {
    let timer;
    const t = new Promise((_, rej) => {
      timer = setTimeout(() => rej(new Error('no progress for ' + idleMs + ' ms')), idleMs);
    });
    seen.push(await Promise.race([step(), t]).finally(() => clearTimeout(timer)));
  }
  return seen;
}

Per withTimeout call1 promise, 1 timerhow long you WAIT
Per-attempt timeout in a retryn timers over the retryeach attempt
A deadline1 timestampthe whole operation
AbortSignal1 controller, 1 listenerhow long the WORK runs

Nothing costs anything measurable. The column that matters is the last one: only the abort row bounds the work. Everything else bounds your patience.

The resource question is the practical one. A hung request that you timed out at 500 ms is still holding a socket, a request context, and whatever the handler captured — potentially for minutes. Under load, a service that times out without aborting accumulates abandoned work until it runs out of connections, which is exactly the failure mode the timeout was meant to prevent.

Say this in the interview

“Promise.race between the work and a timer that rejects, and I clear the timer in a finally — otherwise a pending timer keeps the process alive and fires uselessly. race rather than any, because any ignores rejections so the timer could never win. The important caveat is that this bounds how long I wait, not how long the work runs: the request is still in flight, still holding a socket, and may still complete its side effects. To actually stop it I need to pass an AbortSignal into the operation — AbortSignal.timeout(ms) does the timer, the abort and the cleanup in one call, which is what fetch expects.”

Mistakes people actually make

1. Not clearing the timer

Step 2. It is the mistake in the version everyone writes first, and its symptom — a process or test run that will not exit — looks nothing like its cause.

2. Using Promise.any for a timeout

Broken — the timeout can never fire
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const timer = (ms) => new Promise((_, rej) =>
  setTimeout(() => rej(new Error('timeout')), ms));

const slow = () => sleep(150).then(() => 'the slow answer');

let t0 = Date.now();
console.log('with any :', await Promise.any([slow(), timer(20)]),
            ' after ~' + (Date.now() - t0) + ' ms');
console.log('  the 20 ms "timeout" was ignored entirely.');

t0 = Date.now();
try { await Promise.race([slow(), timer(20)]); }
catch (e) {
  console.log('with race:', e.message, ' after ~' + (Date.now() - t0) + ' ms');
}

console.log('');
console.log('And the mirror-image mistake -- using race for failover:');
const mirrorA = () => sleep(20).then(() => { throw new Error('A is down'); });
const mirrorB = () => sleep(60).then(() => 'B answered');

try { console.log('  race:', await Promise.race([mirrorA(), mirrorB()])); }
catch (e) { console.log('  race:', e.message, '<- gave up on the healthy mirror'); }
console.log('  any :', await Promise.any([mirrorA(), mirrorB()]));

console.log('');
console.log('  race = first to SETTLE   -> timeouts, cancellation');
console.log('  any  = first to SUCCEED  -> failover, mirrors, fallbacks');
console.log('  all  = every success     -> fan-out where you need all');
console.log('  allSettled = every outcome -> reporting');

Step 3. A timed-out write still writes. This is the bug that causes duplicate charges when combined with a retry.

4. Creating the timer before the work

Broken — the budget is spent before the work starts
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

function withTimeout(promise, ms) {
  let timer;
  const t = new Promise((_, rej) => { timer = setTimeout(() => rej(new Error('timeout')), ms); });
  return Promise.race([promise, t]).finally(() => clearTimeout(timer));
}

// expensive synchronous setup happening between the timer and the work
function slowSetup(ms) {
  const end = Date.now() + ms;
  while (Date.now() < end) { /* blocking */ }
}

const work = () => sleep(20).then(() => 'done');

// WRONG: the timeout promise is created, THEN 60 ms is burned, THEN
// the work is started -- with only 40 of its 100 ms left
let t0 = Date.now();
let timer;
const timeoutFirst = new Promise((_, rej) => {
  timer = setTimeout(() => rej(new Error('timeout')), 100);
});
slowSetup(60);
try {
  const v = await Promise.race([work(), timeoutFirst]);
  console.log('timer created first :', v, ' ~' + (Date.now() - t0) + ' ms');
} catch (e) {
  console.log('timer created first :', e.message, ' ~' + (Date.now() - t0) + ' ms');
} finally { clearTimeout(timer); }

// RIGHT: do the setup, then start the timer and the work together
t0 = Date.now();
slowSetup(60);
try {
  const v = await withTimeout(work(), 100);
  console.log('timer created last  :', v, ' ~' + (Date.now() - t0) + ' ms');
} catch (e) {
  console.log('timer created last  :', e.message, ' ~' + (Date.now() - t0) + ' ms');
}

console.log('');
console.log('Both finished here, because 20 ms fits in 40. Push the');
console.log('setup to 90 ms and the first version times out on work');
console.log('that takes 20 ms.');

t0 = Date.now();
let timer2;
const early = new Promise((_, rej) => {
  timer2 = setTimeout(() => rej(new Error('timeout')), 100);
});
slowSetup(90);
try {
  console.log('');
  console.log('with 90 ms of setup:', await Promise.race([work(), early]));
} catch (e) {
  console.log('');
  console.log('with 90 ms of setup:', e.message,
              '-- the 20 ms call "timed out" at 100 ms');
} finally { clearTimeout(timer2); }
console.log('');
console.log('A timeout should measure the OPERATION, not the operation');
console.log('plus whatever happened to run before it.');

5. A timeout that is not distinguishable from a real error

Broken — the caller cannot tell what happened
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

// a plain Error with a message the caller has to parse
function vagueTimeout(promise, ms) {
  let timer;
  const t = new Promise((_, rej) => { timer = setTimeout(() => rej(new Error('Error')), ms); });
  return Promise.race([promise, t]).finally(() => clearTimeout(timer));
}

class TimeoutError extends Error {
  constructor(ms) { super('timed out after ' + ms + ' ms'); this.name = 'TimeoutError'; }
}
function typedTimeout(promise, ms) {
  let timer;
  const t = new Promise((_, rej) => { timer = setTimeout(() => rej(new TimeoutError(ms)), ms); });
  return Promise.race([promise, t]).finally(() => clearTimeout(timer));
}

const slow = () => sleep(150).then(() => 'ok');
const rejects = () => sleep(20).then(() => { throw new Error('Error'); });

// the caller wants to retry a timeout but NOT a validation failure
const classify = (e) => (e instanceof TimeoutError ? 'RETRY' : 'DO NOT RETRY');

for (const [label, fn] of [['vague, timed out ', () => vagueTimeout(slow(), 40)],
                           ['vague, real error', () => vagueTimeout(rejects(), 200)]]) {
  try { await fn(); } catch (e) {
    console.log(label + ' -> message "' + e.message + '", ' +
                'name ' + e.name + ', decision: ' + classify(e));
  }
}
console.log('  -- indistinguishable. The caller has to guess, or parse');
console.log('     the message string, which breaks the moment anyone');
console.log('     rewords it.');

console.log('');
for (const [label, fn] of [['typed, timed out ', () => typedTimeout(slow(), 40)],
                           ['typed, real error', () => typedTimeout(rejects(), 200)]]) {
  try { await fn(); } catch (e) {
    console.log(label + ' -> name ' + e.name.padEnd(13) + ' decision: ' + classify(e));
  }
}

console.log('');
console.log('Give the timeout its own error type, or at least a flag');
console.log('on the error object. Every caller that has to decide');
console.log('whether to retry needs to be able to ask.');
console.log('');
console.log('Note also that AbortError and TimeoutError are different');
console.log('things: "someone cancelled this" and "this took too long"');
console.log('usually deserve different handling.');

Practice before you move on

  1. Write withTimeout from memory, including the clearTimeout in a finally. Then say why race and not any.
  2. Say the caveat before you are asked: this bounds the wait, not the work.
  3. Add an AbortSignal. Step 4. Then mention AbortSignal.timeout(ms).
  4. Write the deadline helper. Step 6 — and explain why three calls each “within budget” can still blow the overall budget.
  5. Combine a per-attempt timeout with a retry and an outer deadline. Step 6's last block. Getting the nesting order right is the whole exercise.
What to carry forward

A timeout is a promise about your patience, not about the work. That single distinction explains the leaked timer, the duplicate write, the exhausted connection pool and the difference between race and an AbortSignal. If you need the work to actually stop, the work has to be told — and it has to be built to listen.
