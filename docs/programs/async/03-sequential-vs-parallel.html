Async patterns · Problem 03

Sequential vs Parallel Execution

The await-in-a-loop bug is the most common async mistake there is, and the fix is one line. The interesting part is the other direction: knowing when sequential is required, and the two traps that make Promise.all the wrong tool even when the work is independent.

Step 1

The problem

the bug, and the one-line fix
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const fetchUser = async (id) => { await sleep(50); return { id, name: 'u' + id }; };

const ids = [1, 2, 3, 4, 5];

// SEQUENTIAL -- each await blocks the next iteration
let t = Date.now();
const seq = [];
for (const id of ids) {
  seq.push(await fetchUser(id));
}
const seqMs = Date.now() - t;

// PARALLEL -- all five start before any is awaited
t = Date.now();
const par = await Promise.all(ids.map(fetchUser));
const parMs = Date.now() - t;

console.log('sequential : ~' + seqMs + ' ms   (5 x 50)');
console.log('parallel   : ~' + parMs + ' ms   (the slowest one)');
console.log('same result:', JSON.stringify(seq) === JSON.stringify(par));
console.log('');
console.log('The requests are independent. There was never a reason to');
console.log('wait for user 1 before asking for user 2.');
console.log('');
console.log('With 100 users and a 200 ms API, the difference is 20');
console.log('seconds versus 200 milliseconds.');
The rule

Sequential when a later step needs an earlier step's result, or when order matters, or when you must not overload something.

Parallel when the operations are genuinely independent.

The tell for the bug: an await inside a loop whose body does not use anything from the previous iteration.

where the awaits actually are
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const timeline = [];
const t0 = Date.now();

const task = async (name, ms) => {
  timeline.push('start ' + name + ' at ' + (Date.now() - t0) + ' ms');
  await sleep(ms);
  timeline.push('  end ' + name + ' at ' + (Date.now() - t0) + ' ms');
  return name;
};

console.log('--- sequential ---');
timeline.length = 0;
await task('A', 40);
await task('B', 40);
timeline.forEach((l) => console.log('  ' + l));

console.log('');
console.log('--- parallel: start both, then await ---');
timeline.length = 0;
const pa = task('A', 40);        // starts NOW
const pb = task('B', 40);        // starts NOW
await pa;
await pb;
timeline.forEach((l) => console.log('  ' + l));

console.log('');
console.log('Note the second version uses `await` twice and is still');
console.log('parallel. What matters is WHEN the function was CALLED,');
console.log('not when it is awaited.');
console.log('');
console.log('An async function starts running the moment you call it.');
console.log('`await` only decides when YOU stop and wait.');
Step 2

Think first — the four loop shapes

four loops, four different behaviours
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const work = async (n) => { await sleep(30); return n * 2; };
const items = [1, 2, 3, 4];

// 1. for...of with await -- SEQUENTIAL, and it waits
let t = Date.now();
const a = [];
for (const n of items) a.push(await work(n));
console.log('1. for...of + await   : ~' + (Date.now() - t) + ' ms  ->',
            JSON.stringify(a));

// 2. forEach with async -- PARALLEL, and it does NOT wait
t = Date.now();
const b = [];
items.forEach(async (n) => { b.push(await work(n)); });
console.log('2. forEach + async    : ~' + (Date.now() - t) + ' ms  ->',
            JSON.stringify(b), ' <- empty!');

// 3. map + Promise.all -- PARALLEL, and it waits
t = Date.now();
const c = await Promise.all(items.map(work));
console.log('3. map + Promise.all  : ~' + (Date.now() - t) + ' ms  ->',
            JSON.stringify(c));

// 4. for await...of over an array of promises -- PARALLEL start,
//    sequential consumption
t = Date.now();
const d = [];
for await (const value of items.map(work)) d.push(value);
console.log('4. for await...of     : ~' + (Date.now() - t) + ' ms  ->',
            JSON.stringify(d));

await sleep(60);
console.log('');
console.log('and forEach eventually filled up:', JSON.stringify(b));
console.log('  -- long after the line that logged it.');

console.log('');
console.log('Number 4 is worth knowing: map() started all four');
console.log('immediately, so it is as fast as Promise.all, but you');
console.log('receive the values one at a time in input order. Useful');
console.log('when you want to process each result as it becomes');
console.log('available without holding them all.');
Why forEach can never work

forEach calls your callback and throws away the return value. An async callback returns a promise; forEach discards it. There is nothing to await, so the loop finishes immediately with every task still in flight.

Worse: a rejection inside that callback becomes an unhandled rejection, because nobody holds the promise. Same for map without Promise.all, and for filter, some and every — all of which treat a returned promise as a truthy object.

filter and some with an async predicate
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const isEvenAsync = async (n) => { await sleep(5); return n % 2 === 0; };

const items = [1, 2, 3, 4, 5, 6];

// filter with an async predicate: EVERY promise is truthy
const wrong = items.filter(isEvenAsync);
console.log('filter(async)  :', JSON.stringify(wrong), ' <- kept everything');
console.log('  because a Promise object is always truthy:',
            !!Promise.resolve(false));

// some / every: same problem
console.log('some(async)    :', items.some(isEvenAsync), ' <- always true');
console.log('every(async)   :', items.every(isEvenAsync), ' <- always true');
console.log('  even with a predicate that always resolves false:');
console.log('    ', items.some(async () => false));

// the fix: resolve the predicates first, then filter synchronously
const flags = await Promise.all(items.map(isEvenAsync));
const right = items.filter((_, i) => flags[i]);
console.log('');
console.log('filter, done properly:', JSON.stringify(right));

// a reusable helper
async function asyncFilter(arr, predicate) {
  const keep = await Promise.all(arr.map(predicate));
  return arr.filter((_, i) => keep[i]);
}
async function asyncSome(arr, predicate) {
  const flags = await Promise.all(arr.map(predicate));
  return flags.some(Boolean);
}
console.log('asyncFilter          :', JSON.stringify(await asyncFilter(items, isEvenAsync)));
console.log('asyncSome            :', await asyncSome(items, isEvenAsync));
console.log('asyncSome(always no) :', await asyncSome(items, async () => false));

console.log('');
console.log('Note asyncSome loses short-circuiting -- it runs every');
console.log('predicate. If that matters you need a loop, and then you');
console.log('are back to sequential.');

Why the difference scales

Timing demo — as the list grows

Step 4

The better idea — ask what depends on what

  Draw the dependency graph. Anything with no arrow between it
  can run at the same time.


  SEQUENTIAL -- a chain:

      getUser  ->  getPosts(user.id)  ->  getComments(posts[0].id)

      Each needs the one before it. No choice.


  PARALLEL -- independent:

      getUser
      getSettings        all three need only the id you already have
      getNotifications


  MIXED -- the common real case:

      getUser  ->  +-- getPosts(user.id)     --+
                   |                            |-> render
                   +-- getSettings(user.id)  --+

      One await, then Promise.all, then continue.
      NOT three sequential awaits.
the mixed case, done three ways
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const getUser = async (id) => { await sleep(40); return { id, name: 'Ada' }; };
const getPosts = async (uid) => { await sleep(40); return ['p1', 'p2']; };
const getSettings = async (uid) => { await sleep(40); return { theme: 'dark' }; };
const getFriends = async (uid) => { await sleep(40); return ['bob']; };

// A: all sequential -- 4 x 40
let t = Date.now();
const u1 = await getUser(1);
const p1 = await getPosts(u1.id);
const s1 = await getSettings(u1.id);
const f1 = await getFriends(u1.id);
console.log('A. four awaits in a row : ~' + (Date.now() - t) + ' ms');

// B: the user first, then the three dependents together -- 2 x 40
t = Date.now();
const u2 = await getUser(1);
const [p2, s2, f2] = await Promise.all([
  getPosts(u2.id), getSettings(u2.id), getFriends(u2.id),
]);
console.log('B. one await, then all  : ~' + (Date.now() - t) + ' ms');

// C: start everything that CAN start, await later
t = Date.now();
const userPromise = getUser(1);
const settingsPromise = getSettings(1);        // only needs the id we already have
const u3 = await userPromise;
const [p3, f3] = await Promise.all([getPosts(u3.id), getFriends(u3.id)]);
const s3 = await settingsPromise;              // already finished
console.log('C. start early, await late: ~' + (Date.now() - t) + ' ms');

console.log('');
console.log('All three produce the same data:',
            JSON.stringify([p1, s1, f1]) === JSON.stringify([p2, s2, f2]) &&
            JSON.stringify([p2, s2, f2]) === JSON.stringify([p3, s3, f3]));
console.log('');
console.log('B is the version to write: it reads top to bottom and it');
console.log('is twice as fast as A.');
console.log('');
console.log('C is faster still where it applies -- getSettings only');
console.log('needed the id, which we had all along. Look for calls that');
console.log('do not actually depend on the await above them; they are');
console.log('very common.');
Step 5

Dry run — when sequential is required

Three cases where the loop must stay sequential, and no amount of Promise.all will help.

1. pagination — you cannot ask for page 2 until page 1 arrives

// the server returns a cursor for the next page
const pages = {
  null: { items: ['a', 'b'], next: 'c1' },
  c1: { items: ['c', 'd'], next: 'c2' },
  c2: { items: ['e'], next: null },
};
const fetchPage = async (cursor) => { await sleep(20); return pages[cursor]; };

const all = [];
let cursor = null;
let requests = 0;
const t0 = Date.now();

do {
  const page = await fetchPage(cursor);          // MUST be sequential
  requests++;
  all.push(...page.items);
  cursor = page.next;
  console.log('  page ' + requests + ': ' + JSON.stringify(page.items) +
              '  next cursor: ' + page.next);
} while (cursor !== null);

console.log('');
console.log('collected:', JSON.stringify(all), 'in', requests, 'requests,',
            '~' + (Date.now() - t0) + ' ms');
console.log('');
console.log('There is no parallel version. The cursor for page 2 is IN');
console.log('page 1. Genuine sequential dependency.');
console.log('');
console.log('If the API gave you a total count or numbered pages, you');
console.log('could parallelise -- which is exactly why good APIs do.');
2. rate limits and 3. ordered side effects
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

// 2. the server allows 1 request per 30 ms
let lastCall = 0;
let violations = 0;
const rateLimitedApi = async (n) => {
  const gap = Date.now() - lastCall;
  if (lastCall !== 0 && gap < 25) violations++;
  lastCall = Date.now();
  await sleep(10);
  return n;
};

violations = 0; lastCall = 0;
await Promise.all([1, 2, 3, 4, 5].map(rateLimitedApi));
console.log('Promise.all against a rate limit:');
console.log('  violations:', violations, 'of 4 gaps -- every one too fast');

violations = 0; lastCall = 0;
for (const n of [1, 2, 3, 4, 5]) { await rateLimitedApi(n); await sleep(25); }
console.log('  sequential with a pause: violations', violations);

// 3. writes that must land in order
const log = [];
const append = async (line, ms) => { await sleep(ms); log.push(line); };

log.length = 0;
await Promise.all([

  append('3. sent the email', 20),

console.log('ordered writes, in parallel:');
log.forEach((l) => console.log('  ' + l));

await append('1. created the record', 30);
await append('2. attached the file', 10);
await append('3. sent the email', 20);
console.log('');
console.log('sequential:');
log.forEach((l) => console.log('  ' + l));

console.log('');
console.log('Three legitimate reasons to stay sequential:');
console.log('  a dependency between steps  (pagination, cursors)');
console.log('  a limit on the other side   (rate limits, connections)');
console.log('  order is part of the result (audit logs, migrations,');

Step 6

Version 1 — the helpers, written out

sequential and parallel map, both explicit
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

// deliberately sequential, and it says so in the name
async function mapSeries(items, fn) {
  const out = [];
  for (let i = 0; i < items.length; i++) {
    out.push(await fn(items[i], i, items));
  }
  return out;
}

// deliberately parallel
async function mapParallel(items, fn) {
  return Promise.all(items.map(fn));
}

// sequential reduce -- each step needs the previous accumulator
async function reduceSeries(items, fn, initial) {
  let acc = initial;
  for (let i = 0; i < items.length; i++) {
    acc = await fn(acc, items[i], i, items);
  }
  return acc;
}

// the same thing written as a promise chain, which is how you did
// it before async/await -- and it is worth recognising
function reduceChain(items, fn, initial) {
  return items.reduce(
    (promise, item, i) => promise.then((acc) => fn(acc, item, i, items)),
    Promise.resolve(initial)
  );
}

const items = [1, 2, 3, 4];
const double = async (n) => { await sleep(20); return n * 2; };
const add = async (acc, n) => { await sleep(20); return acc + n; };

let t = Date.now();
console.log('mapSeries   :', JSON.stringify(await mapSeries(items, double)),
            ' ~' + (Date.now() - t) + ' ms');

t = Date.now();
console.log('mapParallel :', JSON.stringify(await mapParallel(items, double)),
            ' ~' + (Date.now() - t) + ' ms');

t = Date.now();
console.log('reduceSeries:', await reduceSeries(items, add, 0),
            ' ~' + (Date.now() - t) + ' ms');

t = Date.now();
console.log('reduceChain :', await reduceChain(items, add, 0),
            ' ~' + (Date.now() - t) + ' ms');

console.log('');
console.log('The reduce is inherently sequential -- step 3 needs the');
console.log('accumulator from step 2. That is not a bug, it is the');
console.log('definition of a fold.');
console.log('');
console.log('Naming the helper `mapSeries` rather than `mapAsync` is');
console.log('worth doing. A reviewer can then see that the sequencing');
console.log('was a decision, not an accident.');
the reduce trap that looks parallel and is not
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const work = async (n) => { await sleep(20); return n * 2; };

// (a) reduce with an async reducer -- SEQUENTIAL, as intended

  const acc = await accPromise;
  acc.push(await work(n));

}, Promise.resolve([]));

console.log('one line moved above another.');
console.log('');
console.log('This is the whole lesson of the page in miniature: the');
console.log('CALL starts the work, the AWAIT only decides when you');
console.log('block. Move calls up, awaits down.');

Version 2 — the two traps in Promise.all

Trap 1 — which shapes leak an unhandled rejection
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const failFast = async () => { await sleep(10); throw new Error('fast failure'); };
const failSlow = async () => { await sleep(40); throw new Error('slow failure'); };

let seen = [];
const onUnhandled = (e) => seen.push(e?.message ?? String(e));
const canObserve = typeof process !== 'undefined' && !!process.on;
if (canObserve) process.on('unhandledRejection', onUnhandled);

const check = async (label, run) => {
  seen = [];
  try { await run(); } catch (e) { /* handled here */ }
  await sleep(80);
  console.log(label.padEnd(26) + (seen.length
    ? 'UNHANDLED: ' + JSON.stringify(seen)
    : 'no unhandled rejections'));
};

await check('Promise.all', () => Promise.all([failFast(), failSlow()]));
await check('Promise.race', () => Promise.race([failFast(), failSlow()]));
await check('Promise.allSettled', () => Promise.allSettled([failFast(), failSlow()]));

await check('await only one of two', async () => {
  const a = failFast();
  const b = failSlow();      // created, never awaited, never caught
  await a;
});

await check('forEach + async throw', async () => {
  [1, 2].forEach(async () => { await sleep(5); throw new Error('forEach throw'); });
});

console.log('');
console.log('The good news, and it is worth knowing precisely:');
console.log('  Promise.all, race and allSettled all attach handlers to');
console.log('  EVERY input promise. all rejects on the first failure');
console.log('  and then ignores the rest -- but ignoring is not the');
console.log('  same as not handling. Nothing leaks.');
console.log('');
console.log('The two shapes that DO leak:');
console.log('  creating a promise and awaiting only some of them --');
console.log('    the ones you never touched reject into the void;');
console.log('  forEach with an async callback -- the promise is');
console.log('    discarded the instant it is created.');
console.log('');
console.log('So the rule is not "avoid Promise.all". It is: every');
console.log('promise you create must end up somewhere that can catch');
console.log('it. Passing it to a combinator counts.');

if (canObserve && process.off) process.off('unhandledRejection', onUnhandled);

the decision table, as code
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const call = async (n) => { await sleep(20); if (n === 3) throw new Error('n=3'); return n; };
const items = [1, 2, 3, 4];

const describe = async (label, fn) => {
  const t = Date.now();
  try {
    const v = await fn();
    console.log(label.padEnd(30) + '~' + String(Date.now() - t).padStart(4) +
                ' ms  ' + JSON.stringify(v));
  } catch (e) {
    console.log(label.padEnd(30) + '~' + String(Date.now() - t).padStart(4) +
                ' ms  threw: ' + e.message);
  }
};

await describe('all, need every result', () => Promise.all(items.map(call)));

await describe('allSettled, tolerate some', async () =>
  (await Promise.allSettled(items.map(call)))
    .map((r) => (r.status === 'fulfilled' ? r.value : 'X')));

await describe('any, need one winner', () => Promise.any(items.map(call)));

await describe('race, first to settle', () => Promise.race(items.map(call)));

await describe('sequential, order matters', async () => {
  const out = [];
  for (const n of items) { try { out.push(await call(n)); } catch { out.push('X'); } }
  return out;
});

await describe('pool of 2, bounded', async () => {
  const results = new Array(items.length);
  let next = 0;
  const worker = async () => {
    while (next < items.length) {
      const i = next++;
      try { results[i] = await call(items[i]); } catch { results[i] = 'X'; }
    }
  };
  await Promise.all([worker(), worker()]);
  return results;
});

console.log('');
console.log('Six shapes, and choosing between them is the actual');
console.log('question. "Should this be parallel?" is really:');
console.log('  do I need every result?          -> all / allSettled');
console.log('  do I need just one?              -> any / race');
console.log('  does step n+1 need step n?       -> sequential');
console.log('  is there a limit on the other side? -> a pool');
Step 8

Complexity, in sentences

ShapeLatencyPeak memoryFails when
Sequentialsum of all1 resultthe first failure, and it stops
Promise.allthe longestn resultsthe first failure — the rest run on, unobserved
Promise.allSettledthe longestn resultsnever
Pool of kabout sum / kk resultsconfigurable

Latency is the headline, but the memory column decides real systems. Promise.all over ten thousand rows holds ten thousand results before you can process any of them. Sequential holds one. A pool holds k — which is why the pool is usually the production answer even when latency does not require it.

The failure column is the subtle one. Sequential stops at the first error, which is often exactly what you want for a series of writes. Promise.all reports the first error while the other operations run to completion — so a partial write is possible and you will not know which parts landed.

Say this in the interview

“await in a loop is sequential, so the latency is the sum. If the iterations are independent I collect the promises — usually with map — and await them together, which makes the latency the maximum instead. The thing to be precise about is that Promise.all does not create parallelism: calling the async function starts the work, and Promise.all just waits. So Promise.all([await a(), await b()]) is still sequential. I would keep it sequential when a step depends on the previous one, when order is part of the result, or when the other side has a rate limit — and for a large list I would use a bounded pool rather than Promise.all, because all holds every result in memory at once.”

Step 9

Mistakes people actually make

1. await in a loop over independent work

Step 1. It is the most common async performance bug in JavaScript, and it always looks reasonable.

2. forEach with an async callback

Broken — and it swallows errors too
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

let unhandled = 0;
const onUnhandled = () => unhandled++;
if (typeof process !== 'undefined' && process.on) {
  process.on('unhandledRejection', onUnhandled);
}

async function saveAll(items) {
  const saved = [];
  items.forEach(async (item) => {
    await sleep(10);
    if (item === 3) throw new Error('item 3 failed to save');
    saved.push(item);
  });
  return saved;                        // returns BEFORE anything saved
}

const result = await saveAll([1, 2, 3, 4]);
console.log('returned immediately with:', JSON.stringify(result));
console.log('  the caller believes nothing was saved');

await sleep(60);
console.log('');
console.log('60 ms later, actually saved:', JSON.stringify(result));
console.log('unhandled rejections:', unhandled, '-- the throw went nowhere');
console.log('');
console.log('Three separate bugs in four lines:');
console.log('  1. the function returned before the work finished');
console.log('  2. the caller cannot know when it IS finished');
console.log('  3. the error was never reported to anyone');

console.log('');
console.log('Fixes:');
console.log('  for...of  -> sequential, errors propagate');
console.log('  map + all -> parallel, errors propagate');

async function saveAllFixed(items) {
  return Promise.all(items.map(async (item) => {
    await sleep(10);
    if (item === 3) throw new Error('item 3 failed to save');
    return item;
  }));
}
try {
  await saveAllFixed([1, 2, 3, 4]);
} catch (e) {
  console.log('  map + all threw:', e.message, '-- the caller found out');
}

if (typeof process !== 'undefined' && process.off) {
  process.off('unhandledRejection', onUnhandled);
}

3. Parallelising something that must not be

Broken — a lost update
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

// a "database" with read-then-write semantics
let stored = { count: 0 };
const read = async () => { await sleep(10); return { ...stored }; };
const write = async (doc) => { await sleep(10); stored = doc; };

const increment = async () => {
  const doc = await read();          // read
  doc.count += 1;                    // modify
  await write(doc);                  // write
};

// in parallel: all five read 0, all five write 1
stored = { count: 0 };
await Promise.all([increment(), increment(), increment(), increment(), increment()]);
console.log('five parallel increments  -> count is', stored.count,
            '(expected 5)');

// sequentially: each reads what the last one wrote
stored = { count: 0 };
for (let i = 0; i < 5; i++) await increment();
console.log('five sequential increments-> count is', stored.count);

console.log('');
console.log('This is a lost update, and it happens whenever an');
console.log('operation is read-modify-write and you run several at');
console.log('once. JavaScript being single-threaded does not save you:');
console.log('the await is a yield point, and another increment runs');
console.log('there.');
console.log('');
console.log('Fixes, in order of preference:');
console.log('  make the operation atomic  ($inc, UPDATE ... SET x = x+1)');
console.log('  use optimistic concurrency (a version field, retry)');
console.log('  serialise the operation    (a lock, or a queue of one)');
console.log('');
console.log('Only the last one is a JavaScript answer. The first is');
console.log('nearly always the right one.');

4. Building the promise array with await in it

Step 7's second trap. Promise.all([await a(), await b()]) is sequential, and it looks parallel to almost everyone who reads it.

5. Promise.all on a list that is not bounded

Broken — two thousand at once
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

let inFlight = 0, peak = 0;
const fetchRow = async (id) => {
  inFlight++; peak = Math.max(peak, inFlight);
  await sleep(2);
  inFlight--;
  return { id, payload: 'x'.repeat(200) };      // a realistic-ish response
};

const ids = Array.from({ length: 2000 }, (_, i) => i);

// Promise.all: 10,000 concurrent, 10,000 results held at once
peak = 0;
let t = Date.now();
const all = await Promise.all(ids.map(fetchRow));
console.log('Promise.all  : ~' + (Date.now() - t) + ' ms, peak ' + peak +
            ' concurrent, ' + all.length + ' results held');

// a pool: bounded concurrency AND you can process-and-discard
peak = 0;
t = Date.now();
let processed = 0;
async function poolConsume(items, limit, fn, onResult) {
  let next = 0;
  const worker = async () => {
    while (next < items.length) {
      const i = next++;
      onResult(await fn(items[i], i));         // handle it, then drop it
    }
  };
  await Promise.all(Array.from({ length: limit }, worker));
}
await poolConsume(ids, 50, fetchRow, () => { processed++; });
console.log('pool of 50   : ~' + (Date.now() - t) + ' ms, peak ' + peak +
            ' concurrent, 0 results held (' + processed + ' processed)');

console.log('');
console.log('The pool is slower in wall-clock terms here, and it is');
console.log('the one you ship. Promise.all opened 2,000 sockets at once');
console.log('and held 2,000 response bodies in memory simultaneously;');
console.log('the pool held 50 and none of the results.');
console.log('');
console.log('Whenever the list length comes from data rather than from');
console.log('a literal, Promise.all is a decision you have to justify.');
Step 10

Practice before you move on

  1. Say the one-sentence rule: the call starts the work, the await decides when you block. Then explain why Promise.all([await a(), await b()]) is sequential.
  2. Write mapSeries and mapParallel and name them so a reader can tell the sequencing was deliberate.
  3. List the three reasons to stay sequential. Step 5 — dependency, rate limit, order.
  4. Name the two shapes that leak an unhandled rejection — and why Promise.all is not one of them. Step 7.
  5. Take the mixed dependency graph from Step 4 and rewrite version A as version C by hand. Finding calls that do not depend on the await above them is the highest-value habit on this page.
What to carry forward

Calling starts the work; awaiting only blocks you. Every item on this page is a consequence: forEach fails because it throws away the promise, the reduce trap turns on one line's position, and Promise.all is a waiting tool rather than a parallelising one. Move your calls up and your awaits down, and check the dependency graph before you decide either way.
