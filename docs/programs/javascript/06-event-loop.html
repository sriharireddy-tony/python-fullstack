JavaScript semantics · Problem 06

Event Loop Output Order

“What does this print?” — asked in almost every JavaScript interview, and answered correctly by almost nobody who has not learned the one algorithm on this page. There is no intuition to develop. There is a procedure, and it always works.

Step 1

The problem — the four places code can live

   +----------------------------------------------------+
   |                    CALL STACK                      |
   |   whatever is running RIGHT NOW. One thing only.   |
   +----------------------------------------------------+
                          |
        when the stack empties, the loop looks here:
                          |
                          v
   +----------------------------------------------------+
   |               MICROTASK QUEUE                      |
   |   .then / .catch / .finally callbacks              |
   |   await continuations                              |
   |   queueMicrotask()                                 |
   |   MutationObserver callbacks                       |
   |                                                    |
   |   DRAINED COMPLETELY, including anything added     |
   |   while draining.                                  |
   +----------------------------------------------------+
                          |
              only when that is EMPTY:
                          |
                          v
   +----------------------------------------------------+
   |               MACROTASK QUEUE                      |
   |   setTimeout, setInterval, setImmediate            |
   |   I/O callbacks, DOM events, MessageChannel        |
   |                                                    |
   |   ONE task is taken. Then back to the microtasks.  |
   +----------------------------------------------------+
The four-line algorithm
  1. Run all synchronous code to the end.
  2. Drain the entire microtask queue, including microtasks queued during the drain.
  3. Take one macrotask.
  4. Go to step 2.

“All the microtasks, then one macrotask” is the asymmetry that produces every surprising answer.

the canonical question

  .then(() => console.log('4  promise 1'))
  .then(() => console.log('5  promise 2'));

console.log('2  script middle');

queueMicrotask(() => console.log('3.5  queueMicrotask'));

console.log('3  script end');

await new Promise((r) => setTimeout(r, 30));

console.log('');
console.log('Work it out with the algorithm:');
console.log('  1. sync: "script start", "script middle", "script end"');
console.log('  2. microtasks: promise 1, then queueMicrotask,');
console.log('     then promise 2 (queued only when promise 1 finished)');
console.log('  3. one macrotask: setTimeout');
console.log('');
console.log('Note that "promise 2" comes AFTER "queueMicrotask" even');
console.log('though it was written first. The second .then was not');
console.log('queued until the first one returned.');
Step 2

Think first — what “single-threaded” really means

JavaScript runs one thing at a time. Nothing else can happen while your code is running — not a timer, not a click, not a network callback. They queue up and wait.

Version 0 — a timer that cannot fire
const t0 = Date.now();
let fired = null;

setTimeout(() => { fired = Date.now() - t0; }, 10);

// block the thread for 200 ms
let x = 0;
while (Date.now() - t0 < 200) x++;

console.log('asked for a 10 ms timer, blocked the thread for 200 ms');
console.log('  right after the block, has it fired?', fired !== null);

await new Promise((r) => setTimeout(r, 30));

console.log('  it actually fired at ~' + fired + ' ms');
console.log('');
console.log('setTimeout(fn, 10) means "not BEFORE 10 ms", never');
console.log('"at 10 ms". The callback cannot run until the stack is');
console.log('empty, and you kept it full.');
console.log('');
console.log('This is why a slow synchronous loop freezes a page:');
console.log('clicks, scrolls, animation frames and network callbacks');
console.log('are all queued behind it.');
and the 4 ms clamp nobody expects
// setTimeout(fn, 0) is not 0. Browsers clamp nested timers to 4 ms
// after a few levels; Node has its own minimum of 1 ms.
const samples = [];
let last = performance.now();
let depth = 0;

await new Promise((done) => {
  function tick() {
    const now = performance.now();
    samples.push(+(now - last).toFixed(2));
    last = now;
    if (++depth < 12) setTimeout(tick, 0);
    else done();
  }
  setTimeout(tick, 0);
});

console.log('gaps between 12 nested setTimeout(fn, 0) calls, in ms:');
console.log(' ', samples.join(', '));
console.log('');
console.log('None of them are 0. In a browser the 5th and later are');
console.log('clamped to at least 4 ms by the HTML specification; here');
console.log('they land near 16 ms because the timer resolution of the');
console.log('host platform is coarser than that. The exact number is');
console.log('not the lesson -- "not zero, and not under your control"');
console.log('is.');
console.log('');
console.log('Microtasks have no such clamp:');

const microSamples = [];
last = performance.now();
depth = 0;
await new Promise((done) => {
  function tick() {
    const now = performance.now();
    microSamples.push(+(now - last).toFixed(3));
    last = now;
    if (++depth < 12) queueMicrotask(tick);
    else done();
  }
  queueMicrotask(tick);

console.log('That is the real difference: a microtask is "as soon as');
console.log('the stack empties", a timer is "some time later".');
Step 3

Why it matters — microtasks can starve everything

Demo — a microtask loop versus a macrotask loop
// Two ways to run 60 chunks of work. Same total work, completely
// different effect on responsiveness.
const CHUNKS = 60;
function chunk() { let x = 0; for (let i = 0; i < 200000; i++) x += i; return x; }

// (a) chained microtasks -- the timer never gets a look in
let timerRanDuringMicro = false;
setTimeout(() => { timerRanDuringMicro = true; }, 0);

let n = 0;
const microStart = performance.now();
await new Promise((done) => {
  function step() {
    chunk();
    if (++n < CHUNKS) queueMicrotask(step);
    else done();
  }
  queueMicrotask(step);
});
const microMs = performance.now() - microStart;

console.log('(a) ' + CHUNKS + ' chunks via chained microtasks: ' + microMs.toFixed(0) + ' ms');
console.log('    did the 0 ms timer get to run in between?',
            timerRanDuringMicro);

// (b) chained macrotasks -- the loop can breathe between chunks
let timerRanDuringMacro = false;
setTimeout(() => { timerRanDuringMacro = true; }, 0);

n = 0;
const macroStart = performance.now();
await new Promise((done) => {
  function step() {
    chunk();
    if (++n < CHUNKS) setTimeout(step, 0);
    else done();
  }
  setTimeout(step, 0);
});
const macroMs = performance.now() - macroStart;

console.log('');
console.log('(b) ' + CHUNKS + ' chunks via chained setTimeout: ' + macroMs.toFixed(0) + ' ms');
console.log('    did the 0 ms timer get to run in between?',
            timerRanDuringMacro);

console.log('');
console.log('(a) is faster overall and completely blocks everything');
console.log('else. (b) is slower and stays responsive -- each chunk');
console.log('returns to the event loop, so clicks, paints and other');
console.log('timers get their turn.');
console.log('');
console.log('That trade is the reason both queues exist. Use');
console.log('microtasks for "finish this logical operation"; use');
console.log('macrotasks when you must yield the thread.');
Step 4

The better idea — how to answer any such question

Do not read the code top to bottom looking for the answer. Sort every statement into one of three lists first, then read the lists in order.

  Pass 1 -- walk the code once and classify:

     SYNC       anything not inside a callback
     MICRO      .then / .catch / .finally bodies,
                queueMicrotask, everything after an `await`
     MACRO      setTimeout / setInterval bodies, I/O

  Pass 2 -- read the SYNC list. That is your first output block.

  Pass 3 -- read the MICRO list, in the order they were QUEUED.
            If running one queues another micro, append it.

  Pass 4 -- take ONE item from MACRO, run it as if it were sync,
            then go back to pass 3.
The three rules that decide the tricky cases

1. A .then is only queued when the promise it is attached to settles — not when the line is written. In a chain, link 2 is queued when link 1's handler returns.

2. await is .then in disguise. Everything before the first await in an async function is synchronous; everything after any await is a microtask.

3. Returning a promise from a then costs two extra microtask ticks, not one. This is the detail that separates a good answer from a perfect one, and it is in Step 7.

rule 2, made concrete

  await null;                       // even awaiting a non-promise yields
  console.log('5  after the await -- this is a microtask');

console.log('1  before the call');

console.log('3  after the call -- the async function already paused');

Promise.resolve().then(() => console.log('4  a then queued after example paused'));

console.log('');
console.log('An async function runs SYNCHRONOUSLY until its first');
console.log('await. That is why "2" comes before "3".');
console.log('');

console.log('    A;                            A;');
console.log('    await x;             ==>      return Promise.resolve(x)');

Step 6

Build the loop yourself

The clearest way to be sure you understand it is to write one. Twenty lines, and every rule from Step 1 becomes a line of code.

A working toy event loop
function makeLoop() {
  const macro = [];
  const micro = [];
  const output = [];

  const api = {
    log: (s) => output.push(s),
    setTimeout: (fn) => macro.push(fn),
    queueMicrotask: (fn) => micro.push(fn),
  };

  function drainMicrotasks() {
    // note: `micro.length` is re-read every iteration, ON PURPOSE.
    // A microtask that queues another must extend this drain.
    while (micro.length > 0) {
      const task = micro.shift();
      task();
    }
  }

  function run(script) {
    script(api);            // 1. all synchronous code
    drainMicrotasks();      // 2. the whole microtask queue

    while (macro.length > 0) {
      const task = macro.shift();
      task();               // 3. exactly ONE macrotask
      drainMicrotasks();    // 4. and back to the microtasks
    }

    return output;
  }

  return run;
}

const run = makeLoop();

const result = run(({ log, setTimeout, queueMicrotask }) => {
  log('script start');

  setTimeout(() => {
    log('timer 1');
    queueMicrotask(() => log('  micro queued inside timer 1'));
  });

  setTimeout(() => log('timer 2'));

  queueMicrotask(() => {
    log('micro A');
    queueMicrotask(() => log('micro C -- queued by A, still drained now'));
  });

  queueMicrotask(() => log('micro B'));

  log('script end');
});

result.forEach((line, i) => console.log((i + 1) + '. ' + line));

console.log('');
console.log('Two things to notice:');
console.log('  micro C ran in the SAME drain as A and B, because the');
console.log('  while loop re-checks the length each time.');
console.log('  The microtask queued inside timer 1 ran before timer 2,');
console.log('  because the drain happens after EVERY macrotask.');
The same loop with one bug: drain only once
function brokenLoop(script) {
  const macro = [], micro = [], output = [];
  const api = {
    log: (s) => output.push(s),
    setTimeout: (fn) => macro.push(fn),
    queueMicrotask: (fn) => micro.push(fn),
  };

  script(api);

  // BUG: length captured once, so microtasks queued during the
  // drain are not run in this pass
  const count = micro.length;
  for (let i = 0; i < count; i++) micro.shift()();

  while (macro.length) { macro.shift()(); }
  return output;
}

const out = brokenLoop(({ log, setTimeout, queueMicrotask }) => {
  log('sync');
  setTimeout(() => log('timer'));
  queueMicrotask(() => {
    log('micro A');
    queueMicrotask(() => log('micro B -- queued by A'));
  });
});

console.log(out);
console.log('');
console.log('"micro B" never ran, and "timer" ran while a microtask');
console.log('was still pending. The whole guarantee -- microtasks');
console.log('finish before the next macrotask -- is gone.');
console.log('');
console.log('The fix is one character: `while (micro.length)` instead');
console.log('of a cached count.');

Step 8

The reference card

APIQueueRuns
process.nextTicknextTick (Node only)before all microtasks
.then / .catch / .finallymicrotaskwhen the stack empties

queueMicrotaskmicrotasksame
MutationObservermicrotasksame (browser)

Say this in the interview

“The stack runs to empty first. Then the entire microtask queue drains — including microtasks queued while draining. Then exactly one macrotask runs, and we drain the microtasks again. So to predict output I classify every statement as sync, microtask or macrotask, read the sync ones in source order, then the microtasks in the order they were queued, then one timer at a time. The two details people miss: an async function runs synchronously up to its first await, and a .then is only queued when the promise it is attached to settles — so chains interleave rather than running as a block.”

Step 9

Mistakes people actually make

1. Assuming a chain runs as one block

Broken — reading state that has not been set yet

4. Blocking the loop and blaming the framework

Step 10

Practice before you move on

  1. Recite the four-step algorithm. Sync, drain all microtasks, one macrotask, repeat. Then apply it to Step 5's snippet without looking at the trace.
  2. Write the toy event loop from memory. Step 6 — and note where the while goes, because that one line is the whole microtask guarantee.
  3. Predict the interleaving of two promise chains of different lengths. Step 9's first block is the two-equal-chains case; try lengths 2 and 4.
  4. Explain why returning a promise from then costs extra ticks and why await no longer does. Step 7.
  5. Take any snippet you find online and classify it in three lists before running it. Do that five times and these questions stop being hard.
What to carry forward

There is no concurrency here, only interleaving. One thread, one thing at a time, and a strict order for what runs next. Every output-order question is answered by the same four steps — and the two facts that catch people out are that an async function runs synchronously until its first await, and that microtasks queued during a drain join that same drain.
