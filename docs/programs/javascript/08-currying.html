JavaScript semantics · Problem 08

Currying — sum(1)(2)(3)

The generic curry is eight lines and turns on one property most people have never used: fn.length. Then there is the trick version — sum(1)(2)(3)(4)… forever — which is a completely different problem with a genuinely strange answer.

Step 1

The problem

Currying turns a function of n arguments into a chain of n functions of one argument each.

what curry does
function add(a, b, c) { return a + b + c; }

add(1, 2, 3)              // 6      -- normal

const curried = curry(add);
curried(1)(2)(3)          // 6      -- fully curried
curried(1, 2)(3)          // 6      -- and usually: partial in any grouping
curried(1)(2, 3)          // 6
curried(1, 2, 3)          // 6
The question the implementation has to answer

“Do I have enough arguments yet?” — and the answer comes from fn.length, the arity: how many parameters the function declares.

If collected.length >= fn.length, call it. Otherwise return a function that collects more.

fn.length — and everything that breaks it

Step 3

Why it costs something

Every partial call allocates a closure and an array. At normal sizes that is invisible; in a hot loop it is not, and it is worth being able to say so.

Timing demo — curried versus direct
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) return fn.apply(this, args);
    return (...more) => curried.apply(this, [...args, ...more]);
  };
}

Step 4

The better idea — collect until you have enough

  curry(fn):

      return curried(...args):

          if args.length >= fn.length:
              enough -> fn(...args)

          else:
              not enough -> return a function that, when called,
                            re-enters curried with the OLD args
                            plus the NEW ones


  curry(add3) where add3.length === 3:

      curried(1)            1 < 3   -> return g1, remembering [1]
      g1(2)                         -> curried(1, 2)
                            2 < 3   -> return g2, remembering [1,2]
      g2(3)                         -> curried(1, 2, 3)
                            3 >= 3  -> add3(1, 2, 3) = 6

  Each returned function closes over a DIFFERENT args array, so
  a partial can be reused:

      const addTo1 = curried(1)
      addTo1(2)(3)   // 6
      addTo1(5)(5)   // 11    -- addTo1 was not consumed
Why [...args, ...more] and not args.push(...more)

Pushing mutates the array the partial closed over. Reuse that partial and it now carries the previous call's arguments — a stateful bug in something that should be a pure value. Build a new array every time. This is the mistake in Step 9.

Step 6

Version 1 — without arrow functions or rest

Version 1 — ES5, arguments and concat
function curry(fn, arity) {
  if (arity === undefined) arity = fn.length;

  return function curried() {
    // `arguments` is array-LIKE, not an array
    var args = Array.prototype.slice.call(arguments);

    if (args.length >= arity) {
      return fn.apply(this, args);
    }

    var self = this;
    return function () {
      var more = Array.prototype.slice.call(arguments);
      // concat builds a NEW array -- never push into `args`
      return curried.apply(self, args.concat(more));
    };
  };
}

// placeholders -- what lodash calls _
const _ = Symbol('placeholder');
function curryWithPlaceholder(fn, arity = fn.length) {
  return function curried(...args) {
    const filled = args.filter((a) => a !== _).length;
    if (filled >= arity && !args.slice(0, arity).includes(_)) {
      return fn.apply(this, args.slice(0, arity));
    }
    return (...more) => {
      const merged = args.slice();
      let mi = 0;
      for (let i = 0; i < merged.length && mi < more.length; i++) {
        if (merged[i] === _) merged[i] = more[mi++];
      }
      return curried.apply(this, [...merged, ...more.slice(mi)]);
    };
  };
}

The trick question: sum(1)(2)(3)(4)… forever

This is not currying, because there is no arity to reach — the chain never ends. So the returned function must be able to act as both a function and a number.

The answer: give the returned function a toString (and valueOf, and Symbol.toPrimitive) that produces the running total. When JavaScript needs a primitive — printing it, adding it, comparing it — it calls one of those.

the infinite-arity version
function sum(first) {
  let total = first;

  function collect(next) {
    total += next;
    return collect;                 // always returns itself
  }

  // this is the whole trick
  collect.toString = () => String(total);
  collect.valueOf = () => total;
  collect[Symbol.toPrimitive] = () => total;

  return collect;
}

function probe(label, hooks) {
  const f = () => f;
  const called = [];
  if (hooks.includes('toString')) f.toString = () => { called.push('toString'); return '42'; };
  if (hooks.includes('valueOf')) f.valueOf = () => { called.push('valueOf'); return 42; };
  if (hooks.includes('toPrimitive')) {
    f[Symbol.toPrimitive] = (hint) => {
      called.push('toPrimitive(' + hint + ')');
      return hint === 'string' ? '42' : 42;
    };
  }
  return { f, called, label };
}

const scenarios = [

  ['toString + valueOf ', ['toString', 'valueOf']],
  ['valueOf only       ', ['valueOf']],
  ['toString only      ', ['toString']],
];

for (const [label, hooks] of scenarios) {
  const results = [];

Step 8

Complexity, in sentences

OperationCost
Calling a curried function fully appliedO(n) to spread, then the original
Each partial applicationO(k) — a new array of k collected arguments
A full n-step chainO(n2) copies in total
Space per partialone closure plus the args array

That O(n²) is real but almost never relevant: n is the number of parameters, which is three or four. It becomes a genuine problem only with a large explicit arity — curry(fn, 1000) copies the growing array a thousand times.

The cost that actually matters in practice is the one from Step 3: a partial built inside a hot loop allocates on every iteration. Build it once, outside.

Say this in the interview

“curry returns a collector that compares how many arguments it has against fn.length. Enough, and it calls through; not enough, and it returns another collector closing over what it has so far. I always build a new array rather than pushing, so a partial can be reused. The limitation to mention is that fn.length stops counting at the first default or rest parameter, so variadic functions need the arity passed in explicitly. And sum(1)(2)(3) with no fixed arity is a different problem — there you return the function itself and give it a toString, valueOf and Symbol.toPrimitive so it coerces to the running total.”

Step 9

Mistakes people actually make

1. Mutating the collected arguments

Broken — a partial that remembers the last call
function brokenCurry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) return fn.apply(this, args);
    return (...more) => {
      args.push(...more);              // MUTATES the closed-over array
      return curried.apply(this, args);
    };
  };
}

  return function curried(...args) {

  ['r === 6          ', r === 6],
  ['+r === 6         ', +r === 6],
  ['Number(r) === 6  ', Number(r) === 6],
  ['r > 5            ', r > 5],
  ['`${r}` === "6"   ', `${r}` === '6'],
  ['[r].join() === "6"', [r].join() === '6'],
  ['typeof r         ', typeof r],
  ['Array.isArray(r) ', Array.isArray(r)],
  ['JSON of {v:r}    ', JSON.stringify({ v: r })],
];
checks.forEach(([label, v]) => console.log('  ' + label + ' -> ' + v));

console.log('  === is false and can never be made true. Strict equality');

console.log('    Neither toString nor valueOf is consulted; only');

const users = [

];

// curried "point-free" style
const prop = (key) => (obj) => obj[key];
const equals = (a) => (b) => a === b;
const compose = (...fns) => (x) => fns.reduceRight((v, f) => f(v), x);
const inLondon = compose(equals('London'), prop('city'));

console.log('curried :', users.filter(inLondon).map(prop('name')));

// the direct version
console.log('direct  :', users.filter((u) => u.city === 'London').map((u) => u.name));

console.log('');
console.log('Same answer. The second one can be read by anyone; the');
console.log('first needs three helper definitions and a mental stack.');
console.log('');

console.log('reused with the same leading arguments:');

const logger = (level) => (module) => (msg) => '[' + level + '] ' + module + ': ' + msg;

Step 10

Practice before you move on

  1. Write the four-line curry from memory. Then say what fn.length is and the two things that stop it counting.
  2. Write sum(1)(2)(3) with toString, valueOf and Symbol.toPrimitive, and state its limitation before you are asked.
  3. Write the terminating variant sum(1)(2)(3)() and explain why it is the better answer for real code.
  4. Write partial — partial(fn, ...preset) — and say how it differs from curry. It is three lines, and it is what bind already does.
  5. Add placeholder support. Step 7. It is the feature that makes curry genuinely useful, and the merging logic is a good exercise.
What to carry forward

Two different questions wear the same name. Generic currying is about fn.length and collecting arguments — a closure exercise. The infinite sum(1)(2)(3) is about coercion — a type-conversion exercise dressed as a function. Work out which one is being asked before you start writing.
