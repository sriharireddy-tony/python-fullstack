JavaScript semantics · Problem 05

Build a Promise from scratch

A promise is a three-state machine with a list of callbacks attached. That much is twenty lines. The parts that take thought are: what happens when then is called after it already settled, and what happens when your callback returns another promise.

Step 1

The problem — the state machine

                        +-----------+
                        |  PENDING  |
                        +-----------+
                         /         \
              resolve(v)/           \reject(e)
                       /             \
             +-------------+   +------------+
             |  FULFILLED  |   |  REJECTED  |
             |   value: v  |   |  reason: e |
             +-------------+   +------------+

  Three rules, and they are the whole specification:

    1. A promise starts PENDING.
    2. It moves to FULFILLED or REJECTED at most ONCE.
       Every later resolve or reject is ignored, silently.
    3. Once settled, it never changes again -- so a `then`
       attached afterwards fires immediately (well: on the next
       microtask) with the value it already has.
all three rules, observable
// rule 2: settling is one-way and once only
const p = new Promise((resolve, reject) => {
  resolve('first');
  resolve('second');       // ignored
  reject(new Error('no')); // ignored
});
p.then((v) => console.log('1. settled once with:', v));

// rule 3: attaching then() later still works
const settled = Promise.resolve('already done');
setTimeout(() => {
  settled.then((v) => console.log('2. attached 20 ms late, still got:', v));
}, 20);

// and you can attach as many as you like, all get the same value
const shared = Promise.resolve('one value');
shared.then((v) => console.log('3a.', v));
shared.then((v) => console.log('3b.', v));
shared.then((v) => console.log('3c.', v));

// the executor runs SYNCHRONOUSLY; the callbacks do not
console.log('A. before the constructor');
new Promise((resolve) => {
  console.log('B. inside the executor -- synchronous');
  resolve();
}).then(() => console.log('D. inside then -- a microtask'));
console.log('C. after the constructor');

await new Promise((r) => setTimeout(r, 60));
The distinction that trips everyone

The executor — the function you pass to new Promise — runs immediately and synchronously. The callbacks you pass to then never do: they are queued as microtasks, even when the promise is already settled.

That is why the output above is A, B, C, D and not A, B, D, C.

What the promise actually bought

Not fewer lines — a value. A callback is a hole in your program that someone else fills. A promise is a first-class object you can return, store in an array, pass to Promise.all, and attach handlers to later. Everything else follows from that.

Step 3

Why the microtask queue matters

Promise callbacks run on the microtask queue, which drains completely before any timer. Get this wrong in your implementation and the output order is wrong — and output-order questions are the most common promise interview question there is.

Step 4

The better idea — three fields and two queues

  class MyPromise {

      state  = 'pending' | 'fulfilled' | 'rejected'
      value  = the fulfilment value, or the rejection reason
      onFulfilledCallbacks = []      <-- queued while pending
      onRejectedCallbacks  = []

      constructor(executor):
          define resolve(v) and reject(e) as closures over `this`
          run executor(resolve, reject) IMMEDIATELY
          if it throws, reject with what it threw

      resolve(v):
          if state !== 'pending': return        <-- rule 2
          state = 'fulfilled'; value = v
          run every queued onFulfilled callback

      then(onFulfilled, onRejected):
          return a NEW promise
          if already settled  -> queue the handler as a microtask
          if still pending    -> push it into the callback array
  }
The two cases then must handle

Still pending: there is nothing to run yet. Push the handler into an array; the eventual resolve will drain it.

Already settled: there is no future resolve to drain anything, so schedule the handler yourself — as a microtask, never synchronously.

Forget the second case and every promise that settles before then is attached hangs forever. That is the single most common bug in a hand-written promise.

Then the part that makes chaining work.

  then() returns a new promise P2. What settles P2?

      handler returns a plain value v   ->  resolve P2 with v
      handler THROWS e                  ->  reject P2 with e
      handler returns a PROMISE         ->  P2 adopts it:
                                            wait for it, then settle
                                            P2 the same way

  That third line is why you can write

      fetchUser().then(u => fetchPosts(u)).then(posts => ...)

  instead of getting a promise-of-a-promise. The spec calls this
  step "the resolution procedure", and it is the only genuinely
  subtle part of the whole object.
Step 5

Dry run — a chain, step by step

  const p1 = new MyPromise(res => setTimeout(() => res(1), 10));
  const p2 = p1.then(v => v + 1);
  const p3 = p2.then(v => { throw new Error('boom'); });
  const p4 = p3.catch(e => 'recovered');

  t=0   p1 created, executor runs, timer scheduled. p1 PENDING.
        p2 = p1.then(...)   p1 is pending -> push handler onto p1's
                            fulfil queue. p2 PENDING.
        p3 = p2.then(...)   p2 pending -> push onto p2's queue.
        p4 = p3.catch(...)  p3 pending -> push onto p3's REJECT queue.

        Four promises exist, all pending, wired together.

  t=10  the timer fires: res(1)
        p1 -> FULFILLED with 1
        drain p1's queue as a microtask:
            handler v => v + 1  runs with 1  -> returns 2
            2 is not a promise, so resolve p2 with 2
        p2 -> FULFILLED with 2
        drain p2's queue:
            handler throws Error('boom')
            a throw REJECTS the next promise
        p3 -> REJECTED with the error
        drain p3's reject queue:
            catch handler runs, returns 'recovered'
            a normal return from catch FULFILS the next promise
        p4 -> FULFILLED with 'recovered'

  The error travelled forward until something handled it, and
  handling it put the chain back on the success track.

Step 6

Version 1 — the minimum that works

Version 1 — state, queues and then
class SimplePromise {
  constructor(executor) {
    this.state = 'pending';
    this.value = undefined;
    this.onFulfilled = [];
    this.onRejected = [];

    const resolve = (value) => {
      if (this.state !== 'pending') return;        // rule 2: once only
      this.state = 'fulfilled';
      this.value = value;
      this.onFulfilled.forEach((cb) => queueMicrotask(() => cb(value)));
      this.onFulfilled = this.onRejected = [];
    };

    const reject = (reason) => {
      if (this.state !== 'pending') return;
      this.state = 'rejected';
      this.value = reason;
      this.onRejected.forEach((cb) => queueMicrotask(() => cb(reason)));
      this.onFulfilled = this.onRejected = [];
    };

    try {
      executor(resolve, reject);                   // synchronous
    } catch (err) {
      reject(err);                                 // a throwing executor rejects
    }
  }

  then(onFulfilled, onRejected) {
    return new SimplePromise((resolve, reject) => {
      const handleFulfil = (value) => {
        if (typeof onFulfilled !== 'function') { resolve(value); return; }  // pass through
        try {
          const result = onFulfilled(value);
          // if the handler returned a thenable, adopt it
          if (result && typeof result.then === 'function') result.then(resolve, reject);
          else resolve(result);
        } catch (err) {
          reject(err);
        }
      };

      const handleReject = (reason) => {
        if (typeof onRejected !== 'function') { reject(reason); return; }   // pass through
        try {
          const result = onRejected(reason);
          if (result && typeof result.then === 'function') result.then(resolve, reject);
          else resolve(result);                    // recovering puts us back on track
        } catch (err) {
          reject(err);
        }
      };

      if (this.state === 'fulfilled') queueMicrotask(() => handleFulfil(this.value));
      else if (this.state === 'rejected') queueMicrotask(() => handleReject(this.value));
      else { this.onFulfilled.push(handleFulfil); this.onRejected.push(handleReject); }
    });
  }

  catch(onRejected) { return this.then(undefined, onRejected); }
}

Two lines that look optional and are not

if (typeof onFulfilled !== 'function') { resolve(value); return; } is what makes p.then(null).then(v => ...) and p.catch(...) work — a missing handler must pass the value through, not swallow it.

And in handleReject, a handler that returns normally calls resolve, not reject. Catching an error means you have dealt with it, so the chain continues on the success track. Getting that backwards makes every catch re-throw forever.

Version 2 — all four, implemented
function myAll(promises) {
  return new Promise((resolve, reject) => {
    const list = Array.from(promises);
    const results = new Array(list.length);
    let remaining = list.length;

    if (remaining === 0) { resolve([]); return; }    // empty input fulfils at once

    list.forEach((p, i) => {
      // Promise.resolve() so plain values work too
      Promise.resolve(p).then(
        (value) => {
          results[i] = value;          // by INDEX -- order must be preserved
          if (--remaining === 0) resolve(results);
        },
        reject                          // first rejection wins; later ones ignored
      );
    });
  });
}

function myAllSettled(promises) {
  return new Promise((resolve) => {
    const list = Array.from(promises);
    const results = new Array(list.length);
    let remaining = list.length;

    if (remaining === 0) { resolve([]); return; }

    list.forEach((p, i) => {
      Promise.resolve(p).then(
        (value) => { results[i] = { status: 'fulfilled', value }; },
        (reason) => { results[i] = { status: 'rejected', reason }; }
      ).then(() => { if (--remaining === 0) resolve(results); });
    });
  });
}

function myRace(promises) {
  return new Promise((resolve, reject) => {
    // no counter at all -- settling a promise twice is a no-op,
    // so the first one through simply wins
    for (const p of promises) Promise.resolve(p).then(resolve, reject);
    // note: an EMPTY input means this promise stays pending forever,
    // which is exactly what the real Promise.race does
  });
}

function myAny(promises) {
  return new Promise((resolve, reject) => {
    const list = Array.from(promises);
    const errors = new Array(list.length);
    let remaining = list.length;

    if (remaining === 0) {
      reject(new AggregateError([], 'All promises were rejected'));
      return;
    }

    list.forEach((p, i) => {
      Promise.resolve(p).then(
        resolve,
        (reason) => {
          errors[i] = reason;
          if (--remaining === 0) {
            reject(new AggregateError(errors, 'All promises were rejected'));
          }
        }
      );
    });
  });
}

// promisify: callback API -> promise API
function promisify(fn) {
  return function (...args) {
    return new Promise((resolve, reject) => {
      fn.call(this, ...args, (err, value) => (err ? reject(err) : resolve(value)));
    });
  };
}

// deferred: a promise whose resolve/reject you hold from outside.

function deferred() {

Step 8

Complexity, in sentences

OperationCost
then on a pending promiseO(1) — one array push
resolveO(k) for k attached handlers
A chain of d thensO(d) promise objects, O(d) microtasks
Promise.all of nO(n) time, O(n) space

Nothing here is algorithmically interesting, and that is the point — a promise is bookkeeping. The costs that bite in practice are different in kind:

  • Each link in a chain is a microtask. A ten-deep chain means at least ten microtask hops before the final value, which is why await in a hot loop is slow.
  • A pending promise holds its handlers, and its handlers hold their closures. A promise that never settles is a memory leak with an unlimited lifetime.
  • Promise.all keeps every result alive until the last one lands. For a thousand large responses that is a thousand large responses in memory at once.
Say this in the interview

“A promise holds a state, a value, and two arrays of callbacks. The executor runs synchronously in the constructor; resolve and reject flip the state once and drain the queues. then returns a new promise, and has two cases: if this one is still pending, push the handler into the array; if it has already settled, schedule the handler as a microtask myself. The handler's return value settles the new promise — a plain value fulfils it, a throw rejects it, and a thenable is adopted, which is what makes chaining flat rather than nested.”

Mistakes people actually make

1. Not handling the already-settled case in then

Broken — the promise hangs forever
class BrokenPromise {
  constructor(executor) {
    this.state = 'pending'; this.value = undefined;
    this.callbacks = [];

      if (this.state !== 'pending') return;

class SyncPromise {
  constructor(executor) {
    this.state = 'pending'; this.value = undefined; this.cbs = [];
    const resolve = (v) => {
      if (this.state !== 'pending') return;
      this.state = 'fulfilled'; this.value = v;

  }

What to carry forward

“Settle once, then replay to anyone who asks” is the whole idea. The state machine is trivial; what makes promises useful is that the result is a value you can pass around, and that a late subscriber gets the same answer as an early one.
