Arrays · Problem 11

Majority Element

Find the value that appears more than half the time — using one variable and one counter. The Boyer–Moore voting algorithm is four lines long and, once you see the idea behind it, genuinely obvious.

Step 1

The problem

An array contains a majority element: a value that appears more than n / 2 times. Find it. You may assume it always exists.

InputLengthAnswerCount needed
[3, 2, 3]33more than 1.5, so at least 2
[2, 2, 1, 1, 1, 2, 2]72more than 3.5, so at least 4
[1]11trivially
[6, 5, 5]35
“More than half” is much stronger than “most common”

In [1, 1, 2, 2, 3] the most common values are 1 and 2 with two each — but neither exceeds 2.5, so there is no majority element. That distinction is what makes the clever algorithm possible. “Most frequent” needs counting; “more than half” does not, because a value with more than half the slots has a property nothing else can have: it outnumbers everything else put together.

Step 2

Think first — the obvious answers

Version 0a — count each value the hard way
function majorityBrute(nums) {
  const half = nums.length / 2;

  for (let i = 0; i < nums.length; i++) {
    let count = 0;
    for (let j = 0; j < nums.length; j++) {
      if (nums[j] === nums[i]) count++;
    }
    if (count > half) return nums[i];
  }

  return -1;
}

console.log(majorityBrute([3, 2, 3]));                  // 3
console.log(majorityBrute([2, 2, 1, 1, 1, 2, 2]));      // 2
console.log(majorityBrute([1]));                        // 1
Version 0b — a frequency map
function majorityMap(nums) {
  const counts = new Map();
  const half = nums.length / 2;

  for (const n of nums) {
    const c = (counts.get(n) || 0) + 1;
    if (c > half) return n;      // return as soon as one crosses the line
    counts.set(n, c);
  }

  return -1;
}

console.log(majorityMap([3, 2, 3]));               // 3
console.log(majorityMap([2, 2, 1, 1, 1, 2, 2]));   // 2

// O(n) time, O(n) space. This is a perfectly good answer, and the
// one you would write at work. The rest of this page is about
// getting the space down to O(1).
Version 0c — sort and take the middle
function majoritySort(nums) {
  const s = [...nums].sort((a, b) => a - b);
  return s[Math.floor(s.length / 2)];
}

console.log(majoritySort([3, 2, 3]));                // 3
console.log(majoritySort([2, 2, 1, 1, 1, 2, 2]));    // 2
console.log(majoritySort([6, 5, 5]));                // 5

// Why does taking the middle work?
// If a value occupies MORE THAN HALF the slots, then after sorting
// it forms one solid block longer than half the array. A block that
// long must cover the centre, whatever else is around it.
//
//   [1, 1, 2, 2, 2, 2, 2]     middle index 3 -> 2   correct
//   [2, 2, 2, 2, 2, 1, 1]     middle index 3 -> 2   correct
//
// O(n log n) time. A very good answer to give in ten seconds.

That sorting argument is worth having ready. It is short, provably correct, and requires no cleverness — the sort of answer that buys you time to think about the O(1)-space version.

Step 3

Why they are not good enough

The nested loop is O(n²) — unusable at scale. The map is O(n) time but O(n) memory, which matters when the array is a stream of a hundred million events and you cannot hold a counter per distinct value. The sort is O(n log n) and either allocates a copy or destroys the input.

Timing demo
// The majority value is parked at the END, so the brute force has to
// count thousands of unique values -- a full pass each -- before it
// ever reaches one that wins.
const HALF = 7500;
const nums = [];
for (let i = 1; i <= HALF; i++) nums.push(-i);      // 7,500 unique values
for (let i = 0; i <= HALF; i++) nums.push(999);     // 7,501 copies -- the majority

function brute(a) {
  const half = a.length / 2;
  for (let i = 0; i < a.length; i++) {
    let c = 0;
    for (let j = 0; j < a.length; j++) if (a[j] === a[i]) c++;
    if (c > half) return a[i];
  }
  return -1;
}

function voting(a) {
  let candidate = null, count = 0;
  for (const n of a) {
    if (count === 0) candidate = n;
    count += (n === candidate) ? 1 : -1;
  }
  return candidate;
}

let t = performance.now();
const x = brute(nums);
const bruteMs = performance.now() - t;

t = performance.now();
const y = voting(nums);
const fastMs = performance.now() - t;

console.log('array length   :', nums.length);
console.log('counting each  :', x, 'in', bruteMs.toFixed(1) + ' ms');
console.log('voting         :', y, 'in', fastMs.toFixed(2) + ' ms');
console.log('same answer    :', x === y);
console.log('speed-up:', Math.round(bruteMs / Math.max(fastMs, 0.01)) + 'x');
Step 4

The better idea — cancel votes in pairs

Forget arrays for a moment. Imagine an election in a room. Everybody holds up a card with their candidate’s name. Now play this game:

The unlock

Repeatedly find two people supporting different candidates and send them both out of the room. Their votes cancel.

If one candidate had more than half the votes, they cannot be eliminated. Every cancellation removes at most one of their votes and one of somebody else’s, and they have more votes than everybody else combined — so when the room finally runs out of disagreements, whoever is left standing must be them.

Work the numbers. Say the majority value has m votes and the rest have r votes, with m > r. Each cancellation subtracts one from each side, so the difference m - r never shrinks. Since it started positive, it stays positive, and something of the majority always survives.

Doing it in one pass

You do not need to actually pair people up. Track two things:

  • candidate — who is currently “holding the room”.
  • count — by how many votes, after all cancellations so far.

And for each new element:

  1. If count is 0, nobody is holding the room. The new element takes over as candidate.
  2. If it matches the candidate, count++ — one more supporter.
  3. If it does not, count-- — a cancellation, one supporter used up.
the whole algorithm
if (count === 0) candidate = n;
count += (n === candidate) ? 1 : -1;
What the algorithm does not promise

It does not find the most frequent element. It finds “the only value that could be a majority”. If no majority exists it still returns something — whatever happened to survive — and that answer is meaningless. When the problem does not guarantee a majority, you must add a second pass to verify. That verification pass is the most commonly forgotten part of this problem.

Step 5

Dry run — trace it by hand

nums = [2, 2, 1, 1, 1, 2, 2]. The answer is 2, which appears four times out of seven.

candidate = none   count = 0

n=2   count is 0 -> candidate = 2
      2 === 2  ->  count = 1            candidate 2   count 1
n=2   2 === 2  ->  count = 2            candidate 2   count 2
n=1   1 !== 2  ->  count = 1            candidate 2   count 1
n=1   1 !== 2  ->  count = 0            candidate 2   count 0
n=1   count is 0 -> candidate = 1
      1 === 1  ->  count = 1            candidate 1   count 1
n=2   2 !== 1  ->  count = 0            candidate 1   count 0
n=2   count is 0 -> candidate = 2
      2 === 2  ->  count = 1            candidate 2   count 1

answer: 2

Follow what happened in the middle. The run of three 1s knocked the count down to zero and took over as candidate. For a moment the algorithm believed the answer was 1. Then the trailing 2s cancelled that and reclaimed the room. This is normal — the candidate can change several times, and only the final one matters.

Now a case with no majority, to see the algorithm return nonsense:

nums = [1, 2, 3, 4]      -- no value appears more than twice

n=1   count 0 -> candidate = 1, count = 1
n=2   2 !== 1 -> count = 0
n=3   count 0 -> candidate = 3, count = 1
n=4   4 !== 3 -> count = 0

candidate ends as 3, count 0.
The algorithm "answers" 3. There is no majority at all.
This is why you verify.
the algorithm, narrating itself
function majorityExplained(nums) {
  let candidate = null;
  let count = 0;

  console.log('nums =', nums);
  console.log('');

  for (const n of nums) {
    if (count === 0) {
      candidate = n;
      console.log('n=' + n + '   count was 0 -> new candidate ' + n);
    }

    if (n === candidate) {
      count++;
      console.log('n=' + n + '   supports ' + candidate + '   count = ' + count);
    } else {
      count--;
      console.log('n=' + n + '   cancels  ' + candidate + '   count = ' + count);
    }
  }

  console.log('');
  console.log('surviving candidate: ' + candidate);

  // verify -- never skip this unless a majority is guaranteed
  let real = 0;
  for (const n of nums) if (n === candidate) real++;
  console.log('actual count: ' + real + ' out of ' + nums.length +
              '  (needs more than ' + (nums.length / 2) + ')');
  console.log(real > nums.length / 2 ? 'VERIFIED' : 'NOT a majority -- no answer exists');
  console.log('');

  return real > nums.length / 2 ? candidate : null;
}

Step 6

Version 1 — without built-in methods

Version 1 — Boyer–Moore voting
function majorityManual(nums) {
  let candidate = nums[0];
  let count = 0;

  // PASS 1: find the only value that could possibly be a majority
  for (let i = 0; i < nums.length; i++) {
    if (count === 0) {
      candidate = nums[i];      // nobody is holding the room -- take it
    }

    if (nums[i] === candidate) {
      count++;                  // a supporter
    } else {
      count--;                  // a cancellation
    }
  }

  // PASS 2: verify. Skip only if the problem GUARANTEES a majority.
  let occurrences = 0;
  for (let i = 0; i < nums.length; i++) {
    if (nums[i] === candidate) occurrences++;
  }

  if (occurrences * 2 > nums.length) {   // "more than half", no division
    return candidate;
  }
  return -1;                             // no majority exists
}

console.log(majorityManual([3, 2, 3]));               // 3
console.log(majorityManual([2, 2, 1, 1, 1, 2, 2]));   // 2
console.log(majorityManual([1]));                     // 1
console.log(majorityManual([6, 5, 5]));               // 5
console.log(majorityManual([1, 2, 3, 4]));            // -1  no majority
console.log(majorityManual([1, 1, 2, 2, 3]));         // -1  no majority
Why occurrences * 2 > length and not occurrences > length / 2

They agree for these inputs, but multiplying keeps everything in whole numbers. length / 2 produces 3.5 for a 7-element array, and once you are comparing against a fraction it is easy to reach for Math.floor and accidentally accept a value that ties rather than exceeds. Multiplying both sides by 2 removes the question entirely. It is a small habit that prevents a whole family of off-by-one bugs.

Step 7

Version 2 — with built-in methods

Version 2 — the interview answer
function majorityElement(nums) {
  let candidate = null;
  let count = 0;

  for (const n of nums) {
    if (count === 0) candidate = n;
    count += (n === candidate) ? 1 : -1;
  }

  return candidate;   // safe only because a majority is guaranteed
}

console.log(majorityElement([3, 2, 3]));               // 3
console.log(majorityElement([2, 2, 1, 1, 1, 2, 2]));   // 2
console.log(majorityElement([1]));                     // 1

// With verification, when no majority is promised:
function majorityElementSafe(nums) {
  const candidate = majorityElement(nums);
  const hits = nums.filter(n => n === candidate).length;
  return hits * 2 > nums.length ? candidate : null;
}

console.log(majorityElementSafe([2, 2, 1, 1, 1, 2, 2]));   // 2
console.log(majorityElementSafe([1, 2, 3, 4]));            // null
the frequency-map versions you will actually write
// Most frequent element (NOT necessarily a majority)
function mostFrequent(nums) {
  const counts = new Map();
  for (const n of nums) counts.set(n, (counts.get(n) || 0) + 1);

  let best = null, bestCount = 0;
  for (const [value, c] of counts) {
    if (c > bestCount) { best = value; bestCount = c; }
  }
  return { value: best, count: bestCount };
}

console.log(mostFrequent([1, 1, 2, 2, 2, 3]));   // { value: 2, count: 3 }
console.log(mostFrequent([1, 1, 2, 2]));         // { value: 1, count: 2 }

// Every element appearing more than n/3 times -- there can be at
// most two of them. Same voting idea with TWO candidates.
function majorityThird(nums) {
  let c1 = null, c2 = null, n1 = 0, n2 = 0;

  for (const n of nums) {
    if (n === c1) n1++;
    else if (n === c2) n2++;
    else if (n1 === 0) { c1 = n; n1 = 1; }
    else if (n2 === 0) { c2 = n; n2 = 1; }
    else { n1--; n2--; }              // cancel THREE different values
  }

  return [c1, c2].filter(c =>
    c !== null && nums.filter(x => x === c).length * 3 > nums.length
  );
}

console.log(majorityThird([3, 2, 3]));            // [3]
console.log(majorityThird([1, 1, 1, 3, 3, 2, 2, 2]));   // [1, 2]
console.log(majorityThird([1, 2, 3, 4, 5, 6]));   // []

The n/3 version is the standard follow-up, and it shows the pattern generalises: to find everything appearing more than n/k times, keep k - 1 candidates and cancel k distinct values at a time. Note that the order of the else if branches matters — you must check “matches an existing candidate” before “there is an empty slot”, or a repeated value can occupy both slots.

Step 8

Complexity, in sentences

SolutionTimeSpace
Count each valueO(n²)O(1)
Frequency mapO(n)O(n)
Sort, take the middleO(n log n)O(n) or O(1)
Boyer–Moore votingO(n)O(1)

Voting is optimal on both axes: you cannot beat O(n) time, because you must look at every element — miss one and it could have been the majority — and you cannot beat O(1) space. Two variables, whatever the input size.

There is another property worth naming: voting works on a stream. It never looks backwards, so you can run it over data arriving one element at a time and never stored. The map version cannot do that at scale, and the sort version cannot do it at all. That is the real-world reason this algorithm exists.

Say this in the interview

“A majority element outnumbers everything else combined, so if I repeatedly cancel one of its votes against one of any other value, it can never be fully cancelled. Boyer–Moore does that in one pass: keep a candidate and a counter; when the counter hits zero, adopt the current element as the candidate; increment on a match, decrement otherwise. The survivor is the only possible majority. O(n) time, O(1) space, single pass, streamable. If a majority is not guaranteed, I add a second pass to verify the count.”

Step 9

Mistakes people actually make

1. Skipping the verification pass

Broken — when no majority exists
function broken(nums) {
  let candidate = null, count = 0;
  for (const n of nums) {
    if (count === 0) candidate = n;
    count += (n === candidate) ? 1 : -1;
  }
  return candidate;      // no verification
}

console.log(broken([1, 2, 3, 4]));        // 3   -- confident nonsense
console.log(broken([1, 1, 2, 2, 3]));     // 3   -- also nonsense
console.log(broken([5, 5, 1, 2, 3, 4]));  // 3   -- also nonsense

// It never says "I do not know". If the problem guarantees a
// majority this is correct and fine. If it does not, this is a
// silent wrong answer, which is the worst kind.

2. Updating the candidate after the count check

Broken — wrong order
function broken(nums) {
  let candidate = nums[0], count = 0;
  for (const n of nums) {
    count += (n === candidate) ? 1 : -1;   // counted first
    if (count === 0) candidate = n;        // adopted after -- bug
  }
  return candidate;
}

console.log(broken([2, 2, 1, 1, 1, 2, 2]));   // 2   right, by luck
console.log(broken([1, 1, 1, 2, 2]));         // 1   right, by luck
console.log(broken([1, 2, 1]));               // 2   WRONG, should be 1

// Walk the last one through. candidate starts as 1, count 0.
//   n=1  matches   -> count 1
//   n=2  differs   -> count 0, and THEN adopts 2 as candidate
//   n=1  differs from 2 -> count -1
// The new candidate was adopted without being given its own vote,
// so it sits on a count of 0 instead of 1 and the array ends with
// the wrong survivor. Check for zero FIRST, then count.

3. Comparing with >= instead of >

“More than half” means strictly more. In [1, 1, 2, 2] the value 1 appears exactly half the time and is not a majority. Verifying with occurrences * 2 >= nums.length would wrongly accept it.

4. Assuming the candidate never changes

The trace in Step 5 shows the candidate switching from 2 to 1 and back to 2. People sometimes add a “once we have a candidate, keep it” guard, which breaks the algorithm on exactly the inputs where the majority is clustered at the end.

5. Reaching for the middle element without sorting

Broken — the middle of an unsorted array
function broken(nums) {
  return nums[Math.floor(nums.length / 2)];   // no sort -- bug
}

console.log(broken([2, 2, 1, 1, 1, 2, 2]));   // 1   WRONG, should be 2
console.log(broken([6, 5, 5]));               // 5   right, by luck

// "Take the middle" is only valid AFTER sorting, because sorting is
// what turns the majority into one solid block covering the centre.
Step 10

Practice before you move on

  1. Write the two-line core from memory, then say out loud why the count can never reach zero permanently when a majority exists.
  2. Majority Element II. Everything appearing more than n/3 times. It is in Step 7 — cover it and rewrite it, paying attention to the order of the branches.
  3. Generalise to n/k. Write a version taking k as a parameter, keeping k - 1 candidates in a Map. Then work out why there can be at most k - 1 answers.
  4. Return the count as well as the value. Note that count at the end of pass 1 is not the number of occurrences — it is what survived cancellation. You need the verification pass for the real number.
  5. Streaming version. Write it as an object with a push(value) method and a current() getter, so it can consume an endless feed. This is how the algorithm is actually used in practice, in heavy-hitter detection.
What to carry forward

Cancellation. When one thing is guaranteed to outnumber everything else combined, you can pair items off and destroy them without ever counting anything — the winner survives by arithmetic. The same shape appears in “find the number that appears once when all others appear twice” (XOR cancels pairs) and in heavy-hitter detection on data streams. Look for it whenever a problem promises a strict majority.
