Arrays · Problem 09

Move Zeroes

A small problem that carries a large idea: the read pointer and write pointer. One finger reads every element; a second, slower finger writes only the ones you want to keep. You will use this shape constantly.

Step 1

The problem

Move all the zeroes in an array to the end, in place, while keeping the non-zero numbers in their original relative order.

InputAnswerNote
[0, 1, 0, 3, 12][1, 3, 12, 0, 0]1, 3, 12 stay in that order
[0][0]nothing to do
[1, 2, 3][1, 2, 3]no zeroes at all
[0, 0, 1][1, 0, 0]

Two constraints, and each one rules out an easy escape:

  • In place. No building a new array and returning it. You must modify the one you were given.
  • Keep the order. [1, 3, 12, 0, 0] is right; [12, 1, 3, 0, 0] is not, even though the zeroes are in the right place.
Why this matters beyond the interview

“Keep the ones that pass a test, in order, without allocating a new array” is what every in-place filter, compaction, deduplication and garbage-collection sweep does. Move Zeroes is the smallest possible version of it, which is exactly why it is worth doing properly rather than reaching for filter.

Step 2

Think first — the obvious answer

Find a zero, remove it, stick a zero on the end. Repeat.

Version 0 — splice and push
function moveZeroesBrute(nums) {
  let zerosMoved = 0;

  for (let i = 0; i < nums.length - zerosMoved; ) {
    if (nums[i] === 0) {
      nums.splice(i, 1);   // cut the zero out -- everything after shifts left
      nums.push(0);        // put a zero on the end
      zerosMoved++;
      // do NOT advance i: a new value just slid into this slot
    } else {
      i++;
    }
  }

  return nums;
}

console.log(moveZeroesBrute([0, 1, 0, 3, 12]));   // [1, 3, 12, 0, 0]
console.log(moveZeroesBrute([0, 0, 1]));          // [1, 0, 0]
console.log(moveZeroesBrute([1, 2, 3]));          // [1, 2, 3]
console.log(moveZeroesBrute([0]));                // [0]

Two things here trip people up. First, after a splice you must not advance i — a different value now occupies that index, and skipping it misses consecutive zeroes. Second, the loop bound shrinks by zerosMoved, otherwise you walk back over the zeroes you already parked at the end and move them forever.

Step 3

Why it is slow

splice looks like one operation. It is not. Removing an element from the middle of an array means every element after it shifts one place left — that is an O(n) operation hiding inside a single method call. Do that once per zero and you have O(n²).

The methods that secretly cost O(n)

splice, shift, unshift and indexOf all touch the whole array. push and pop are the cheap ones, because they only work at the end where nothing has to move. Any time you see splice or shift inside a loop, suspect an accidental O(n²).

Timing demo
// Mostly zeroes -- the worst case for splice.
// Kept modest on purpose: the slow version really does block the
// browser for about a second, which is itself the lesson.
const N = 25000;
const base = [];
for (let i = 0; i < N; i++) base.push(i % 6 === 0 ? (i || 1) : 0);

function spliceVersion(nums) {
  let moved = 0;
  for (let i = 0; i < nums.length - moved; ) {
    if (nums[i] === 0) { nums.splice(i, 1); nums.push(0); moved++; }
    else i++;
  }
  return nums;
}

function twoPointer(nums) {
  let write = 0;
  for (let read = 0; read < nums.length; read++) {
    if (nums[read] !== 0) { nums[write] = nums[read]; write++; }
  }
  while (write < nums.length) { nums[write] = 0; write++; }
  return nums;
}

let t = performance.now();
const a = spliceVersion(base.slice());
const spliceMs = performance.now() - t;

t = performance.now();
const b = twoPointer(base.slice());
const fastMs = performance.now() - t;

console.log('splice loop  :', spliceMs.toFixed(1) + ' ms');
console.log('two pointers :', fastMs.toFixed(2) + ' ms');
console.log('same answer  :', a.length === b.length && a[0] === b[0] && a[N-1] === b[N-1]);
console.log('speed-up     :', Math.round(spliceMs / Math.max(fastMs, 0.01)) + 'x');
Step 4

The better idea — two pointers, different speeds

Stop removing things. Start overwriting instead.

The unlock

Use two indexes into the same array. read visits every element. write marks the next slot where a keeper belongs. Whenever read finds something worth keeping, copy it to write and advance write. Everything else is simply passed over — not deleted, just not copied.

Watch the two indexes drift apart. They start together, and write falls behind by exactly the number of zeroes seen so far:

       0   1   0   3   12
       r
       w                     read a 0 -> skip. w stays put.

       0   1   0   3   12
           r
       w                     read a 1 -> copy to slot w=0, w becomes 1

       1   1   0   3   12
               r
           w                 read a 0 -> skip

       1   1   0   3   12
                   r
           w                 read a 3 -> copy to slot w=1, w becomes 2

       1   3   0   3   12
                       r
               w             read a 12 -> copy to slot w=2, w becomes 3

       1   3   12  3   12
                            read pointer done. w = 3.
                            Slots 3 and 4 still hold junk from before.

fill from w to the end with zeroes:

       1   3   12  0   0     done.

Notice that at the moment read finishes, everything from index 0 to write - 1 is exactly the non-zero values in their original order. The tail [write .. end] is stale leftovers, and since we know the array must end with zeroes, we just overwrite that whole tail with zeroes. Two simple loops.

Is it safe to overwrite while reading the same array? Yes, and the reason is worth stating: write is never ahead of read. It starts equal and only advances when read also advances, so it can never clobber a value that read has not visited yet. When write === read, the copy is an element onto itself — harmless.

Step 5

Dry run — trace it by hand

nums = [0, 1, 0, 3, 12].

write = 0

PASS 1 -- copy the keepers forward

read=0  value 0   zero, skip                     array [0,1,0,3,12]   write=0
read=1  value 1   keeper -> nums[0] = 1          array [1,1,0,3,12]   write=1
read=2  value 0   zero, skip                     array [1,1,0,3,12]   write=1
read=3  value 3   keeper -> nums[1] = 3          array [1,3,0,3,12]   write=2
read=4  value 12  keeper -> nums[2] = 12         array [1,3,12,3,12]  write=3

PASS 2 -- zero out everything from write to the end

nums[3] = 0                                      array [1,3,12,0,12]
nums[4] = 0                                      array [1,3,12,0,0]

answer: [1, 3, 12, 0, 0]

Look at the array after pass 1: [1, 3, 12, 3, 12]. It contains duplicates and looks broken — and that is fine. The contract at that moment is only “indexes 0 to write-1 are correct”. Pass 2 makes the rest correct. Being comfortable with a half-finished array is part of learning in-place algorithms.

Step 6

Version 1 — without built-in methods

Version 1a — two passes, copy then fill
function moveZeroesManual(nums) {
  let write = 0;

  // pass 1: bring every non-zero value forward, in order
  for (let read = 0; read < nums.length; read++) {
    if (nums[read] !== 0) {
      nums[write] = nums[read];
      write++;
    }
  }

  // pass 2: everything left over must be a zero
  while (write < nums.length) {
    nums[write] = 0;
    write++;
  }

  return nums;
}

console.log(moveZeroesManual([0, 1, 0, 3, 12]));   // [1, 3, 12, 0, 0]
console.log(moveZeroesManual([0, 0, 1]));          // [1, 0, 0]
console.log(moveZeroesManual([1, 2, 3]));          // [1, 2, 3]
console.log(moveZeroesManual([0, 0, 0]));          // [0, 0, 0]
console.log(moveZeroesManual([0]));                // [0]
console.log(moveZeroesManual([]));                 // []

The one-pass version, with swapping

There is a variant that finishes in a single pass by swapping instead of copying. When read finds a keeper, it trades places with whatever sits at write — which is guaranteed to be a zero or the same element.

Version 1b — one pass, swapping
function moveZeroesSwap(nums) {
  let write = 0;

  for (let read = 0; read < nums.length; read++) {
    if (nums[read] !== 0) {
      // swap nums[read] and nums[write]
      const tmp = nums[write];
      nums[write] = nums[read];
      nums[read] = tmp;
      write++;
    }
  }

  return nums;
}

console.log(moveZeroesSwap([0, 1, 0, 3, 12]));   // [1, 3, 12, 0, 0]
console.log(moveZeroesSwap([0, 0, 1]));          // [1, 0, 0]
console.log(moveZeroesSwap([1, 2, 3]));          // [1, 2, 3]

// Why is the swap always safe?
// nums[write] is either a zero we passed over earlier, or -- when
// write === read -- the very element we are holding. Swapping a
// keeper with a zero moves the zero backwards, which is exactly
// where zeroes should go. Order is preserved because the keepers
// are copied in the order they were read.
Two passes or one?

Both are O(n) — two sequential passes add, they do not multiply. The swap version does one pass but performs three assignments per keeper; the copy version does two passes but one assignment per element. In practice they are the same speed. Prefer the one you can explain without hesitating. The copy version generalises better to “remove everything that fails this test”, which is why it is first here.

Step 7

Version 2 — with built-in methods

Version 2a — filter, but read the small print
function moveZeroesFilter(nums) {
  const keepers = nums.filter(n => n !== 0);
  const zeros   = nums.length - keepers.length;
  return [...keepers, ...new Array(zeros).fill(0)];
}

console.log(moveZeroesFilter([0, 1, 0, 3, 12]));   // [1, 3, 12, 0, 0]
console.log(moveZeroesFilter([0, 0, 1]));          // [1, 0, 0]

// Clear and short. But it RETURNS A NEW ARRAY -- it does not modify
// the one you were given, so it fails the "in place" requirement.
const arr = [0, 1, 0, 3, 12];
moveZeroesFilter(arr);
console.log('original untouched:', arr);   // [0,1,0,3,12]
Version 2b — in place, using built-ins honestly
function moveZeroes(nums) {
  let write = 0;

  for (const value of nums) {
    if (value !== 0) nums[write++] = value;
  }

  nums.fill(0, write);      // fill(value, startIndex) -- to the end
  return nums;
}

const a = [0, 1, 0, 3, 12];
moveZeroes(a);
console.log(a);            // [1, 3, 12, 0, 0]  -- modified in place

const b = [0, 0, 1];
moveZeroes(b);
console.log(b);            // [1, 0, 0]

const c = [4, 0, 5];
moveZeroes(c);
console.log(c);            // [4, 5, 0]

nums.fill(0, write) is the whole of pass 2 in one call, and it is the right kind of built-in to reach for: it does exactly the loop you would have written, with no hidden cost. Compare that with splice, which hides an O(n) shift behind a friendly name.

The general version: in-place filter

the pattern, generalised
// The same read/write pointer, with the test as an argument.
// This is the shape you will actually reuse.
function retainInPlace(arr, keep) {
  let write = 0;
  for (let read = 0; read < arr.length; read++) {
    if (keep(arr[read], read)) {
      arr[write] = arr[read];
      write++;
    }
  }
  arr.length = write;        // truncate -- drop the stale tail entirely
  return arr;
}

const nums = [3, 0, 7, 0, 0, 9, 2];
retainInPlace(nums, n => n !== 0);
console.log(nums);                          // [3, 7, 9, 2]

const words = ['a', '', 'bb', '', 'ccc'];
retainInPlace(words, w => w.length > 0);
console.log(words);                         // ['a','bb','ccc']

// arr.length = write is a genuinely useful trick: assigning to
// .length truncates an array in place, with no copy.
Step 8

Complexity, in sentences

SolutionTimeSpaceIn place?
splice + pushO(n²)O(1)yes
filter + concatO(n)O(n)no
Read/write pointersO(n)O(1)yes

Only the last row satisfies both requirements at once, which is why it is the answer.

“O(1) space” here means genuinely two integer variables, regardless of input size — the strongest kind of space claim. The number of writes is also worth mentioning: the copy version writes at most n times, and if the array has no zeroes at all, every write is nums[i] = nums[i], which some solutions guard against with if (write !== read). That guard changes nothing about the complexity.

Say this in the interview

“I avoid splice, because removing from the middle shifts the rest and turns this into O(n²). Instead I keep a write pointer at the next slot for a non-zero value and a read pointer scanning the array. Every non-zero gets copied to the write slot; at the end, everything from the write pointer onwards is filled with zeroes. O(n) time, O(1) space, in place, and stable because the keepers are copied in read order.”

Step 9

Mistakes people actually make

1. Swapping the zero forward instead of the keeper back

Broken — destroys the order
function broken(nums) {
  let last = nums.length - 1;
  for (let i = 0; i <= last; i++) {
    if (nums[i] === 0) {
      // swap this zero with the last element
      const tmp = nums[i];
      nums[i] = nums[last];
      nums[last] = tmp;
      last--;
      i--;                    // recheck this slot
    }
  }
  return nums;
}

console.log(broken([0, 1, 0, 3, 12]));   // [12, 1, 3, 0, 0]

// The zeroes ARE at the end. But 12 has jumped to the front --
// the relative order of the non-zero values is destroyed.
// This solution is correct for "move zeroes to the end" only if
// the problem does NOT ask you to preserve order. Read the question.

2. Advancing the read index after a splice

Broken — skips consecutive zeroes
function broken(nums) {
  for (let i = 0; i < nums.length; i++) {      // i++ always -- bug
    if (nums[i] === 0) {
      nums.splice(i, 1);
      nums.push(0);
    }
  }
  return nums;
}

console.log(broken([0, 0, 1]));      // [1, 0, 0]   looks fine
console.log(broken([1, 0, 0, 2]));   // [1, 0, 2, 0]  WRONG

// After splicing out the zero at index 1, the SECOND zero slides
// into index 1 -- but i has already moved to 2, so it is never seen.
// It also loops forever on some inputs, because the pushed zeroes
// keep the length up while i keeps finding them.

3. Counting zeroes but forgetting to overwrite the tail

A common half-solution copies the keepers forward and stops. The array then still holds stale values in the tail: [0,1,0,3,12] becomes [1,3,12,3,12]. The second pass is not optional.

4. Returning a new array when asked for in place

filter and map always allocate. If the signature is moveZeroes(nums): void, returning something is a hint you misread the requirement. Assign into nums, or use nums.length = k to truncate.

5. Treating other falsy values as zero

Broken — truthiness instead of equality
function broken(nums) {
  let write = 0;
  for (const v of nums) if (v) nums[write++] = v;   // `if (v)` -- bug
  nums.fill(0, write);
  return nums;
}

console.log(broken([0, 1, 0, 3, 12]));        // [1,3,12,0,0]  fine
console.log(broken([0, '', 5, null, 7]));     // [5,7,0,0,0]

// '' and null are falsy but they are NOT zero. They were silently
// deleted and replaced with real zeroes.
// Test the thing you actually mean:  v !== 0
Step 10

Practice before you move on

  1. Move zeroes to the front, keeping the non-zero order. Hint: run the same algorithm backwards, with write starting at the last index.
  2. Remove Duplicates from Sorted Array. Identical pattern: keep an element only if it differs from the last one you wrote. It is in the two-pointers topic and you can already write it.
  3. Remove Element. Delete every occurrence of a given value in place and return the new length. Literally this problem with 0 replaced by a parameter.
  4. Partition by a predicate. Move everything satisfying a test to the front and return the split point. That is the core of quicksort’s partition step.
  5. Count the writes. Modify the solution so it does not write when read === write, then measure how many writes each version does on an array with no zeroes. It is a good demonstration that two solutions with the same Big-O can still do very different amounts of work.
What to carry forward

Read pointer, write pointer. Whenever a problem says “in place” and “keep the order”, this is almost certainly the answer. The mental model: the read pointer inspects; the write pointer commits. Everything before write is finished and correct; everything from read onwards has not been looked at; the region between them is scrap you are allowed to overwrite.
