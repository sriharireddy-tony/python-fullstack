Arrays · Problem 01

Two Sum

This is the first problem in almost every interview list, and it is not there because it is hard. It is there because the trick it teaches — write down what you have already seen so you never have to look for it again — reappears in about a third of every other problem you will ever be asked.

Step 1

The problem

You are given a list of numbers and one target number. Find the two positions in the list whose numbers add up to the target, and return those two positions.

Explain it to someone who has never programmed, like this: you have a row of price tags and a fifty-rupee note. Which two tags add up to exactly fifty?

InputTargetAnswerBecause
[2, 7, 11, 15]9[0, 1]2 + 7 = 9
[3, 2, 4]6[1, 2]2 + 4 = 6
[3, 3]6[0, 1]the same value twice is fine
[1, 2, 3]99[]no pair works

Three rules that the problem statement always includes, and that beginners always skip:

  • Return the positions (indexes), not the values. [0, 1], not [2, 7].
  • You may not use the same element twice. Position 2 plus position 2 is cheating.
  • The same value appearing twice at two different positions is completely fine — see the [3, 3] row above. This is where a lot of solutions quietly break.
Step 2

Think first — the obvious answer

Before reading any clever solution, ask yourself what you would do with pen and paper. Almost everyone lands on the same thing:

Take the first number. Try it with the second, then the third, then the fourth… if none of them work, move on to the second number and try it against everything after it. Keep going.

That is a completely valid algorithm. It always finds the answer. Write it down first — in a real interview, saying “the brute force is two nested loops, O(n²); let me now improve it” scores far better than sitting in silence hunting for the clever version.

Turning that sentence into code needs two loops. The outer one picks the first number. The inner one picks a partner from the positions after it — and that j = i + 1 is doing real work: it stops us pairing a number with itself, and it stops us checking the pair (2, 7) and then later checking (7, 2) all over again.

Version 0 — brute force
function twoSumBrute(nums, target) {
  // i walks every position: the "first" number of the pair
  for (let i = 0; i < nums.length; i++) {

    // j starts one past i, so we never pair a number with itself
    // and never re-check a pair we already tried
    for (let j = i + 1; j < nums.length; j++) {

      if (nums[i] + nums[j] === target) {
        return [i, j];          // found it, stop immediately
      }
    }
  }
  return [];                    // looked at every pair, nothing added up
}

console.log(twoSumBrute([2, 7, 11, 15], 9));   // [0, 1]
console.log(twoSumBrute([3, 2, 4], 6));        // [1, 2]
console.log(twoSumBrute([3, 3], 6));           // [0, 1]
console.log(twoSumBrute([1, 2, 3], 99));       // []
Read the loop out loud

“For every position i, for every position j after it, if those two numbers add to the target, return both positions.” If you can say that sentence, you understand the code. Code you cannot say out loud is code you have memorised, not learned.

Step 3

Why it is slow

Count the comparisons instead of guessing. With 5 numbers, the outer loop runs 5 times, and the inner loop runs 4, then 3, then 2, then 1, then 0 times. That is 10 comparisons. In general it is n × (n − 1) / 2, which grows like n².

Look at what happens between the last two rows. The data got 10× bigger and the work got 100× bigger. That is the entire meaning of O(n²), and it is why a solution that felt fine on your test data falls over in production.

Do not take my word for it. Press Run — this builds an array of 20,000 numbers where the answer is deliberately hidden at the very end (worst case) and times both approaches:

Timing demo — slow vs fast
// Build 20,000 numbers. The only pair that works is the last two,
// so both solutions are forced to do their maximum work.
const N = 20000;
const nums = [];
for (let i = 0; i < N; i++) nums.push(i);
const target = (N - 1) + (N - 2);   // 39997 = last + second-last

function brute(nums, target) {
  for (let i = 0; i < nums.length; i++)
    for (let j = i + 1; j < nums.length; j++)
      if (nums[i] + nums[j] === target) return [i, j];
  return [];
}

function fast(nums, target) {
  const seen = new Map();
  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i];
    if (seen.has(need)) return [seen.get(need), i];
    seen.set(nums[i], i);
  }
  return [];
}

let t = performance.now();
const a = brute(nums, target);
const bruteMs = performance.now() - t;

t = performance.now();
const b = fast(nums, target);
const fastMs = performance.now() - t;

console.log('brute force :', a, '->', bruteMs.toFixed(1) + ' ms');
console.log('hash map    :', b, '->', fastMs.toFixed(1) + ' ms');
console.log('the fast one is roughly', Math.round(bruteMs / Math.max(fastMs, 0.01)) + 'x faster');

On my machine that printed 269 ms against 2 ms. Same answer, same language, same computer. The only difference is that one of them stopped repeating work.

Step 4

The better idea — and where it comes from

Here is the question that unlocks this problem, and it is worth memorising the question rather than the answer:

The unlock

What am I doing over and over that I could just write down instead?

Look again at the brute force. When it sits on the number 2 with a target of 9, it walks the rest of the array asking “are you 7? are you 7? are you 7?”. And it did the same kind of walk for the previous number, and it will do it again for the next one. The array is being re-scanned constantly.

Now flip the problem around. Standing on the number 2 with a target of 9, I do not actually need to search. I can calculate exactly what partner I need:

the whole idea in one line
need = target - current
     = 9      - 2
     = 7            // I am not searching. I know the answer is 7.

So the question stops being “which number pairs with me?” and becomes “have I already walked past a 7?” — and that is a question I can answer instantly if I have been keeping notes.

The notebook is a Map: value → the position it was at. Looking something up in a Map takes the same tiny amount of time whether the Map holds 10 entries or 10 million. That is the trade at the heart of this problem, and at the heart of most “make it faster” problems:

The trade

Spend a little memory (a Map holding what you have seen) to stop spending a lot of time (re-scanning the array). Almost every optimisation you will learn is some version of this sentence.

One detail that catches everyone

Check the Map before you add the current number to it, not after. If you add first, then with nums = [3, 3] and a target of 6 you would store 3, immediately look up 3, find the one you just stored, and return [0, 0] — the same element used twice, which the problem forbids. Checking first means you can only ever match against something genuinely earlier in the array.

Step 5

Dry run — trace it by hand

This is the most important section on the page. Cover the code and follow the table with a finger. nums = [2, 7, 11, 15], target = 9.

seen = {}          (empty notebook)

i = 0   nums[0] = 2
        need = 9 - 2 = 7
        is 7 in seen?  seen is empty  ->  no
        write it down:  seen = { 2 -> 0 }

i = 1   nums[1] = 7
        need = 9 - 7 = 2
        is 2 in seen?  YES, at position 0
        answer = [ seen.get(2), i ] = [0, 1]
        STOP

Notice we never reached positions 2 or 3. Notice also the order of the returned pair: seen.get(need) comes first because it was found earlier in the array, and i second. Getting that backwards is a real and very common bug.

Now a trace where the answer is not near the front. nums = [4, 1, 9, 3, 5], target = 8:

seen = {}

i = 0   value 4    need 4    seen has 4? no     ->  seen = { 4 -> 0 }
i = 1   value 1    need 7    seen has 7? no     ->  seen = { 4 -> 0, 1 -> 1 }
i = 2   value 9    need -1   seen has -1? no    ->  seen = { 4 -> 0, 1 -> 1, 9 -> 2 }
i = 3   value 3    need 5    seen has 5? no     ->  seen = { 4 -> 0, 1 -> 1, 9 -> 2, 3 -> 3 }
i = 4   value 5    need 3    seen has 3? YES at 3
                                  answer = [3, 4]      (3 + 5 = 8)

Read that trace again and notice what never happens: the array is never scanned backwards, never re-read, never searched. Each number is looked at exactly once. That is O(n).

Here is the same trace produced by the code itself — press Run and compare it line for line with the table above:

the algorithm, narrating itself
function twoSumExplained(nums, target) {
  const seen = new Map();
  console.log('nums =', nums, ' target =', target);
  console.log('');

  for (let i = 0; i < nums.length; i++) {
    const value = nums[i];
    const need  = target - value;

    console.log('i = ' + i + '   value = ' + value + '   need = ' + need);

    if (seen.has(need)) {
      console.log('        found ' + need + ' at position ' + seen.get(need) + ' -> answer!');
      console.log('');
      return [seen.get(need), i];
    }

    console.log('        ' + need + ' not seen yet, remember ' + value + ' at ' + i);
    seen.set(value, i);
    console.log('        seen =', seen);
  }

  console.log('reached the end, no pair exists');
  return [];
}

Step 6

Version 1 — without built-in methods

Now write it with nothing but loops, indexes and a plain object. No Map, no includes, no indexOf. This version exists so you can see there is no magic hiding anywhere.

A plain JavaScript object is itself a lookup table: seen[7] = 1 stores it, and seen[7] reads it back, both in constant time. That is genuinely all a hash map is, at the level that matters for this problem.

Version 1 — loops and a plain object
function twoSumManual(nums, target) {
  // our notebook: seen[value] = the position that value was at
  const seen = {};

  for (let i = 0; i < nums.length; i++) {
    const value = nums[i];
    const need  = target - value;

    // "have I written this number down before?"
    // Object.prototype.hasOwnProperty.call is the safe way to ask.
    // Why not `if (seen[need])`? Because if the stored position is 0,
    // `seen[need]` is 0, which is falsy, and we would miss a real answer.
    if (Object.prototype.hasOwnProperty.call(seen, need)) {
      return [seen[need], i];
    }

    seen[value] = i;   // write down where this value lives
  }

  return [];
}

console.log(twoSumManual([2, 7, 11, 15], 9));   // [0, 1]
console.log(twoSumManual([3, 2, 4], 6));        // [1, 2]
console.log(twoSumManual([3, 3], 6));           // [0, 1]
console.log(twoSumManual([-3, 4, 3, 90], 0));   // [0, 2]  negatives work fine
console.log(twoSumManual([1, 2, 3], 99));       // []
The falsy-zero trap

if (seen[need]) looks natural and is wrong. If the number you need was stored at position 0, then seen[need] is 0, JavaScript treats 0 as false, and you silently skip a correct answer. Try twoSumManual([2, 7], 9) with that bug in place and it returns []. Ask “does the key exist?”, never “is the value truthy?”.

And the version with no lookup table at all

For completeness: this is the same brute force from Step 2, written out with a manual result variable instead of an early return, which is how you would write it if the interviewer asked for all pairs rather than the first one.

variation — find every pair, not just the first
function allPairs(nums, target) {
  const result = [];

  for (let i = 0; i < nums.length; i++) {
    for (let j = i + 1; j < nums.length; j++) {
      if (nums[i] + nums[j] === target) {
        result[result.length] = [i, j];   // push(), written by hand
      }
    }
  }

  return result;
}

console.log(allPairs([1, 2, 3, 4, 5, 6], 7));   // [[0,5],[1,4],[2,3]]
Step 7

Version 2 — with built-in methods

This is the code you would actually write at work and in an interview. Map is the purpose-built tool for “remember a value, look it up fast”.

Version 2 — Map
function twoSum(nums, target) {
  const seen = new Map();          // value -> index

  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i];

    if (seen.has(need)) {
      return [seen.get(need), i];  // earlier index first
    }

    seen.set(nums[i], i);
  }

  return [];
}

console.log(twoSum([2, 7, 11, 15], 9));   // [0, 1]
console.log(twoSum([3, 2, 4], 6));        // [1, 2]
console.log(twoSum([3, 3], 6));           // [0, 1]
console.log(twoSum([-1, -2, -3, -4], -6));// [1, 3]
console.log(twoSum([1, 2, 3], 99));       // []

The version people write that quietly fails

Right answer, wrong complexity
function twoSumIndexOf(nums, target) {
  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i];
    const j = nums.indexOf(need, i + 1);   // search only after i
    if (j !== -1) return [i, j];
  }
  return [];
}

console.log(twoSumIndexOf([2, 7, 11, 15], 9));   // [0, 1]  correct!
console.log(twoSumIndexOf([3, 3], 6));           // [0, 1]  correct!

// It gives the right answers. So what is wrong with it?
// indexOf is itself a loop over the array. A loop inside a loop
// is O(n squared) -- exactly the brute force, just harder to see.
// It is three lines shorter and no faster at all.

This is the trap the index page warns about. A built-in method is not automatically fast. indexOf, includes, find and filter all walk the whole array. Only Map, Set and plain-object key lookup are constant time.

Step 8

Complexity, in sentences

SolutionTimeSpaceIn words
Brute forceO(n²)O(1)For each number, scan the rest. No extra storage.
Sort + two pointersO(n log n)O(n)Faster, but sorting destroys the original positions — and positions are the answer.
Hash mapO(n)O(n)Touch each number once, remember each number once.

Time O(n) means: the loop runs once per element, and everything inside the loop — one subtraction, one has, one set — takes the same time no matter how big the Map has grown. So the total work is proportional to the number of elements. Ten times more data, ten times more work. Not a hundred.

Space O(n) means: in the worst case (no pair exists) every number ends up in the Map, so the memory used grows in step with the input. That is the price of the trade, and it is almost always worth paying.

Say this in the interview

“Brute force is O(n²) time, O(1) space. I can trade space for time: one pass with a hash map storing value → index gives O(n) time and O(n) space. I check the map before inserting so I never reuse the same element.” That is roughly thirty seconds and it covers everything the interviewer is listening for.

Step 9

Mistakes people actually make

1. Inserting before checking

Broken
function broken(nums, target) {
  const seen = new Map();
  for (let i = 0; i < nums.length; i++) {
    seen.set(nums[i], i);                    // inserted FIRST -- bug
    const need = target - nums[i];
    if (seen.has(need)) return [seen.get(need), i];
  }
  return [];
}

console.log(broken([3, 3], 6));      // [0, 0]  <- position 0 used twice
console.log(broken([3, 2, 4], 6));   // [0, 0]  <- claims 3 + 3, but there is only one 3

// Fix: move seen.set() to AFTER the check.

Watch what it returns: [0, 0] — the same position twice. On the very first step it writes down “3 is at position 0”, then immediately asks “have I seen a 3?”, finds the note it wrote a line earlier, and believes it. The second example is worse: [3, 2, 4] has only one 3 in it, and the function still reports a pair. Check first, then write down.

2. Returning values instead of indexes

return [nums[i], nums[j]] returns [2, 7] when the problem asked for [0, 1]. Re-read the question before you write the return. This costs people real interviews.

3. Overwriting a duplicate’s position and not caring

worth understanding
// With [3, 3] the Map can only hold one key "3".
// The second set() overwrites the first. Does that break us?

const seen = new Map();
seen.set(3, 0);
seen.set(3, 1);
console.log(seen);          // Map(1) {3 => 1}  -- position 0 is gone

// It does NOT break Two Sum, because we check BEFORE we set.
// When i = 1 we look for 3, find the entry from i = 0, and return
// straight away -- the overwrite never happens.
//
// It WOULD break a problem that needs every occurrence.
// Then you store an array of positions instead:

function positionsOf(nums) {
  const at = new Map();
  for (let i = 0; i < nums.length; i++) {
    if (!at.has(nums[i])) at.set(nums[i], []);
    at.get(nums[i]).push(i);
  }
  return at;
}

console.log(positionsOf([3, 1, 3, 3]));   // Map {3 => [0,2,3], 1 => [1]}

4. Forgetting the “no answer” case

If no pair adds up, the loop simply ends. Without a return [] after the loop your function returns undefined, and the caller crashes on Cannot read properties of undefined. Every loop that searches for something needs an answer for “I did not find it”.

5. Assuming the array is sorted

It is not. Two Sum arrays are unsorted and may contain negatives, zeros and duplicates. [-3, 4, 3, 90] with target 0 is a valid input and the answer is [0, 2]. If a solution only works on sorted positive numbers, it does not work.

Step 10

Practice before you move on

  1. Close this page and rewrite the Map version from memory. If you cannot, you have not learned it yet — reread Step 4, not Step 7.
  2. Two Sum on a sorted array. If the input is guaranteed sorted, you can solve it with O(1) extra space using two pointers, one at each end: if the sum is too big move the right pointer left, too small move the left pointer right. Try it — you will meet this pattern again in the two-pointers topic.
  3. Return the values, not the indexes. A two-line change. Do it without re-reading the solution.
  4. Count how many pairs sum to the target (not just find one). Careful with duplicates: how many pairs does [1, 1, 1] with target 2 have? The answer is 3, not 1.
  5. Three Sum. Find three numbers that add to the target. Do not look it up. Just notice that if you fix one number, the rest is Two Sum on what is left — that reduction is the whole point of doing this problem first.
What to carry forward

The pattern you just learned has a name you will see everywhere: complement lookup, or more generally one pass with a hash map. Whenever a problem makes you compare every element against every other element, stop and ask the Step 4 question: what am I doing over and over that I could just write down instead?
